# 证据纪律（下判断前）

## 触发条件

- 要断言「没有 / 不存在 / 不可回核 / 无法复现」
- 要复核他人交付（不采信完成声明，回原件）
- 要对他人维护的区域（`docs/`／`TODO.md`／生成区／他人 log）下「表述有问题」类判断
- 判「假绿 / 假红」

## 怎么做

1. **对照组先钉通道**：判「0 命中 / 通道没反应」前，先跑一个明知存在的（阳性）对照 —— 否则「工具链失效」与「确无」同形（工具层故障会伪装成被测对象故障）。
2. **回原件，别停在中间层**：复核时去原件目录做逐字 / 哈希比对，不采信自产摘要（如 `raw.txt`）；判「原件已回收 ⇒ 不可回核」前，**先枚举原件目录的完整产物集**（曾只枚举自己用过的那类产物，被更原始的产物打出更强证据）。
3. **对外部区域**：① 先读回上下文（「留痕 / 勿当既成事实 / 历史记录」类标注会反转含义）；② 先查是否已被他人处置（定案区全文 ＋ `git log`）；③ 之后才谈「是否要改」。
4. **只读码不算数**：判「假绿 / 有没有缺陷」必须实跑一次（读码推出的「空掩码⇒假绿」曾被内核当场推翻）。
5. **收尾核现场**：取证 / 复核动作自身也会改现场 —— 清自建残留、核 `git status`、核被复核对象现状（如重放会覆盖原始 session）。

## 已知坑

1. **检索式不得截断**：⛔ 不用 `| head -N` 收窄取证检索（会静默吃掉命中）；说「没有」必须附完整检索式与遍历范围。
2. **印象 / 记忆不算证据**：对事实的任何断言先查记录再下结论（多 AI 协作下「我不知道的事」随时在发生）。
