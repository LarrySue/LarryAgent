# 探针：核查「某内容是否真的注入到 AI 上下文」

## 铁律（先记住这条）

**AI 无法内省自己的 system prompt。**

问 AI「你知道 X 吗 / 我被注入 X 了吗」得到的永远是**自我报告**，不是证据。
判「是否注入」**只能查外部记录**（trace ／ 请求体 ／ 日志）。

这条是既有纪律「判据须取自真实运行时，不能取自替身运行时」的直接推论。
真实案例：WB 曾报告「我核了上下文，没有这条注入」——**结论侥幸正确，但方法是不可靠的自省**；
真相只能靠 trace 钉死。另有反向案例：一度据「我没读到」推断「机制不存在」，实为**通道差异**。

## 何时用

- 用户问「我设的规则生效了吗」「这条指令有没有注入给你」「你为什么不知道 X」
- 刚改过自定义指令 ／ 记忆文件 ／ 规则文件，要确认**真的被加载**
- 排查「明明写了规则，AI 却违反」类问题

## 步骤

### 1. 定位存储（先钉住「存了什么」）

WorkBuddy 侧常见位置：

| 内容 | 路径 |
|---|---|
| 个人化「自定义指令」 | `~/.workbuddy/app/app-config.json` → `personalization.customPrompt` |
| 用户级记忆（每轮无条件注入） | `~/.workbuddy/user-<id>-personal/MEMORY.md`（⚠️ 2026-10 前后自 `~/.workbuddy/MEMORY.md` **迁移而来**；⛔ **旧路径那份仍在磁盘上、但已过期**，别读错） |
| 项目级记忆 | `<proj>/.workbuddy/memory/MEMORY.md` |

⚠️ **不要用 mtime 推断设置时点** —— 打开设置界面就会刷新它（实测踩过：据此误推「刚设置」）。

### 2. 找「实际发出的请求」记录

```
~/.workbuddy/traces/<端口号>/trace_*.json        # 旧格式（~2026-10-11 前）：单 JSON，spans 完整
~/.workbuddy/traces/<端口号>/trace_*.jsonl       # 新格式（2026-10-12 起）：逐行 span_start/span_end
```

⚠️ **jsonl 格式的 generation 请求体被截断在 ~20KB** —— 而 `<user_custom_instructions>` 块位于
**首轮 user 消息尾部**（`</product_identity>` 之后，**不在 system 消息本体**），刚好被截掉
⇒ **10-12 后的会话纯 trace 不可判**，只能判 10-11 前的旧格式会话；新会话只能新开会话用自报辅助。
先按扩展名分流再下结论，别把「截断」误判成「未注入」。

**探针选择**：别用指令内容本身做 needle（对话引用会污染命中）。用**结构探针**：
`user_custom_instructions` 标签字节存在性，或正则 `</product_identity>.{0,100}<user_custom_instructions>`
（真·注入形态）。内容 needle 命中 ≠ 注入，须再定位相对首个 `"role":"user"` 的位置。

每个文件含该会话的请求记录 ＋ spans。二进制安全搜索即可（json 内标签原样保留）。

### 3. 先做全量统计（**关键，别跳过**）

按**目录**统计「含 / 不含目标字符串」：

- 呈**两极**（某些目录 100%、某些 0%），且**时间交错** ⇒ **通道 / 窗口差异**（不同入口构造不同）
- 呈**单向时间趋势**（早的全有、晚的全无）⇒ **回归 / 被清空**

**这一步决定归因，单样本结论不可用。** 实测样本：1757 个 trace 中仅 112 个含注入（6.4%），
含注入目录多为 100%（12/12、8/8、5/5），零注入目录为 0%（0/195、0/235）⇒ 判定为窗口差异。

### 4. 同通道逐段对照（排除「trace 只存片段」）

取「已知含目标」与「待查」两份，对**同一 system prompt 的多个段落标记**做存在性对照
（如 `<content_policy>` ／ `<memory_system>` ／ `<user_memory>` …）。

若前半段偏移几乎一致、只差尾部几项 ⇒ **构造器相同，尾部缺失即真缺失**（排除截断误判）。
⚠️ 不做这一步，「找不到」可能只是「trace 没存全」，结论会反。

### 5. 结论分两层（别合并成一句）

- **机制层**：这条通道存不存在注入？（外部证据说话）
- **本次会话**：我此刻在不在那条通道上？

用户真正要知道的是**「此刻有没有生效」**。答「会注入」或「不会注入」都不完整。

## 6. 若目标是「记忆注入」：先量截断点，别看到标记就下结论

**三层信号（由弱到强）**：

1. **字面标记（最弱，仅供参考）** —— WB 的 `<user_memory>` 块末尾会出现 `(user memory truncated)`。
   有它 ⇒ 必然截断；**但没有它 ≠ 没截断**（可能按 token 截、也可能正好断在句边界）。
2. **文本形态（次弱）** —— 注入内容最后一条**半句断掉**／括号未闭合／条目突然中止。"读起来觉得别扭"通常就是它。
3. **对照法（唯一可定量、可复算）** —— 取注入里**能看到的最后一个短语**，去 grep 自己的记忆文件 ⇒ 得字符位置 ÷ 文件总字符 ＝ 截断比例。
   实测（2026-10-21）：`MEMORY.md` 总 **8801** 字符，注入止于 **4413** 字符 ＝ **50.1%**；用「含反引号」这一短语定位即可。

**⚠️ 三条坑**：
- **各家阈值不同，不能互相套用**（WB ≈ 4400 字符，别家未必）⇒ **要测，不要猜**。
- **截断只发生在"用户级"那一块，不是全部**：同一轮里 `<working_memory_content>`（项目级）是整段进来的 ⇒ 判"注入不全"必须先分清是哪一层。
- **记录「怎么测」而非「测到了啥」**：这个数随版本／会话形态变。

**处置**：量出阈值后，把**「读不到就等于没有」的内容放前半段**、把「截断了也能查回来」的放后半段 —— 比反复精简有效，且一个字不丢。

## 陷阱

- **污染**：一旦把目标文本读进上下文（读图 ／ 读配置文件），**本会话再测注入即失效** —— 必须开新会话重测。
  测完要主动声明污染，否则用户会拿被污染的会话继续测，得出错误结论。
- **长任务别接管道**：进程被 SIGTERM 时管道里的输出**整段丢失**（`cmd | head` 拿不到已打印内容）
  ⇒ 一律**先重定向落盘再读文件**。脚本遍历大目录时尤其容易触发。
- **mtime ≠ 内容创建时点**：UI 打开 ／ 应用启动都可能重写文件。见步骤 1。
- **别问 AI**：见铁律。AI 的「我知道 / 我不知道」不构成证据。
- **未查到底要如实说**：查不到的（如客户端逻辑在打包产物里）就写「未查明」，不要编成因。

## 输出模板

1. **能否读到**：目标内容本身是否进入本轮上下文（多模态附件 ≠ 注入）
2. **存储位置**：实读到的路径与字段（含原文片段）
3. **注入形式**：外部记录里的实际形态（如 `<user_custom_instructions>` 块）
4. **全量统计**：总数 ／ 命中数 ／ 比例 ＋ 两极 or 趋势
5. **本会话归属**：在不在注入通道上（给对照表）
6. **建议**：如何让规则真正生效（通常是搬进「每轮无条件注入」的通道）
