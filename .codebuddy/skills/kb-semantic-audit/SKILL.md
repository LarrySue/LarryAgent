# kb —— 语义检索 ＋ 文档语义体检

> **一句话：检索是手段，读「命中分布」才是目的。**
> 它不只回答"这句话在哪"，还能回答"我们文档里对这件事的表述，是不是只有一处、说没说清、有没有自相矛盾"。
> ⇒ 别把它当"模糊版 grep"用，那样只用到了它一半。

## 一、何时用（与 grep 的分工）

| 场景 | 用哪个 |
|---|---|
| 关键词已知，要精确位置／精确计数 | **grep**（更快更准，可复算） |
| 怀疑自己的词不对（换了三种说法都 grep 无果） | **kb 先行** |
| 聚合类："哪些地方讨论过 X""这个概念散落在哪几份" | **kb** |
| **文档语义体检**（本技能的核心增量，见 §四） | **kb** |
| 查 `TODO.md`／`exchange/log-*`／各 AI 记忆区 | **直接读文件** —— 索引刻意排除流水层，查了也是空 |

## 二、可复跑命令

```bash
cd "D:/AI Work/knowledge engine"

python kb.py stats   -p LarryAgent          # ① 先看索引构成（块数分布）——体检第一步
python kb.py search "<查询>" -p LarryAgent -k 8   # ② 日常：懒更新 + 检索
python kb.py sync    -p LarryAgent          # ③ 改了 kb.json 的 exclude 后用（秒级，不必 rebuild）
python kb.py rebuild -p LarryAgent          # ④ 索引坏了／换模型时（分钟级）
```

- `-p larryagent-ref` = 只查参考资料层（`ref/`）。**DSH 策展类查询走它**，别混进主库查。
- 配置在 `LarryAgent/kb.json`（`root` / `include_suffix` / `exclude`，fnmatch 语义，`*` 跨目录）。
- 输出格式：`#序 分数 绝对路径:起-止 [标题路径]` ＋ 片段预览。

## 三、判读三条铁律

1. **命中是 🟡 级线索** ⇒ 引用任何内容前必须 `Read` 命中位置的**正本**核对（与"背诵不可信，验证读盘"同一条纪律）。
2. **只看排序，不看绝对分**。低分段（经验上 ≲0.55）常是噪声水位 —— **top1 也可能是错的**。
3. 分数相近（±0.02）视为**并列** ⇒ 别在一堆并列里挑一个当"唯一命中"，那是在编故事。

## 四、⭐ 语义体检：把检索当测量

### 4.0 ⛔ 前置闸：**先证明索引健康，再解释分布**（不通过就只出检索层结论）

> **为什么**：命中分布可能是**索引缺陷**的产物，不是文档语义的产物。索引坏了的时候，"排不上来"跟"文档没写清"**长得一模一样** —— 直接解释分布，会把"索引坏了"判成"文档该改"，然后去改一份本来没问题的文档。

**三条自检**（在 `indexes/` 目录跑，秒级、只读）：

```bash
cd "D:/AI Work/knowledge engine/LarryAgent/indexes"

# ① 向量坍缩：**分型**——A 类＝文本互异却 bit 级同向量（真坍缩，>0 才不准做分布类结论）；B 类＝组内 text 完全相同（语料重复，非引擎缺陷）
python -c "import numpy as np,json;X=np.load('index.npy');ch=json.load(open('index.meta.json',encoding='utf-8'))['chunks'];u,inv,c=np.unique(np.ascontiguousarray(X).view([('','float32')]*X.shape[1]),axis=0,return_inverse=True,return_counts=True);rows=[np.where(inv==g)[0] for g in np.where(c>1)[0]];A=sum(1 for r in rows if len({ch[i]['text'] for i in r})>1);print('A真坍缩',A,'组 | B文本重复',len(rows)-A,'组 | dup总组',len(rows))"

# ② 长面包屑：**回归探测器**（引擎已有 PREFIX_BUDGET=120 硬截断 ⇒ 结构性恒 0，见下方判据）
python -c "import json;ch=json.load(open('index.meta.json',encoding='utf-8'))['chunks'];t=[c for c in ch if len(c['title'])>800];print('long-breadcrumb',len(t),sorted({c['file'] for c in t}))"

# ③ 空块／碎片块：只有标题或 `---` 的占位块（它们会占用 top-k 名额）
python -c "import json;ch=json.load(open('index.meta.json',encoding='utf-8'))['chunks'];print('fragments',sum(1 for c in ch if len([l for l in c['text'].splitlines() if l.strip()])<=2),'/',len(ch))"
```

**判据**（v1.3.1 改，与引擎 `check_index` 同口径）：

| 读数 | 怎么判 | 理由 |
|---|---|---|
| **A 真坍缩 > 0** | 🔴 索引不健康 ⇒ 只出检索层结论 | 文本各异却同向量 = 嵌入窗口被挤爆的硬症状 |
| **B 文本重复 > 0** | ⚪ **不红**（语料属性） | 组内 `text` 完全相同 ⇒ 同一段被重复收进来，引擎没算错 |
| `long-breadcrumb > 0` | 只证"**引擎被回退**"，⛔ 不证健康 | 引擎 `PREFIX_BUDGET=120`／`EMBED_BUDGET=540` 硬截断（`kb.py:44-45,192`）⇒ **结构性恒 0** |
| `fragments` | 只作参考（>5% 时 top-k 名额被挤） | 必须抽验，见下条 |

- ⚠️ **A 类命中后先分型再看要不要报警**：同一段的多语言翻译（如 README 英／俄 `## 📄 License` 与 `## 📄 Лицензия`，标题不同、正文逐字相同）**也是 A 类**（text 不同只因标题），但它是**语料近重复**、不是引擎缺陷。⇒ 先抽 1–2 组看 text 差异在哪，再决定是"修索引"还是"这本库本来就这样"。
- ⚠️ **B 类虽不红，但有一条副作用值得记**：多语言 README 的同一段落被收 5 次 ⇒ 检索时同一段内容独占 5 个 top-k 名额（多样性受损）。属**语料侧选择**（要不要把多语言 README 排掉），不是引擎 bug。
- ⚠️ **`long-breadcrumb` 恒绿不代表闸没问题**：它现在只能证明"没退回旧缺陷"。**别把它当"索引健康"的证据**——一个只见过绿的判据等于没验过，所以基线段保留了两组红／绿样例。

- ⚠️ **fragments 不能只看比例，必须抽验**：按"字数"过滤碎片块会**误杀"短但实义"的结论行**（实发生过：一次修复把 19 行真结论当空块丢掉，后改按**形状**过滤——只丢分隔线／表框／围栏／纯标题行——才修回）。⇒ 看到 fragments 大幅下降，先抽 3–5 条被剔掉的块，确认里面有实义结论。

- 🟢 **健康** ⇒ 照常做 §4.1–§4.4，可以下"文档语义病灶"结论。
- 🔴 **不健康** ⇒ **降级为检索层**：只回答"去哪儿读"，⛔ **不出**"概念散落／正本不自解释／结论未升格"这类分布类结论。**先把索引修好（或换用 grep），再谈文档。**

**索引坏了时，§4.2 的表会怎么骗你**（实测形态，逐条对上）：

| §4.2 的判据 | 索引不健康时的假象 |
|---|---|
| 同一概念命中散在 3+ 文件 | 坍缩块**不参与**正常分布 ⇒ **低估**该区域的重复，漏报 |
| 正本排不过旁支 | 坏掉的那一侧**根本排不上来** ⇒ 把"索引坏了"读成"正本不够自解释"，从而**去改一份没问题的文档** |
| 命中过程稿而正本无结论 | 空块／碎片块**占着 top-k 名额** ⇒ 看起来"正本缺失"，其实是被占位块挤掉 |

> ⚠️ **基线会变，⛔ 别当常量引用，每次体检现跑**。三组实测（判据演变＋两个 profile）：
> - **修复前（主库，旧粗判据下红）**：`dup rows 200 / distinct 2476`（总 2648）、`long-breadcrumb 143`（全在 `archive/roadmap-history.md`，成因＝`:541` 一个 968 字符的 `####` 标题把正文挤出 512-token 窗）、`fragments 304/2648`。
> - **修复后（主库，2026-10-19 复跑）**：`A 0 / B 0 / 总 0`（总 1814）、`long-breadcrumb 0`、`fragments 135/1814`（≈7.4%）。总块数下降＝主库排除了 `ref/*`。
> - **ref 库（2026-10-19 实测，2735 块）**：`A 1 / B 26 / 总 27`、`long-breadcrumb 0`、`fragments 172/2735`（≈6.3%）。⭐ **这一组就是"旧粗判据会假红"的实证**：按 `dup rows > 0` 判，ref 库 27 组全红；按 A 类判，只有 1 组、且是 README 英／俄 License 跨语言近重复（正文逐字相同）⇒ 并非引擎缺陷。
> ⇒ 这三组的用处：**证明这道闸真的会红、也真的会转绿、还会在"语料天然重复"的库上假红**。判据用"A 类 `>0` 即红"，与具体数值无关。


### 4.1 出探针

同一主题，**换 4 种问法**各查一次（这四条就是你的"测量组"，记下来可复跑）：

| 探针 | 例子 | 测什么 |
|---|---|---|
| 定义式 | "X 是什么／X 的口径" | 权威定义落在哪 |
| 问题式 | "怎么避免 X" | 结论有没有用**问题语言**写过 |
| 否定式 | "不要 X 会怎样／不隔离会出什么事" | 有没有反面表述。⚠️ **不能用来判"一致／矛盾"** —— 见 §4.3 反义陷阱 |
| 同义词式 | 换成行业说法／口语说法再问 | 概念是否**只绑了一个专名** |

### 4.2 读分布 → 定病灶

> ⚠️ **本表只在 §4.0 闸通过后适用**；闸红时下表每一行都可能反向骗你。

| 症状（看命中集合的形状） | 说明什么 | 怎么办 |
|---|---|---|
| 同一概念命中**散在 3+ 文件**，每处都像"定义" | **概念无单一权威** | 留一处权威，其余改指针；⛔ 别让读者自己挑 |
| **正本排不过旁支**（参考资料／archive／过程稿压在自家结论前） | ① 索引范围被稀释（先 `stats` 看构成）② 正本的**标题／首句没把概念词写出来**（模型拿不到信号） | ① 调 `exclude`；② 给该段标题或首句补**自解释**的说法 |
| 一对正反查询**各自命中不同段** ⇒ 只是**矛盾候选对**，⛔ 不是矛盾结论 | 两侧可能真在对着干，也可能只是同义改写 | **逐字读**两段原文（否定词／必须-禁止／适用条件）再判；见 §4.3 |
| 一对正反查询**命中同一段** | ⚠️ **不能读成"文档一致"** —— 反义句在向量空间里极近，命中同段是**必然**，不是证据 | 无信号，别当结论；要判一致仍须读原文 |
| 该回答某问题的段**完全不在 top-k**，但 grep 能命中关键实体 | 该段写的是**内部术语**，没写"问题语言" | 补一句人话版定义（"这解决的是……的问题"） |
| 命中大量**过程稿／日志**而正本无对应结论 | **结论未升格**（治理信号） | 结论搬进 docs，过程稿只留回溯 |

⇒ **报告写法**：先列命中表（`file:line` ＋ 一句话"它其实在讲什么"），再给病灶判定与动作；**⛔ 不把检索结果本身当证据**，只当作"去哪儿读"的指路。

### 4.3 ⚠️ 反义陷阱 —— 向量接近 ≠ 语义一致

- **反直觉事实**：「**必须**断言 DB 路径」与「**禁止**断言 DB 路径」在向量空间里**非常相似**（词面几乎全同，只差一个否定）⇒ **高相似度不证明一致，它恰恰是矛盾的常见形状**。
- 所以判矛盾只能两步走：**向量粗筛**（把候选从几千段缩到几十对）→ **判官读正本逐字比**：否定词（不／禁止／勿／must not）、模态（必须／可／建议）、**适用条件**（谁、在哪、哪个阶段）。
- ⛔ 绝不能只凭"相似度 0.9"或"反义查询也命中了"就宣布两处矛盾——那是把线索当结论。这条是「背诵不可信，验证读盘」在向量世界的投影：**向量给 🟡 线索，定论必须回到 `file:line`。**

### 4.4 四类现成审计动作（把索引当"分析层"，不只是"检索层"）

| 动作 | 做法 | 产出 |
|---|---|---|
| **口径一致性扫描** | 同一概念（某默认值／某隔离规则…）在各文件的表述全部向量化后做**近邻聚类**；语义上扎堆的段落一把抓出来**人肉对账** | "三处各说各话"自己浮出来 |
| **矛盾候选对挖掘** | 相似度高但**字面性质相反**的句对（§4.3 的形状） | 候选对清单 → 逐条 Read 定案（⛔ 不批量判） |
| **孤岛检测** | 跟谁都不相近的段落 | 废弃文档 or 断链孤儿（git 账实不符的信号） |
| **历史漂移轨迹** | 逐版本向量化，看某口径的语义**从哪次提交开始偏** | "什么时候偏的"从感觉变成可量化（成本高，按需做） |

- **切块粒度是第一个要试的参数**：按标题切 vs 按段落切，直接决定近邻结果有没有意义。粒度不对，"同一概念"会被切成互不相邻的碎块，聚类全是假的。
- ⇒ **双向正反馈**（这是它比 grep 多出来的东西）：审计能查出"该段标题／首句没把概念词写出来"这类病灶；**修掉之后该段更容易被命中** ⇒ **文档更正确 ⇒ 索引更有用 ⇒ 下一次审计更准**。反过来，只当检索用，这条回路永远不会启动。

## 五、已知坑

- **模型是主题级的**：bge-small 系列对**意图级、推理链长**的查询会偏航（实测形态：问"怎么防止误连生产库"→ 命中一堆"部署坑清单"）⇒ 换措辞重试，或退回 grep。
- **索引排除流水层**（`TODO.md`／`exchange/log-*`／各 AI 记忆区）⇒ 查待办、查过程必然无果，**不是工具坏了**。
- 命中 `HUMAN*.md` 带 ⚠️ 标记 ＝ 体系外备忘 ⇒ ⛔ 不作项目口径依据。
- 大块过程日志类文件是**噪声源**，命中时要甄别（是不是又把过程稿当结论）。
- **懒更新是默认行为**：每次 `search` 前 diff 文件 sha256，新写的内容会自动进索引 ⇒ 日常不必手动 `sync`；`sync` 只在"改了 `exclude` 配置"时用。
- **体检前先 `stats`**：某目录块数占比异常高（比如参考资料层压过正本）时，排序问题多半不是模型，是索引范围。
- **反义陷阱（最贵的一个坑）**：向量模型对**否定不敏感** ⇒ 反义句、正反规定、`必须/禁止` 两种写法会被排在一起。凡是"这段说了不能 X、那段说了必须 X"的判定，⛔ 一律不许用相似度下结论（§4.3）。

## 六、别把它用成什么

- ⛔ 不是"更聪明的 grep"：已知关键词还用 kb 查，是把可复算的定位换成不可复算的相似度。
- ⛔ 不是证据来源：命中 ≠ 事实成立，它只证明"库里有段文字和你的问法像"。
- ⛔ 不是完备性证明：**没命中的话题不等于没人写过**（换措辞、退回 grep、或直接问人）。
