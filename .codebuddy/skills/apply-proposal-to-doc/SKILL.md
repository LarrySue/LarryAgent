# 提案稿套用与退役

> ⛔ **执行权已移交（2026-10-13 老大裁定）**：`docs/**` 与交流区讨论稿归 **Qoder** ⇒ 本技能（提案稿 ／ 讨论稿套用进权威文档 ＋ 退役草稿）**由 Qoder 执行**，WB 不再执行。
> 本文件保留全文，用途有二：① **移交 Qoder 吸收**（抽离版已入 `exchange/log-qoder.md`）；② WB 复验他的套用 ／ 退役动作时对照。⛔ 除非老大点名，WB 不按本技能触发执行。

把一份**已获批的过程稿**落到权威文档（`docs/` / 代码），然后**退役草稿**。与 `doc-sunset-handoff`（清退）互补：那个是"扔"，这个是"搬"。

## 何时用

- 「把 `exchange/xx-revision.md` 应用到 `docs/yy.md` 上」
- 「套用这份提案」「按这份可审清单改」
- 讨论稿定稿、要合并进权威文档
- 「**他们都加了意见**，你先按当前状态提交一版，然后融合、保证意见不悬空、删除他们的意见、把定稿移入 docs」⇒ 见 §9 多方评审融合

## 铁律

### 1. ⭐ 先定稿件性质 —— 它决定动作形态

| 性质 | 特征 | 动作 |
|---|---|---|
| **内容稿** | 稿内是**成品内容**，可整段搬 | 合并 / 替换 → 退役 |
| **编辑指令集** | 稿内逐条写「**现状原文（含行号）→ 建议改后**」 | **套用编辑** → 退役 |
| 混合稿 | 部分节是成品、部分节是指令 | 逐节定性 |

⚠️ **编辑指令集若按"合并"字面理解 ⇒ 会造出双份"现状原文"**（稿里一份、目标文件一份），成为后续漂移源。判断法：看它是否在引用目标文件的**行号**与**逐字原文**——是则为指令集。

### 2. 锚点用内容匹配，不用行号

外部清单给的行号**必须逐条实测复核**（实测 2026-09-17：一份清单 8/8 行号全对，但**行号会因他人编辑而漂**，且清单作者扫的是某个快照）。执行时一律按**内容前缀匹配**定位。

⚠️ **锚点串本身要「从目标文件里读」，不要手抄进脚本**（实测 2026-09-21）：手抄一段长锚点（含中文标点／反引号／术语）极易**差一个字符**，而引号冲突会直接让脚本 **`SyntaxError`（编译期报错）** —— **前面所有步骤一行都没跑，却看不出进度**，浪费时间。⇒ 脚本里只存**短特征子串**做定位（`if KEY in line`），**长正文一律用三引号**承载。
⚠️ **表格行在列表项内常有前导缩进**（如 `    | **3** | ...`）⇒ `line.startswith('| ...')` 会**0 命中**；改用子串匹配，并在替换时**保留原缩进**（`IND = line[:len(line)-len(line.lstrip())]`）。

### 3. 脚本化 + 双断言，失败即不落盘

- **锚点断言**：每处编辑的锚点 `命中数 == 1`，否则打印候选行并 `exit(1)`（多在"当前"与"修订后"文本相似时命中 2 次）
- **计数断言**：批量插入（N 条子项、N 行字段）后统计插入数 `== 预期`，不符则不落盘
- 编辑清单**逐条独立**（不要写"先 A 再 B 依赖"的复合替换——一处失配会静默污染另一处）

### 4. 批量文本从源稿解析，不手抄

清单里有 N 行现成文本（如 31 行字段行）时，**正则解析源文件的代码块**取出，不手工转写 ⇒ 消除转写错误，且可断言条数。

### 5. ⭐ 出稿方的清单必查漏项

清单作者只扫了他关心的面。套用前**自己重扫目标文件 + 相邻文档**（实测：清单列了 2 处联动，我查出第 3 处——同一份被引稿在联动状态表里还有一行）。

### 6. 转写残留五查（清单不会写，但必须做）

1. **外部路径**：稿内引用的路径若属**别的仓库 / 参考件**（如浅克隆的 `ref/xxx/docs/...`），**不能原样搬进本仓** ⇒ 改述出处（写"取自 `<tag>` 的 `<子系统>` 规格"而非路径）
2. **草案口吻**：「抄进本条」「建议改为」「套用时注意」等对**套用者**说的话 ⇒ 改**正文口吻**
3. **枚举结构**：稿说「紧接 ① 之后」，而原行是 `①…；②…；③…` 的**分号枚举** ⇒ 插入会拆散，改为**行末追加 + 衔接词**
4. **符号一致性**：半角/全角引号、破折号、括号按**目标文件的既有惯例**统一
5. **列表连续性**：插入块**首尾的空行**会隔断原列表（4 条断成 2+2）⇒ 插入后检查列表是否被切段

### 7. 退役前置：查反向引用

`grep -r '<稿名>'` 全仓扫，命中分三类：

| 类型 | 处置 |
|---|---|
| **承重引用**（把内容委托给该稿）| 必须与套用**同批**处理，改指**已被套用的目标文件**（不是删掉） |
| **索引条目**（README 的稿名列举）| 同批删除 |
| **工具自生成缓存**（`.qoder/repowiki/` 等，通常已 gitignore）| 不用管；**先核 `git ls-files` 确认未跟踪** |

⚠️ 扫描面**必须含非文档文件**（`.ts` / `.py` 注释里也会写稿路径）。
⚠️ 「必须同批」的理由：套用后草稿退役，承重引用即成死链；分家处理会留下一个中间态。

### 8. 退役与落点

- 删前**逐节核**稿件独有内容是否全部有落点（含"未决清单 → TODO""判据原话 → 决策追溯"这类**非正文**内容）
- 活区规矩「已闭环的直接删除、不留指针、不留底（git 存底）」⇒ 删除
- 退役说明里**不留文件名**（写"原载 `exchange/`"而非"原 `exchange/xx.md`"）——与 `test-env.md` 那类"已清理"型引用同口径

### 9. ⭐ 多方评审融合（N 方意见 → 逐条处置 → 落进正文 → 删意见 → 移入权威区）

场景：稿件挂在交流区，被 N 方（不同职责的 AI / 人）**各自追加了评审附录**，要求「融合 → 保证意见不悬空 → 删除他们的意见 → 定稿移入 `docs/`」。

**六个步骤，缺一步就出问题**（顺序不可换）：

1. **先按原样提交一版存档**（**含全部意见**）—— 「删意见」≠「意见消失」，git 必须留底。提交信息里**逐方列条数与编号**（如「Trae 16 条 ／ Claude 11 条 ／ Qoder 10 条」＋分档），否则日后无法回溯"他当时到底提了哪几条"。
2. **核意见里的外部事实论断** —— 评审几乎必写「上游原文是 X」「npm 上版本是 Y」这类**可回源核**的断言。⚠️ **身份不为证据加权**：逐条回源核，且**注明取自哪条通道**。
   - 实测（2026-09-22，3 条）：2 条**成立**（逐字复核过上游文件与包依赖）；1 条**被改判** —— 原结论「某包不可启用」的观察面（`latest` dist-tag 停在旧代）**成立**，但同包存在当代版本且 `next` 指向它 ⇒ **若原实测未钉版本，该结论可能是装置产物**。
   - ⚠️ **此时不能直接采信、也不能直接推翻**（原结论取自定义装置的**运行时**通道，我核的是 registry ＋ 源码 tag ⇒ **通道不同，结论不可互推**）⇒ 写成 **未验项 ＋ 明确的重测建议**，并标出**影响面**（若推翻，哪些节会变）。
3. **逐条处置，三档各自留痕**：
   - **吸收** → 落进正文对应位置；正文里标注「v1.x 新增 ／ 修正」，便于实现方区分哪些是评审后加的
   - **部分吸收 / 改判** → 写清采纳了哪一半、理由是什么（实测：一方要求「把超时值拍死」，另一方给出更强理由反对 ⇒ 改「可配 ＋ 默认值」，并说明否决了一半）
   - **不吸收** → **必须给理由，且理由要落在正文里能被找到的地方**（实测：某条属产品文档层 ⇒ 正文写明「不在本稿决定，待定」，而不是默默不写）
4. **⛔ 删意见前，先扫「正文对附录的引用」** —— 这是**新一类反向引用**：不是引用别的文件，而是引用**同一文件里即将被删掉的节**。实测踩到：正文写着「（Trae 附录 A·C1 ／ Claude 附录 B·立场 1）」，附录一删即成**悬空引用** ⇒ 改成**主体名**（「Trae ／ Claude ／ Qoder 三方一致」），⛔ 正文里不留「附录 X」字样。
5. **核「稿件本体之外是否还有副本」** —— 各方可能把同一份意见也贴进了自己的 log ／ 其他文档。**有则同批处置**，否则"删意见"是假动作。（实测：三方 log 里均无副本，故只动稿件本体。）
6. **定稿落位 ＋ 同步索引 ＋ 提交** —— 正文里留一句「**含意见的存档版本 = git `<hash>`**」⇒ 让"删意见"不等于"抹掉痕迹"。提交信息里**逐条列处置结论**（这是"不悬空"的最终凭证）。

⚠️ **定稿与"进入下一轮"的分界**：若还有**必须由用户裁决**且**无法从评审意见收敛**的项，则**不要定稿**，留在交流区进入下一轮。反之，若各方意见**一致**（如本轮两处岔路 N 方同向）⇒ 可依一致意见**收敛定案**，但必须在正文与报告里**显式标注"非用户裁决"**并给出改判成本。

## 常见矛盾（主动暴露给用户，别自行消化）

- **新增字段行 vs 正文详细段内容重叠**：统一字段（速览）与逐条详细段（论证）常讲同一事实。**别默认"不冲突"** —— 要么明确分工（字段=速览 / 段=论证）、要么合并。这是清单作者常未预见的（他先出清单、你后套用，两者未对账）。
  - **老大 2026-09-17 对本案的裁决（可作先例）**：**允许精简** ⇒ 保留字段行（速览），**删掉详细段的重复叙述**，把详细段**独有的论证 / 限定并入字段行**（别直接丢）；并在该文档的读法节**立成规则**（"本行只作速览…同一事实不在两处各写一遍"）⇒ **套用后主动立规则，防未来再堆积**。
- **目标文档的变更记录表可能自述「此表不再修改」** ⇒ 本次改动要不要破例加行，交用户定。
  - **同案裁决**：**可以加行**，且**顺手撤掉该约束**（改写为"本表持续维护"）——产品文档的变更记录本就该随功能增补 / 口径修订持续维护，原约束是为阶段性冻结写的，不该长期生效。

## 复检清单

- **行尾**：**已由仓库 `.gitattributes` 统一为 LF**（`* text=auto eol=lf`，2026-10-08）⇒ 行尾由基建层保证，**无需再人工核对 / 维护**。
- **删块后查连续空行**：删掉一个引用块时注意**块首尾空行的归属**（把 old 串末尾的 `NL` 一并吃掉），否则留下三连空行
- `**` 加粗奇偶（脚本化扫）—— ⚠️ **但奇偶只抓「漏闭合」，抓不到「嵌套」**：`**A**B**C**` 也是偶数、也平衡，渲染却乱。实测（2026-09-21）自己往文档插一段含加粗的文案时踩到，奇偶扫描全绿、靠肉眼才发现。⇒ 插入**含加粗**的内容后，须另检「**加粗块内部再出现 `**`**」（用 `\*\*(.+?)\*\*` 逐个匹配，看 body 里还有没有 `**`）。**反例提醒**：「加粗块以 `）` 等标点结尾」这类启发式**没有区分度** —— 标题式加粗大量如此（实测 220 行命中 164 行，全是误报），别拿它当判据。⇒ ⚠️ **扫之前必须先剔除行内代码 span**（正则 `` `[^`]*` ``）再数奇偶 —— **行内代码里的 glob**（`harness/**` ／ `.qoder/repowiki/zh/content/**`）会被数成加粗标记 ⇒ **假阳性**（实测 2026-09-22：`TODO.md` 报出「三处疑似未闭合」，剔除后 **2 处**消掉、只剩 **1 处**真缺陷）。**肉眼看"有没有"可以，奇偶必须程序算、且口径要对。**
- 全仓残留引用扫描（排除已 gitignore 的工具目录）
- 敏感串扫描：`Bearer` / `password` / `secret` / `sk-` / `api_key`
- 提交前**重新 `git status`**（用户可能在你工作期间自己提交/改动）
- **改措辞前先全库 grep 同名表述**：同一矩阵／清单常在**多处有副本**。实测（2026-09-21）：`answerer 抛错或超时` 同时存在于 `TODO.md` 贯穿规则与 `dsh-migration.md` 负向对照矩阵 —— 只改一处会被读成"两处口径不一致"。⇒ **先 grep、再改、副本一起改**。
- **不变量检查的「口径」本身也要复核**：段标题形态多样（`#+` ／ `**`）。实测（2026-09-21）：只认 `**` 的口径把 `#### DSH-3.8` 之后的 `- [ ]` 误判成挂在前面带 ✅ 的段下，**误报 11 条** ⇒ 口径须覆盖全部标题形态；**报出冲突时先怀疑口径，别急着改文档**。
- **表格单元格里避免「code span 内含竖线转义」**：用 `\|` 在 code span 内表达竖线时各渲染器行为不一（CommonMark 规定 code span 内反斜杠是**字面量**，而 GFM 表格另有转义规则）⇒ **改写**成 `output 或 error` ／ `kind ∈ {unknown, settled}` 这类形式最稳。⚠️ 副作用：自检脚本按竖线计数时会把 `\|` 算进去，**误报"表格列数不一致"**（实测 2026-09-22 误报 3 处）—— 报出不一致时**先看该行有没有 `\|`**。
- **`git mv` 之后若内容同时被重写，可能不被识别为重命名**（相似度低于阈值 ⇒ 显示成 `A 新文件` ＋ `D 旧文件`）。**不影响**可追溯性（旧内容已在上一步的存档提交里），但**提交信息须写明"由 X 移入"**，否则读者会以为旧文件被直接删除。
