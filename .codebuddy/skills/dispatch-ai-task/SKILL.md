# 派发 AI 任务（写派发稿）

把一个工作切片交给执行方 AI 时，**派发稿的质量决定返工量**。
本技能把「怎么派」固定成骨架 ＋ 铁律，避免派出"执行人只能现场推导"的稿子。

配套：回报回来后的验收走 `verify-ai-delivery`。

## 何时用

- 用户说「派发 X」「派给 Y」「你派吧」「这块起跑」——**包括"你看着办派多少"这类授权**（此时要自己判拆块）
- 一个切片要交给执行方 AI，需要写任务规格 / 判据 / 参考件 / 场地
- 用户问「这块计划颗粒度够不够 / 该不该拆 / 要不要回 TODO 细分 / 能不能一次派发」——**即便本次不写稿，也用「拆块与编号」节自检**（拆不准的后果 = 多 AI 分不清自己那块 ⇒ 已做/未做混乱）

## 派发前必做四件事（**跳过这四步 = 派发稿必然缺项**）

1. **自己实测"前提是否仍成立"** ★ 最容易被跳过、也最贵的一步
   旧规格写的"前提已就绪"在写下的那一刻是真的，但**前提会随时间失效**。
   ⇒ 逐条去**磁盘上实测**：文件在不在、挂载点在不在、版本对不对、凭据有没有、脚本能不能跑。
   ⚠️ 实测教训：一份派发稿的三项"已定前提"全部是缺项，其中两项会直接造成「**落点对了却没生效**」。
   ⚠️ **远端场地同样要实测，不能默认"远端核不到"** ★（2026-09-20 实测）：
   一次派发把场地设在远端机器，本机侧前提逐条核了、**远端侧一条没核** —— 真连上去后发现**三处全缺**：
   稿里引的"平台分支"在那边**根本不存在**（那边是改动前的旧版）、某条"否则会 exit N"的提醒**只对改版后成立**、
   一份参考件**根本不在那台机**。⇒ 三处都**不会报错**，只会让执行人产出**对不上稿子的假矛盾**，
   或**自己造等价方案**（铁律 3 那个坑）。
   - 核远端**先解决通道**，而通道本身可能就是坑：本机 `ssh` 若是 **Windows OpenSSH**，
     给它 MSYS 风格路径（`/c/...`）或 `~` 会报 `not accessible` ＋ `Permission denied` ——
     **伪装成"沙箱／权限拒绝"**（实测：换 `C:/Users/...` 即通，且**无需免沙箱**）。
     ⇒ 报"被拒"之前先用同通道跑一条**必成功的对照**。
   - **"版本"的判据也要问「那边用什么判」**：本机常用 git 记版本，远端可能是**无 git 的同步副本**
     （靠 `SYNC-ANCHOR.txt` 之类的锚文件）⇒ 拿本机判据去核会"判不出来"，别当成"那边有问题"。
   - 远端副本每次**增量同步都留锚**（源 commit ＋ 时间 ＋ 件清单 ＋ sha），核版本读锚即可。
   - ⚠️ **要核到「本工程里能不能用」这一层，不能停在「包存在／文档说已公开导出」** ★（2026-09-21 实测）：
     本轮要用的一个官方包，**文档与包层面都是"公开导出、可用"**，但它在**本工程的 `package.json` 里没有** ——
     pnpm 严格模式下只躺在 `.pnpm` 深层 ⇒ `import` 直接报 **`ERR_MODULE_NOT_FOUND`**。
     ⇒ 漏了这层，执行人**第一件事就卡住**，且该报错**极易被误读成"包没装"**。
     ⛔ 判"可用"必须**在本工程的解析环境下实跑一次 import**（写个三行探针跑完即删），不要凭 `exports` 字段推断。
     ⚠️ 同族坑（同日实测）：**"包 A 依赖包 B" ≠ "能从包 A 借道拿到 B 的导出"** —— 实测某个重导出面**不含**你要的那个类。
   ⚠️ **核路径前先读源码里它的定义式，别凭目录名猜层级** ★（2026-09-22 实测）：
     核"源 profile 在否"时按 `harness/.dsh-home/...` 查 ⇒ **MISS**，差一步就把它当成"前提缺口"写进派发稿；
     按装置源码的定义式 `SRC_SDK = join(REPO,'.dsh-home','profiles','sdk')`（`REPO = resolve(HARNESS,'..')` ＝ **仓库根**）复核 ⇒ **存在**。
     ⇒ 同名的相对目录**极易错层级**，而"MISS ／ 不存在"这个读数**看不出错** —— 它和真缺项长得一模一样。⇒ 报缺项前先回源码**把路径拼出来**再 stat。
2. **定位参考件并落位**（不要把"去拉参考件"当成执行人的活）
   官方件读本地 `ref/` 或装好的产物；社区件**未落位就自己浅克隆**（`git -c http.proxy= -c https.proxy= clone --depth 1 <url> <dst>`）。
   找不到就写"无" —— **空着比编一个强**。
3. **确认场地与器材可达**：通道（能不能上机）、路径（写全、可复制）、版本（与基线同代吗）、
   以及那条**"不这么写就会假绿"的坑**（例：env 值不做路径转换 ⇒ 指错目录 ⇒ 工具自建空目录 ⇒ 判据全绿）。
4. **核"器材能不能验这个靶子"** ★ —— **「器材能跑」≠「器材能验目标」**。
   现成装置常带**隔离/覆盖行为**，会把你要验的对象**排除在外**（实测：测试装置 `isolated-setup` 强制覆盖 `DSH_HOME`
   到临时目录、刻意"不穿透源 profile" ⇒ 它**永远验不了工程 home 的落盘生效**）。
   ⇒ 逐条问：这个装置**跑的是哪个 home / 哪个 profile / 哪个通道**？是我要的那一个吗？
   ⚠️ 同时核**"源目录的随身行李"**：复制类任务要先看源目录**是否自带依赖树**（`node_modules`）。
   带则**必须排除**，否则"落点对了却在搬运时把坏树一起搬走" —— 判据会以"我没做错"的姿势失败。

   ⭐ **优先找"零副作用"的验靶手段**（2026-09-21 实测）—— 产物若是**配置层**（能否命中 / 禁用 / 插入位置 / 字段合并语义），
   用**配置预览**即可端到端验、**不必真 boot**：DSH 的 `dsh --profile <p> --dump-config` 组合出配置树就退出、**不激活插件**，
   且**被命中的条目会在来源注释追记 `, patched by <层>`、未命中的层会打 `not found` 警告** ⇒ 命中与否有**机械可读判据**。
   更好的是它的 **`--patch <临时层.yml>`（可重复叠加）= 无副作用试验通道** ⇒ **不改场地文件就能把写法试通**。
   ⇒ 把这条写进派稿的"场地器材"，执行人就不必用"改场地 ＋ 真跑"去试错。⚠️ 但这类预览路径的警告**往往仍 `exit 0`**（实测同上）⇒ 别把"退出码 0"当"没问题"。
   ⚠️ 顺带一条：**判"未命中"必须先有一个"必中的对照组"** —— 用一个明知不存在的目标跑出那条警告，才敢说"没警告 ＝ 命中"。

## 派发稿骨架（按此顺序，缺节即不完整）

```
0 · 目标          —— 一句话说清"要回答哪一个问题"；把"容易被混淆成同一件事的两个结论"显式拆开
1 · 判据          —— 逐条编号，每条写明"取什么证据"＋"缺这条即未闭合"
2 · 判据前置      —— 不满足则实验根本没跑起来、会得到假阴性（如：先清孤儿锁）
3 · 交付物        —— 具体路径 ＋ 命名 ＋ 退出码约定 ＋ 证据落哪
4 · 参考件四要素  —— ① 路径 ② 怎么参考 ③ 参考程度 ④ 哪部分不可参考（**照抄现成清单，勿另行转述**）
5 · 场地器材      —— 通道 / 路径 / 版本 / 环境变量注入方式 / 已知假绿坑
6 · 回报格式      —— 结论先行 ＋ 逐条证据 ＋ 未闭合项单列 ＋ **自曝**
7 · 禁区          —— 禁改什么、禁用哪个动作、禁把什么落盘
```

**顶部要有状态区**：在飞任务清单（块 / 执行人 / 场地 / 状态 / 派发日）写在**顶部**，
**不可只追加到末尾** —— 执行人是扫描式阅读，末尾追加等于没写。

## 铁律

1. **判据必须"可被第三方复跑"** —— 禁止"跑通了""验证过"这类自述型判据；每条要能写出**命令 ＋ 期望观测**。

2. **说"没有 / 不存在"必须附检索式与遍历范围** —— 否则不可验，等于没回答。

3. **前置要写"不通过 ⇒ 走哪条路"** ★ —— 只写"装前核版本"而不写"版本不同时走 A 还是 B"，执行人只能现场推导。
   实测教训：规格里缺这半句，执行人被卡住、只能自己造等价方案（运气好才等价）。

4. **参考件四要素照抄** —— ① 路径（可复制）② 怎么参考（读哪几个文件 / 读码还是读文档 / 要不要先跑）
   ③ 参考程度（只借设计 / 可抄形状 / 可 fork）④ **哪部分不可参考**（许可 / 与锁定版不符 / 与产品形态冲突 / 别搬它的骨架）。
   ⚠️ 外部参考件的**签名与行号常锚在别的版本**上 ⇒ 四要素④必须写"**须在本方实物上复核**"。

5. **归因类任务：判据要钉主体** ★ —— 「谁的沙箱 / 谁拦的 / 出自哪条通道」是判据的一部分。
   同一条拒绝，出自**工具沙箱**还是**被调用程序自身**，归属与严重性完全不同。
   ⇒ 要求执行人给**触发命令原文 ＋ 完整错误对象（code / errno / 栈帧模块路径）＋ 抛出者是谁**。

6. **结论不得跨通道外推** —— 明确写"**只写在实测过的那条通道上**"（A 能写 ≠ B 能写；本机 ≠ 远端；TS SDK ≠ Python SDK）。
   两通道结论分歧时**并列留痕、不合并**。

7. **负向对照必须派**，且**负向变体须双锚** —— 破坏 X ⇒ 断言 Y 变红，**同时**断言"其余仍活"，
   否则"环境没起来"与"破坏生效"不可区分（假通过）。破坏面**要实测**，别按变体名推断（名字常小于实际破坏面）。

8. **诚实边界要写进稿** —— 例："本块单独不得声称『X 语义验成立』"。让执行人知道**哪些话现在不能说**。

9. **回报格式要求自曝** —— 跑歪了 / 判据要订正 / 发现矛盾，**直接写**；
   并写明"**『成因未知』是可接受的结论，别为叙事完整编一个**"。

10. **凭据纪律** —— 稿里只写"取哪一层凭据"，**值一律不落稿**；
   并写明"值不得落任何受版本控制的文件 / 日志 / 工具输出"。

11. **别把"实现细节选择"塞进判据** —— 判据只约束**可观测结果**；实现路径留给执行人，否则会把实现写死、且后续无法演进。

12. **稿里要写"实测过的调用式"，并锁定手段** ★ —— 两条同类坑（2026-09-17 实测）：
    - **同一个工具在不同宿主 shell 下可用性不同，且裸调用崩掉的报错样貌很像工程故障** ⇒ 场地器材段必须写
      **实测过的调用式**，并要求执行方**先自证**（报版本）。例：本机 pnpm 必须 `pnpm.cmd -v`；裸 `pnpm`
      因 npm 的 sh 垫片缺 `sed`/`dirname`/`uname` 而崩、并把入口错解析到别的盘 ⇒ 执行方看到
      `Cannot find module '<错盘>:\node_modules\…'` 会误判成"**工程坏了**"。
    - **锁定包管理器**：涉及依赖树的任务写死用哪个，⛔ 显式禁止 `npm` / `yarn` 替代（换掉会重排整棵树 ⇒ 本块判据全作废）。

13. **合并派要留痕"为什么合并" ＋ "哪一件动哪棵树"** —— 多件合成一份稿时须写明合并理由
    （常见：同一交付面 / **同一靶子**；历史上还有“争用同一资源”＝同一场地 ＋ 同一棵 `node_modules` ⇒ 只能串行 —— 但本项目执行默认串行，此项一般不是合并的主要动因），以及**每件各自会动到哪棵树**。
    ⛔ 不写这段，后续无法判断"能不能拆开重派"，也看不出哪件把哪个环境弄脏了。

14. **判据要区分"引用者"与"被引用者"** ★ —— 清理/降级类任务的诚实边界：
    把**引用某旧版的东西**改掉/删掉，**不等于**把**那份旧版本体**迁走了。稿里必须把这两个结论**显式拆开**，
    并写明本次只覆盖哪一个（例：删掉拉入旧代的声明 ⇒ 只消掉"引用者"；镜像了旧解析结果的共享层
    （如 241 条 junction）需**另行处置**）。⛔ 混报会得出"旧代问题已彻底解决"的**错误结论**。

15. **场地器材的"版本"必须连「取自哪条通道」一起写** ★ —— 实测（2026-09-17）：派稿写「node 22.22.2」，
    执行方在其通道读到 **24.14.1** 并**报为矛盾**；复核发现**两者皆真**（我方通道 = managed `22.22.2` ／
    system `D:\App\node` = `24.14.1`）。⇒ **同机不同通道会给不同版本**（同族：python、包管理器、shell 内建），
    只写版本号 = **给执行方埋一个假矛盾**，会把复验预算烧在"对账"上。
    ⇒ 写法：`node 22.22.2（取自 Bash 通道）`；版本敏感的工具还要在稿里写明「以你通道实测为准，对不上先报差异再动手」。

16. **禁出现"手工整理 ／ 意译工具输出"的余地** —— 派稿须写明「证据原文**原样落盘**」，并给出**取原文的口径**（如「按 ACP 936 解码」）。⚠️ 工具输出被"顺手润色"（本地化文字改英文）会让整条证据链**失去可采信性**，且**看不出错**（结论可能仍对）。
    ⚠️ **但"原样（含编码）"这条要求本身有不可达边界，别把它写成判据** ★（2026-09-20 实测）：
    被派方的工具链可能**自带编码／语言前导码**（实测 DSH 的 pwsh 工具带 `ENCODING_PREAMBLE`，其输出**本来就**
    倾向英文 ＋ UTF-8）⇒ 「要求中文原样落盘」在该通道上**不可能满足**，写进判据 = 造一条必然为红的假判据。
    更进一步：**语言 / 编码形态不得用作"是否被后处理过"的判据**（本机实测：同一条 `powershell.exe`
    **会稳定落在英文态**，与伪造无关；曾据此误判对方的英文证据为"必为伪造"，已撤回）。
    ⇒ 正确口径 = 「**禁人工改写 / 意译**」＋「工具链自身的语言与编码差异**原样保留**」＋「**注明取自哪条通道**」；
    凡与语言 / 编码有关的观察，结论**只写在实测过的那条通道上**（与铁律 6、15 同源）。

17. **判"应红 ／ 应绿"必须逐件读源码定期望** —— 同一批同类装置**可能方向相反**（实测：三个哨兵里两个"落红才对"、一个"**落绿才对**"）⇒ 按"组"给口径会把后者**判反**。派稿只可给"每件写清它自己的期望"，不可给"这组应该红"。

18. **「前提重测」常常就是「结论复核」** ★（2026-09-22 实测）—— 派发前逐条实测时，若其中一条覆盖的是**稿子里的环境 / 上游判定**，它可能**直接推翻那条判定**（实测：一条被标「待重测・等级最高」的选型结论，**一条零副作用命令即见翻转**）。
    ⇒ 此时有一件比写派发稿更重要的事：**回填决策稿**。结论要落在**原文档**（派发稿是活日志，会被清），且必须把「**原结论是否仍成立**」与「**新证据够不够下结论**」**显式拆开**（示例：`装配层` 翻转 ≠ `运行时层` 可用 ⇒ **两通道并列留痕**）。
    ⚠️ 别让「待重测」长期停在决策稿里只当备注 —— 它是**派发时的实际输入**。

19. **待派发项自己声明的首个交付物，也要拿去实测** ★（2026-09-29 实测）—— 第 18 条说的是「稿子里的**环境 / 上游判定**」会翻转；**更靠前一层**：**待派发项的首个工作项本身可能不成立**。
    实测：某切片 TODO 首条写「**compaction provider 插件**」（假定要自写插件）；派发前实测发现**官方默认装配里三件已就位**（零副作用命令即见）⇒ **那个交付物根本不需要写**，本块退化为「配置 ＋ 验收 ＋ 采数」。
    ⇒ 后果两个方向、**都要处理**：① **交付量大幅缩水** ⇒ 别让执行人写一个不需要的东西（纯浪费，且会造出一条**产品上不存在**的链路去验收）；② **「接入面已天然就位」必须在稿里明写**，否则执行人会按旧假设先去找「该写什么插件」。
    ⇒ 纪律：**写派发稿的第一步不是抄 TODO，是把 TODO 的首条假设拿去实测**；实测推翻 ⇒ **同批回填 TODO**（一处两面），并在稿里显式留痕「原假设已订正、现口径是什么」。

20. **「配置预览通道」≠「运行时通道」** ★（2026-09-22 实测，第 4 条的反向边界）—— 第 4 条推荐的零副作用验靶手段（`--dump-config` 一类）证明的是**装配层**：某行在不在、有没有被禁、层序对不对。
    ⛔ 它**不证明**该能力运行时可用（实测：某组件在配置树里**默认装配且未禁用**，而**运行时**的原结论恰是「其端点 404、无法独立起 HTTP」）。
    ⇒ 引用时必须**注明取自哪条通道**；两通道分歧**并列留痕、不合并**（同源：铁律 6、15）。

## 拆块与编号

⭐ **本项目非全自动运行**（2026-10-09 老大口径）：派发稿写完后由**老大手动**安排执行方 AI 去跑，**一般情况下均为串行** ⇒ **不必为并发冲突做设计**（“哪块能不能同时跑 / 会不会互撞”不是本项目的派发关切）。
- **拆块的总纲（为什么拆）**：方便**派发 ／ 实现 ／ 测试 ／ 复验 ／ 版本管理** —— 五者任一因“块太大”而变难，就该拆。
- **一个编号 = 一份派发稿**。
- **拆块判据（化繁为简）**：判据 / 交付能**单独验收**、技术形状同质 ⇒ 可拆。拆完**继续往后加子编号**（`3.7` → `3.7.1` / `3.7.2`；`3.2` → `3.2.1`）。
  - （旧版判据写「独立判据 ＋ 独立场地 ＋ 不争同一资源」；第三条只在**确要并行**时才成立 —— 本项目默认串行，**通常不必考虑**，留此备查。）
- **设回报卡点**：前置块先回报，再起跑后续块（“别自行往下做”要明写）。
- ⭐ **颗粒度不够 ⇒ 先回 TODO 就地细分，再派发**（2026-10-09 老大口径）：
  - 派发前若觉块太大 / 含多个应拆分的独立功能 ⇒ **回 TODO 就地拆次级标题**（`3.1` → `3.1.1` → `3.1.1.1`，可一直往下拆），拆完再派。
  - **就地往下拆 = 直接做、不讨论**（只在现有结构上加深度，不扰其他块）。
  - 若要**重整既有阶段划分 / 改结构**（属大动作，需这样做的可能性极低）⇒ **提议并讨论，⛔ 不直接调整**。
- ⭐ **可以一次多派**（2026-10-09 老大口径）：一条功能链（如 **实现 → 测试 → 复验**）可**同时写多份稿**（Trae 实现稿 ＋ Claude 测试稿 …）一次交给老大；但须**显式标注谁先谁后**，并写明“**全链跑完回到 WB 复验**”。
  - 与「一个编号 = 一份派发稿」不冲突：并行的是**不同编号的多份稿**，⛔ 不是把多块塞进同一编号。
- ⭐ **同一靶子不得两路派发** ★（2026-09-15 立为候选，2026-10-09 定稿入本 skill）—— 两个执行方被派**同一个验证对象**（同一项机制是否生效 ／ 同一份证据）⇒ 各出一套**不可互推**的结论，只能对账（实例：Trae 与 Claude 的"最小反证集 #1"同为 `permission-presets` 自定义表生效 ⇒ 已合并成一次派发）。处置二选一：
  - **合并成一次派发**（默认；合并理由与"哪件动哪棵树"须留痕，见铁律 13）；
  - **显式约定为「有意独立交叉验证」** ⇒ 须按「多方独立调研」节的纪律走（同规则 ／ 异通道 ／ **提交前互不翻看**）；⛔ 无意的重复派发**不产生**交叉印证，只产生对账成本。
  ⚠️ 边界：**「同一靶子」≠「同一主题」** —— 同主题下**不同靶子**（如 A 验写入面、B 验召回面）分派属正常拆块，不适用本条。
- 顺延 / 提前都要**留痕**（编号在前 ≠ 先做，除非用户定调）。

## 一处两面（派发必同步）

- 待办文件（「**怎么做**」：任务 / 进度 / 派发状态）↔ 决策稿（「**做什么**」：判据 / 验收基准 / 既定前提）。
  **改一面必改另一面，两面不一致即为缺陷。**
- 派发后要更新的最少三处：① 该切片段落的**派发状态**（含场地、拆块去向）；② 中央**派发进度**清单；③ 若前提被改判（如"已定前提"降为"待实测"），**旧结论要标注已被推翻 / 已解除**，别留两套说法。
- ⚠️ 同步时别把结论**寄居在交流区**（`log-*` 是临时会话空间）—— 要引用就指向稳定落点，或就地自足。
- ⚠️ **「转 X 一并判定」必须回填 X 的承接清单** ★（2026-09-20 实测缺口）：
  在 A 段写「某未闭合项**转 X 块一并判定**」时，**X 段必须同期把这一项列进自己的承接清单** ——
  否则**派发时读的是 X 段**，那一项就**根本不会被派出去**（它会一路"存在"在 A 段里，看起来没丢）。
  实测：A 段写了"装置脆弱性**转 3.7.4 一并判定**"，而 3.7.4 段「未闭合」只列了第 ① 项 ⇒ 第 ② 项在派发前一刻才被 WB 补齐。
  ⇒ **承接清单是派发时的实际输入，不是备忘**；跨段"转"是**双向义务**（A 段写转出、X 段写承接）。

## 多方独立调研（同规则网）

同一份调研派给 N 个 AI **各自独立**做，用于对抗单通道盲区。要点（2026-09-23 实测，DSH-3.4 参考件调研）：

- **规则要落稳定落点**（`docs/` 之类），⛔ 不能只写在 `exchange/` —— N 份报告都会引用它，而交流区不承诺保留 ⇒ 清理后全是断链。
- **独立纪律是核心，必须写进每份派发稿**：「**提交自己的报告前 ⛔ 不得翻阅其他方交流区**」。
  本机制的价值在「**同规则、异通道、互不影响**」的交叉对照；一旦互看，就退化成 1 份报告 ＋ N 份抄写。
- **统一报告格式 ＋ 统一字段表**，否则 N 份无法合并。字段务必含「**它怎么验的**」（对方如何验证该设计）与「**证据等级**」。
- **共同基线 ＋ 自选区**：共扫区 N 方都过一遍（**保证可对账**），自选区各自外扩（**保证广度**）。可给「建议侧重」，但须写明**非强制、不构成分工**，且**不要求执行方猜别人扫了什么**。
- **反纪律必备**：找不到写「无」（不编）／ 热度不构成理由 ／ 不采信二手转述 ／ 版本脱节须**显式暴露** ／ **必须注明检索通道 ＋ 时间**（通道不同结论不可互推）。
- **入口写到可复制**：本地给到文件级；上游主仓给 `git show <tag>:<path>`（裸仓库不必 checkout）；社区给 `owner/repo`。
  ⚠️ **只写短名会撞同名异物** —— 实测同时存在 `giter00/dsh-headroom`（插件）与 `wjxn13/dsh-headroom`（另一形态的代理），检索二者都会命中。
- **要求各方对规则里的入口「至少实测一条可达」并报出不可达者** —— 规则本身可能藏着假前提，这是最便宜的验靶。
- ⚠️ **汇总方自己也要出一份**，但**独立性最脆弱的是它**（它天然最先动）。若它先出报告，只能靠「提交前不互看」的纪律兜 —— 更稳的做法是**让它最后出**，或至少**不与其他方的独立期重叠公开**。
- **判据（归档时用）**：N 份报告里凡**只有一方提到**的候选，标为「单通道待复核」；**多方独立撞到同一件**才升级为交叉印证。

- ⭐ **规格稿只放规则，结论一律不进共用文件**（2026-09-23 实测补救）：把某方结论写进 N 方共用的规格稿，**会污染其余 N−1 方的独立性** —— 且它们是**被要求**读规格稿的 ⇒ 污染发生在**合法路径上**，不算违规互看。⇒ **每方结论只落自己的交流区**；规格稿里只留「报告落点 = 各自交流区」＋ 汇总指针。若已写入 ⇒ **摘干净 ＋ 同时修掉所有指向它的指针**（否则留断链），并**说明补救时点与已暴露面**。同理：**汇总区也别设进规格稿**。
- ⭐ **执行方分轮次时，轮次必须显式标注通道**：若某方的检索通道中途恢复（如代理从"未开"变"已开"），让它**补做一轮**，并要求**报告里把两轮分开写**（轮 1 通道 ／ 轮 2 通道）—— 依「通道不同则结论不可互推」，**两轮结论不得合并成一条**。实测：补救轮常是**最高产**的一轮（本轮 6 件社区件从 🟡 升 🟢、并翻出 2 处对上一轮的实质修正）。
- ⚠️ **对他方交付物取「当下状态」当一版看待**（2026-09-23 老大口径）：派发后各方常**自行补做多轮**（如通道中途恢复、被要求补宽度）⇒ 汇总方**不做版本考古、不区分轮次**，读到什么算什么。**与上一条不冲突** —— 上一条约束的是**自己**的两轮（通道不同，结论不可互推），本条是他方的交付物（汇总方只关心最终态）。
- ⭐ **融合轮（第二阶段：吸收方法）** —— 独立轮收齐后，再派一轮「**只吸收方法、不搬结论**」（2026-09-28 实测，单方产出 ≈1.4 万字）。要点：
  ① 授权话术须**逐字写明**「吸收他们的**方法、路径**，**并非**简单吸取整合**结论**」—— 不写死，执行方会直接抄结论，交叉对照价值归零。
  ② 产出固定三段：**吸收清单（方法 → 我的动作）／ 据此实做（可复算）／ 对我报告的调整清单**；并**显式写「⛔ 不吸收他方的候选结论与分档」**。
  ③ **订正不重写历史行**，集中登记调整清单 ⇒ 供汇总取**当下状态**。
  ④ 实做项**必须可复算**（给命令／脚本路径 ＋ 通道四元组），否则与"只是读过"无从区分。
  ⑤ 预期产出**通道间不一致**（实测：同一 semver 串两方结果相反）⇒ **摆矛盾、不裁决**；给**可自查的姿势分解**比给结论更有用。
  ⑥ ⚠️ **未做融合轮的一方，结论停在独立轮时点** ⇒ 时间窗会造出"过期结论"（实测：某件 peer floor **5 天内从 `0.1.5-rc.2` 抬到 `0.1.7-rc.1`**，两方结论各自在其时点都正确）⇒ 汇总**必须同时记结论与其时点**。

**收口（汇总）八要点**（2026-09-28 实测，DSH-3.4-R 四方收口）：

- ⭐ **收口＝一次「性质转换」，须先判时机**：规格稿的中立需求**只在各方独立作业期间成立**。⇒ 全部交付（含融合轮）之后，**该窗口关闭**，规格稿可由「操作规格」转为「**调研成果稿**」，结论写进去不再算污染。⚠️ 但须**抬头显式声明性质变化**，并**保留原规则节不改**（作留痕）—— 直接改写旧规则会让后人对"当初派了什么"无从复核。
- ⚠️ **污染披露必须放在汇总最前面，且要量化它**：若规格稿曾内嵌汇总方结论（哪怕事后已摘除），**暴露期内的读者就是被污染方** —— 实测：两方在报告里**主动写明"已读到它"**。⇒ 披露后**下调交叉印证等级**：**与汇总方结论重合的项只能记 1 条通道**。
- ⭐ **交叉印证分两级，别把「同源」当「互证」**：① **跨通道实做互证**（不同人各跑一遍、值相同）⇒ 硬；② **判断汇合**（依据同源、结论相同）⇒ 弱，**不构成互证**。⚠️ **凡出自同一份上游／同一份名录的条目，天然属 ②** —— 汇总时若把它们并成"多方佐证"，就是**造证据**。
- **各方「通道对照」是汇总的核心产出之一**：逐方写清**它那条通道拿到了别人拿不到什么**（实测：一方在**联网不可用**的阶段被迫本地深挖 ⇒ 反而产出全场最有价值的官方判据表；**同一方通道恢复后又补了 5 件社区件** ⇒ ⛔ 别把"通道受限"当终身属性，也**别据此给该方打折**）⇒ ⛔ **别把"谁扫得多"当排名**，通道不同则产出类型不同。
- **分歧点单列，摆矛盾不裁决**：实测四组分歧里**两组是时间窗**（同一件在 5 天内变了）、**一组是姿势差异**（同串 semver 结果相反）⇒ 汇总给的是**可自查的姿势分解 ＋ 时点**，不是胜负判定。
- **按口径降档的项要显式降档**：老大若已把某项判为"观察、不深追"（如版本锚定），汇总里就**保留数据、去掉选型指令**（"建议不要计入可用池"这类话必须删），并注明**降档依据**。
- **收口物要同步多处（一处两面的推广）**：成果稿 §N ＋ 登记表对应行（**状态列从"调研中"改"已收口"＋ 填汇总指针**）＋ `TODO.md` 对应行（**`[ ]`→`[x]` 且写明汇总落点**）。⚠️ 改 TODO 标记后**跑一次标记不变量检查**（"✅ 段内不得含 `[ ]`"）。
- ⭐⭐ **汇总方必须「连续通读」被汇总的全文，不得跳读分段**（2026-09-28 实测，代价真金白银：首版汇总漏掉两大段）：⚠️ **跳读会把「没读到」伪装成「没有」** —— 汇总方看不见自己的盲区，成果稿照样显得"完整"。实测形态：读某方报告时按「报告主体 ＋ 融合轮段」两段读，**跳掉了中间的「补充调研」段**，而那段恰含「**3 处订正 ＋ 3 处升级**」；另一方的「**补遗**」段同样被跳掉。⇒ 规则：① 汇总前先列出每份报告的**章节清单**（`grep -n "^#"`），**逐段确认已读**，别按"看起来读完了"行事；② ⚠️ **最危险的段是「补段」** —— 它们是后加的，**常写在段尾且自带汇编指令**（实测原文：「**本节对原报告有 3 处订正 ＋ 3 处升级，请以本节为准**」／「请汇总时看到」）⇒ **段尾必看**；③ 漏读被补救后**必须在成果稿里如实披露**（写入"诚实边界"），并给出教训 —— 否则下一个汇总方会重犯。
## 校验（提交前跑一遍）

- 行尾：**已由仓库 `.gitattributes` 统一为 LF**（`* text=auto eol=lf`，2026-10-08）⇒ 行尾由基建层保证，**无需再人工核对 / 维护**。
- **收尾检查**：`git status` 若仍报 `M` 而 `git diff --numstat` 为空、且 worktree 字节 == `HEAD:<file>` 字节 ⇒ 是 **stat 缓存陈旧**，`git add` 一次即消；⚠️ 别据此判「还没提交完」。
- 标记不变量：如"✅ 段内不得含 `[ ]`"，**程序化检查别靠肉眼**。
- 待提交 diff 扫 `Bearer` / `password` / `secret`。
- 提交前**重新确认磁盘状态**（多方会实时改文件，快照会过期）。
