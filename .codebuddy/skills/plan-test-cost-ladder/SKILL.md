# 花钱测试前的量级阶梯

**适用**：一个测试的花费 ∝ 某个「规模」参数（context 容量、并发数、数据量、轮数）时，**开跑前**先把它算清楚。
**不适用**：零成本的只读探针（走 `remote-probe-dryrun`）；回报后的验收（走 `verify-ai-delivery`）；**判据本身怎么写**（走 `design-verifiable-criteria`）。

**一句话目标**：把「花 N 倍钱能多测出什么」写成阶梯，并**明确划出不做的那档**。用户要的往往不是"最小花费"，而是**「最佳量」+「每档的边际收益」**。

## 何时用

- 用户问「这个测试要多少 token／多少钱」「给我个最佳量」「分档能测出什么」。
- 你要跑一个**会真实计费／占资源**的实验（LLM 调用、长时间压测、真机判定）。
- 判据里写了「开跑前先给 token／费用上限」——**上限不是拍脑袋给的，是算出来的**。

## 七步

1. **钉触发常量（读源码，不读文档）** —— 把"什么时候才会触发"写成一行可复算的式子。
   找：阈值默认值、判据是 `ratio × 容量` 还是绝对值、单位是什么。
   ⚠️ **文档会脱节**：实测踩过官方 design note 写死一个容量常量、而代码常量**大 4 倍**（note 定稿在前）⇒ **以代码为准**，并把脱节本身记成一条发现。
2. **找「规模」从哪来** —— 它是硬编码常量，还是**配置面**？后者就是省钱杠杆。
   ⭐ **容量类参数常可改小**：把 `容量 × 阈值比` 的容量调小，阈值**线性下降**，成本同比例下降（实测：100 万 → 2 万，阈值 80 万 → 1.6 万，**降 50×**）。
   ⚠️ 代价：这是**容量被改写的夹具** ⇒ 结论只能写「机制成立（容量 X 下）」，**不得外推成「默认容量下亦然」**。
3. **核估算器的精度**（若成本由"估算值触发、真实值计费"决定）——
   触发看的是**估算**，账单看的是**真实 token**，两者偏差直接变成钱。
   ⭐ 结论常是「**填空用 ASCII／纯数字，别用 CJK**」：固定「N 字符 ≈ 1 token」这类启发式对 CJK 与 JSON **系统性低估**（且按 UTF-16 code unit 计长）⇒ 达到同一"估算触发线"，CJK 的真实 token 远高于 ASCII。**方向可由源码＋文档钉死，倍率必须用一次真调用的 usage 实测校准**，不要凭记忆填数。
4. **找前置状态**（触发需要几次调用／几个 turn／先有什么历史）——
   这是最容易漏的一步。实测踩过：某触发依赖"上一条已完成的路由请求头"，**首轮永远不触发** ⇒ 最少要 2 个 turn ⇒ **预算 ≈ 3 × 阈值**（主请求 ×2 ＋ 摘要输入 ×1），凭空多一倍。
5. **找零成本反向对照** ——
   ⭐ 最便宜的真判据往往不是"看它生效"，而是**"故意配坏，看它按预期报错"**（非法参数组合、未知键、非空闲态调用）。
   0 token 就能证明「配置真的被这个引擎读进去了」——比任何"跑起来看着对"都硬。
6. **排档（每档四列：怎么造／量级／能测出／测不出）** ——
   ⚠️ **「测不出什么」这一列不能空**。缺了它，读者会把某一档的结论外推到整条链。
   典型分层：零调用（配置面）→ 极小（人工强制触发路径）→ 小规模（自动触发路径 + 阈值边界）→ 中规模（多段／收敛／失败路径）→ 真锚（默认规模）→ 极端路径（只由外部真实错误才能触发的那类）。
7. **给建议预算 + 划不做档** ——
   输出三件：① 推荐主线（哪几档）② 建议上限（**含重跑与边界双跑的 3~6 倍余量**）③ **哪档不做，以及为什么不做**（典型理由：机制里唯一的容量依赖只是一处纯算术，已读源码 ⇒ 不必花 N 倍钱去"证"；或该档需外部真实错误，构造不出来）。

## 输出形态

```
① 触发常量从哪来（一行算式 + 源码 文件:行号）
② 省钱杠杆（每条：怎么改 / 省多少 / 代价与诚实边界）
③ 阶梯表（档 | 怎么造 | 量级 | 能测出 | 测不出）
④ 不做档及理由
⑤ 不必实测就能算出的成本方向（前置状态 / 谁跟谁同阶 / 哪些是"免费"的）
⑥ 建议预算（主线 + 上限 + 余量倍数）
```

## 铁律

1. **触发常量只认源码**（`文件:行号`）。文档、note、README 都可能过期；**脱节本身要作为发现写出来**。
2. **"能改小容量"一定要写成杠杆**，同时**必须写明它是夹具**（结论不可外推到默认容量）。
3. **估算法要区分「触发用估算」与「计费用真实」**，并给出校准方法（跑一次读 `usage`）。
4. **每档必须写「测不出什么」**；**边界双跑**（阈值 −1 不触发 ／ 阈值 +0 触发）是把"真按式子算"钉死的硬证据。
5. **先找零成本反向对照**（配坏 → 应报错），再考虑花钱。
6. **预算 = 量级 × 3~6**，并把"为什么不跑最贵那档"写成一句可复核的理由。
7. **一次性成本判据优先**：优先找**已落盘的事件／日志里自带用量或标记**（如事件 payload 里的 `usage`、checkpoint 标记）⇒ 成本与效果都可事后核，不必额外埋探针。

## 常见坑

- **把"估算压力"当成"真实账单"**：两者在 CJK / JSON 场景下能差数倍 ⇒ 预算按真实 token 算，填充按估算线设计。
- **漏掉前置状态**：多一个 turn 就多一整份上下文输入 ⇒ 预算直接翻倍。
- **只排"能测出"，不排"测不出"**：读者会把小规模结论外推到默认规模。
- **忘了固定开销也算规模**：系统提示、工具 schema（常被 `JSON.stringify(...)/4` 计入）本身占一截 ⇒ 实际填充需求 = 阈值 − 固定开销；工具多时这部分是**免费填充**。
- **在"只读探针"和"真跑"之间没有中间档**：忘了**人工强制触发路径**（往往有一条 bypass 阈值的人工入口）是**最便宜的机制验证档**——但它的保留／收缩语义常与自动路径**不同**，必须分别写判据（实测：人工路径硬编码"保留 0"⇒ 只留最后 1 条，与自动路径的"保留尾部 16%"是两回事，用人工路径验「近文保留」会误判成立）。
