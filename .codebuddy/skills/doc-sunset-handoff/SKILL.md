# 文档清退与承接

> ⚠️ **分工变更后的用法（2026-10-13 老大裁定）**：清退范围按归属拆开 —— **`exchange/log-*`（含派发稿 ／ 回报段）归 WB**；**讨论稿 ／ `docs/` ／ `archive/` 归 Qoder**。跨界清退（如 log 引了讨论稿、或讨论稿引了 log）**须双方同步后动手**，⛔ 不单方越界；`exchange/README.md` 亦归 Qoder，WB 不碰。

把「过程性文档」按 **结论 → `docs/` / 待办 → `TODO`** 分流，然后删除；同时保证 **不丢证据、不断引用、不越权**。

## 何时用

- 「清理 XX 交流区」「把 log-X.md 清一下」
- 「XX 讨论稿收口」「这段已经闭环了删掉」
- 派发稿与回报已完成使命、要腾位置

## 铁律

1. **删前必核 git 留底**
   跑 `git diff --numstat -- <file>` ＋ `git log --oneline -- <file>`。
   ⚠️ **「文件在仓库里」≠「我要删的那段也在里面」** —— 他人正在写的文件常只存在于工作区（HEAD 版可能是几天前的）。直接清 = 永久丢证据。
   ⇒ 发现未提交：**先单独提交一次留档**（提交信息写清"纯留档、未改内容"），再做清理。
   ⛔ **不另存物理备份**（`*.bak.md` / 复制到 `D:\Temp` 之类）—— **git 即留底**，回溯一律走 `git log -p -- <file>`。老大 2026-10-13 定：清交流区 log 的这类备份必要性低、纯冗余。

2. **逐条核承接，不凭印象**
   每段问两句：「这段的**结论**进 docs 了吗？**待办**进 TODO 了吗？」—— 必须 **grep 目标文件实证**，不能凭印象说"应该有了"（印象经常错，尤其"我说过要落"≠"真落了"）。
   ⚠️ **被清理物「自述已迁出」也是印象，不是证据** —— 实测 2026-09-17：`log-workbuddy.md` 一段自己写着"已迁 `TODO.md`，本处仅留索引"，我据此放过多轮；真去逐条 grep，才发现那条的 4 个子项散落在 `TODO:251/253/254/260`。⇒ **凡承接，必回源核，不采信被清理物的自述。**
   - 结论型（实测事实、判据、机制）→ `docs/` 对应专题
   - 待办型（未做的事、待验证项）→ `TODO.md` 对应任务条目
   - **建议型（"要不要改"）→ 不自行处置**，留在原处待裁（替用户拍定性决策 = 越权）

3. **先落盘，再删除** —— 顺序不可颠倒。

4. **引用完整性**（最容易漏，见下节）。

5. **产物台账要随其生命周期回流** ★（2026-09-17 新增）
   凡我在文档里写下的「**某产物 / 路径 / 备份存在于某处**」这类**操作性陈述**，当该产物被后续操作改变
   （**被真删 / 移动 / 改名**）时，**必须在同一批把陈述改掉**。
   ⚠️ 实测：我做了「重命名备份」这个**动作**并在三处写"备份在 `<xxx>.RETIRED-<ts>`"，用户随后**真删**了它们
   —— 而**我没回头改陈述**，于是留下三处"按图索骥会扑空"的失活路径（由第三方复核才发现）。
   ⇒ 两条硬做法：① **收尾时主动交回"我留下的产物清单"**（路径 ＋ 用途 ＋ 可否删），让删的人回报；
   ② 他人回报删除后，**grep 自己的历史陈述去改**（改法：保留名字供追溯 ＋ 明写"**磁盘上已不存在**"）。
   ⇒ 一般化：**「我做了 A」之后「别人对 A 做了 B」时，A 相关的所有陈述都进入待更新集**。

## ⭐ 判据：什么算「必须清」——段落引用 vs 行动指南

判定之根（2026-09-17 老大给出）：**`log-*` 是 AI 之间的临时会话空间，不做任何长期保留** ⇒ 引用它 = 借一个**会消失的地址**。由"存续要求不同"分出两类：

| 形态 | 例 | 判 |
|---|---|---|
| **段落引用**（把 log 里某具体章节当**长期证据**用） | 「来源 = `log_design.md` 设计精化定案 §3–§7 ＋ `log-marvis.md` 产品方向 §0–§5」 | 🔴 **必清** |
| **行动指南**（"什么什么情况下去读什么文件"，**当下**用） | 「每个 Vue 组件开发前先读 `exchange/log-trae.md`（任务简报）」 | ⚪ 不算引用 |
| **讨论稿指针** | 指向 `exchange/deployment-architecture.md` 等待定稿的稿子 | 🟡 缓 —— 稿子定稿搬入 `docs/` 时统一改 |

⭐ **补充限定**：**行动指南只允许指向稳定落点**（`docs/` / `archive/` / `TODO.md`）。指向 `log-*` 的"行动指南"照样会失活 —— 实测 `backend/tests/test_integration_llm.py:48`「排查记录见 `exchange/log-claude.md`」正是行动指南句式，而 `log-claude.md` 已整体轮换 ⇒ 照样指空。

## ⭐ 引用完整性

删除会打断引用；**插入内容同样会让其后所有行号引用偏移**；且**跨文件引用不会在编辑时报错**。

- 全仓扫：`` `:\d{1,4}` ``（行号引用）＋ 被删文件名 / 被删段名
- 逐条核对**实际行号**是否仍指对内容（用脚本打印该行内容比对，别肉眼猜）
- 修法优先**改成段名 / 锚点**（行号引用本身是脆弱引用）
- 做插入时先数**插入了几行** ⇒ 其后引用整体后移几行，一次改齐
- 指向被删段的外部引用 → 改成「已清理 ＋ `git show <留档 commit>:<file>`」的形式（保留可追溯性）
- **扫描面必须含非文档文件**（`.ts` / `.py` / `.sh` 的注释与测试里同样会写 `exchange/log-*.md` 指针）—— 实测 2026-09-17：`harness/tests/global-setup.ts` 两处、`backend/tests/test_integration_llm.py` 一处，**三处全已失活**。原出处已消失时，注释只能**就地自足化**（把语义 ＋ 裁决日期 ＋ 现存权威出处写进注释本体），不再留指针。
- **锁定件（归档报告 / 历史快照）里的失效指针**：那类区的「不就地更新 / 一般不修改」是为防篡改**叙述**，不是防修正**已失效的引用** ⇒ 改法 = **保留原意 ＋ 注明失效**（如「原载交流区 `log-x.md`；**该稿已随交流区清理，不可再查**」），**绝不改动叙述本身**；并在交付说明里留判断留痕供复议。（2026-09-17 实测：archive 两文件 5 处）

### ⭐⭐「文件还在、内容被轮换」= 静默失活（比断链更阴）

**断链至少能看出来**；而**活日志被内容轮换后，指向它的段落引用看起来完好**（文件在、文件名对、格式正常），**实际指空**，且**无人会察觉**。

- 实测 2026-09-17：`log-claude.md` 仍在（325 行），但内容已整体换成 DSH 主题 ⇒ 指向它的「防挂死安全网」节 / 排查记录**全 0 命中**（两通道复核：Python 扫 ＋ Grep 工具）。`log_design.md` / `log-marvis.md` 同类风险。
- ⇒ **核引用不能只核"文件在不在"，要核"指向的那段内容当下还在不在"。**
- ⇒ **判「内容不存在」前先自证判据**：拿 `§0/§3/§7` 这类**编号字面**去 grep，而原文用的是 `### 3.` / `#### Logo 设计定案` 形式 ⇒ **编号差异会伪装成缺失**（据此误报过一次"已失活"，回读原文才发现内容都在）。**判据测的若是形式，就会漏内容。**

### ⭐ 反向用法：引用存在 ⇒ 该物件「不可删，只可归档」

清理时若发现**目标文件被某文档登记为资产 / 复现件 / 器材**（不只是"被提到"，而是被登记），则**删除动作本身会同时制造断链 ＋ 资产损失** ⇒ 正确处置是**归档而非删除**：

- 实例（2026-09-16）：CVM 上 `~/dshprobe/landlock-test.mjs` 等三个探针，`docs/production-env.md` §10 明确登记为「复现资产」、且该节自己写着「该机有期限 → 应回传本地」⇒ 用户那句「用不上就清理了吧」若照字面删，会**断掉文档引用 ＋ 丢掉唯一副本**。做法 = **回传入仓 ＋ 清机器 ＋ 同步引用**。
- ⇒ **删前先问**：这个物件在别处被「登记」过吗？（grep 文件名 / 路径，而非只 grep 语义）
- ⇒ 「删」与「归档」是两种动作；**用户给「清理」的授权 ≠ 给了「删除资产」的授权** —— 拿不准先归档：归档可逆，删不可逆。

### ⭐ 反向过检：仓库内「零承接」≠ 可删 ★（2026-09-20 新增）

上一条说的是「**被登记 / 被引用** ⇒ 不可删」。**反方向同样有坑，而且更隐蔽**：一段内容在仓库内
**零引用、零承接**（既没进 `docs/`，也没进 `TODO.md`），看着最像"没人要的东西"，
但它可能是**某件事的唯一证据**（外部调研、一次性实测的原始观察、别处从未落盘的结论）。
⇒ 删它 = **没人报错、没人察觉的永久丢失** —— 断链至少会露，这个不会露。

- 实测（2026-09-20）：`exchange/log-qoder.md` 三段社区调研（外部社区对 DSH 的评估），
  全仓 grep **零承接**，且**删了再没有第二份**。
  ⇒ 处置 = **不删 ＋ 上报归属**：「此段无任何承接，删则永失，请定去留」。
- ⇒ 纪律：**用户给的「清理」授权 ≠ 替他承担"丢证据"后果的授权**（与上一条同源：清理 ≠ 删资产）。
  另见「建议型 → 不自行处置」（铁律 2）。
- ⇒ 判「零承接」要**两通道核**（grep 内容关键词 ＋ grep 段名 / 编号），并防上一条那个坑：
  **编号 / 措辞差异会伪装成缺失**。

## 流程

0. **先定「谁来动手」** —— 读各区 `README.md` 的规则，建权限矩阵（实测 2026-09-17）：
   - `exchange/log-*`：**各自区域只有本人能修改**，他方只能「新增内容派发任务」（WB 有权在本区各 log 派发任务或按需修改）；**`docs/` ／ `archive/` ／ 交流区讨论稿 ／ `exchange/README.md`：Qoder 维护**（2026-10-13 老大裁定）⇒ WB **不亲自改**，只暴露 ＋ 备好精确改法；`TODO.md`：**WB 维护**（复验后只改标记，归档交 Qoder）；根 `README.md`：**Qoder**（归属已由 `docs/ai-governance.md` §3〈文件归属表〉定案，该表为唯一权威落点）。
   - ⚠️ **旧矩阵已废**：此前的「`docs/` AI 不动 ／ `archive/` WB 维护」是 2026-10-13 之前的归属，⛔ 不得再照其行事。
   - ⇒ **权限不在自己手里的：只暴露 ＋ 备好精确改法**（改哪一行 / 原文 → 改成什么），不擅自改。
1. `git status` ＋ `git diff --numstat` 看工作区状态（识别哪些改动是别人的）
2. **通读全文** —— 不看片段（片段会漏掉"这句还挂着未办的事"）
3. 逐段分类：已闭环 / 活稿 × 结论型 / 待办型 / 建议型
4. 核 git 留底（铁律 1）；未留底先提交
5. 落盘未承接项（铁律 2、3）
6. 修引用完整性（含代码注释；含"内容已轮换"的静默失活）
7. 删除或压缩（活稿 **压缩保留"未结项"**，别把未决内容一起删掉）
8. 复检

## 复检清单

- **行尾**：**已由仓库 `.gitattributes` 统一为 LF**（`* text=auto eol=lf`，2026-10-08）⇒ 行尾由基建层保证，**无需再人工核对 / 维护**。
- [ ] 加粗奇偶：每行加粗标记成对（⛔ 判前先剔除反引号内的星号字面量，否则说明本条规则的行自己就会被误报）
- [ ] 标记不变量：`✅` 小节内不得含 `[ ]`（**程序化检查**，别肉眼）
- [ ] 待提交 diff 扫 `Bearer` / `password` / `secret` / `sk-` —— 命中逐条判性质（**删除行内**的普通用词无害）
- [ ] `git diff --numstat` 与预期改动量一致（不一致就查：可能他人同时在改）
- [ ] **段落级引用逐条核「指向的内容当下是否还在」**（文件在 ≠ 内容在；编号/措辞差异会伪装成缺失）
- [ ] **状态面板同步**：项目若有 TODO 之类的状态面板，删改后同步
- [ ] **多 log 场景：交叉核对各文件对「同一块」的状态记载是否一致** —— 实测（2026-09-22）同一个 `DSH-3.7.4-T·P`：一处写「🚀 已派发 · **待起跑**」、另一处写「✅ **已复核（早一天）**」⇒ **状态相反**。清理是顺手对齐的时机

## 常见坑

- `head` / `grep` / `ls` / `mkdir` 的 PATH shim 会**间歇失效** ⇒ 一律走 Python（`io` / `os` / `subprocess`）
- **同一文件的多个 Edit 不得并行** —— 并行 = 各自 read-modify-write 同一快照，**后来者静默覆盖先到者**，而每个调用都回 "Successfully edited"，只在 diff 里才暴露。**要大改直接一次 Write 全量重写。**
- 含**反引号**的文本别塞进 `python -c "..."`（会被 shell 当命令替换、静默吞掉）⇒ 写成 `.py` 再跑，或用 Write/Edit 工具
- 提交时**只提自己的改动** —— 工作区里他人正在写的文件（M 状态且非本次所改）不纳入
- 压缩活稿时保留**未结项**（未裁决建议、未派发任务），并注明原稿可追溯方式
- **清点残留别只用关键词 grep** —— 关键词覆盖面由你的假设决定，**漏了就是漏了（且不报错）**。做法：列**全量目录**逐项判定；grep 只用于"批量比对是否与仓库版同源 / 是否被文档登记"。（实测 2026-09-16：第一轮 grep `dsh|probe|larry|harness|acp|claude|trae` 漏掉 7 个 `cvm-*.sh` ＋ 5 个 `.db`，改列全量目录才发现）
- **heredoc（`<<'PYEOF'`）会吃掉转义反斜杠** —— `os.path.join(...).replace('\\','/')` 报 `SyntaxError: unterminated string literal`。⇒ 凡脚本含**反斜杠 ／ 正则**，**写成 `.py` 文件再跑**（2026-09-22 又实测踩一次）。

## ⭐ 多 log 联合清理（2026-09-22 实战：一次清 4 个 log）

「清理 XX 交流区」通常是一批文件一起清（每个 AI 一个 log，共享一个区）。除单文件纪律外，多一层要点：

1. **授权先读两处**：① 各 log **自己的头部**（多数写着「本区为**活日志**：已闭环、已升格的段**直接删除**」——
   这就是清理力度）；② 区 `README.md`（常写着「**WB 有权**在本区各 log 文件中派发任务，或根据需要修改内容」＋
   「老大可以直接（或要求 WB）对本区文件进行干涉」）。**两处合起来才是逐文件清理的授权依据**，比通用推断可靠。
2. **保留"活层"**：状态区（在飞任务）／未结项／待裁／待讨论提案／通用纪律／头部说明 —— 这些**不是**"已闭环"，一律留。
3. **未裁的"建议型"不成批删** —— 报告类内容（如巡检 ／ 专题稿）里混着**未裁建议**时，
   做法 = 把未裁项**提炼成一个简短的「⏳ 未结项（待老大裁）」节**留在原文件，删掉已消费的分析叙述。
   既清了地方，又不替老大拍定性决策（与铁律 2「建议型不自行处置」一致）。
4. **清理记录形制**：各文件末尾留一节 `## 🗂 已清理段落（按交流区规矩）` ＋ 一句话
   「删了什么 ／ 权威落点在哪 ／ 回溯法 `git log -p -- <file>`」。好处：后人知道"这文件为什么只剩状态区"，
   且**不需要写 commit hash**（避免"先提交拿 hash 再改引用"的两次提交）。
5. **哪类文件不该清**：头部自述保留「设计过程记录」「产品方向源与未决提案」的 log（如 `log_design.md` /
   `log-marvis.md`）—— 它们本身**不是"已闭环的派发稿＋回报"**，清了等于毁掉其声明的职能。⇒ 判「该不该清」
   先看**它的头部声明自己是什么**。
6. **提交判据只看 `--cached numstat`**：只看 `git diff --cached --numstat` **有无全文件噪声**（正常 = 只有真实改动的行数）。
7. **实测收益**（供预期校准）：一轮清 4 个 log ⇒ `log-trae −95%` ／ `log-qoder −91%` ／ `log-workbuddy −90%`。
   外部引用改动量小：一个 `TODO.md` 改 7 处（numstat 7/7）。
