### ⭐ 行尾陷阱（本轮最值得记的一条，我差点自己制造污染）

**现象**：`git add` 两个 log 时 git 警告 `LF will be replaced by CRLF`；我第一次改用 `git -c core.autocrlf=false add` 想"保住 LF"，结果 `git diff --cached --stat` 显示 `docs/local-env.md` **1412 行**、`production-env.md` **1174 行**（我只改了各 2 行）⇒ **全文件被替换**。

**真相**（实测 HEAD vs 工作区）：
```
TODO.md             HEAD:CRLF=0/LF=292 | WORK:CRLF=299/LF=0
docs/local-env.md   HEAD:CRLF=0/LF=706 | WORK:CRLF=706/LF=0
README.md           HEAD:CRLF=0/LF=227 | WORK:CRLF=227/LF=0
exchange/log-trae.md HEAD:CRLF=0/LF=368 | WORK:CRLF=0/LF=33
```
⇒ **本仓库 `core.autocrlf=true`，库里（HEAD）所有文本文件统一是纯 LF**；工作区看到的 CRLF 是**检出时自动转换**的产物。
⇒ 所以「`TODO.md` = CRLF」这条**项目行尾纪律指的是"工作区形态"**，**不是"入库形态"**。
⇒ `git add` 时 autocrlf **正确地把工作区 CRLF 转回 LF 入库** —— 这是**预期行为**，不污染历史。
⇒ ⛔ **`git -c core.autocrlf=false add` 是错的**：它让工作区 CRLF **原样入 index**，与库里 LF 打架 ⇒ 整文件 diff。

**结论（写进纪律）**：
1. **本仓库 `git add` 一律用默认配置**，不要为了"保行尾"去绕 autocrlf —— 绕了才是制造污染。
2. **只有「工作区本来就不是 CRLF」的文件**（如 `exchange/log-*` 一直纯 LF）需要留意，但它们的 LF 是**因为工作区就 LF**，autocrlf=true 对纯 LF 文件**不转换**（无 CR 可转）⇒ **也无需特殊处理**。
3. **判"diff 是否被行尾污染"**：`git diff --cached --stat` 若行数与实际改动量严重不符（如改 2 行显示 1412 行），**先怀疑行尾**，用 `git show HEAD:<f>` vs 工作区逐字节对 `CRLF/LF` 计数即可确诊。
4. **提交前必用 `--stat` 核改动量**，别直接 commit。

**处置**：`git reset` → 分两批 `git add`（默认配置）→ `--stat` 复核回到预期（TODO 9 行／local-env 2 行／production-env 2 行／两 log 大删）→ 提交 `98d0349`。**工作区收尾干净（`git status` 空）**。
