## ⚠️ 工具层教训：同一文件的并行 Edit 会互相覆盖

- **现象**：对**同一个文件**发起多个 `Edit` 调用（同一消息内并行），返回值均报 success，但**只有最后一个落盘**，其余静默丢失。本次实测：README 的三个并行 Edit，仅第 3 个生效；migration 的两个并行 Edit，仅第 2 个生效。
- **成因**：并行 Edit 基于同一基线快照，后写整文件覆盖前写。
- **纪律**：**同一文件的多个 Edit 必须串行**（一次一个，等返回后再下一个）。跨不同文件的 Edit 可并行。
- **验证手段**：改完后**必须 Read 磁盘复验**，不能只信 Edit 的 success 返回。

## T2 触发线待验：官方 web surface 经反向代理对外是否可行（WB 实做，2026-09-11）

- **背景**：TODO「⭐ 通信面定型」段待验项 T2 —— 原设「`--trusted-host` 白名单为唯一已知障碍，未实测反代」。老大问派发，判为 WB 做（产出=架构触发线判定，属架构角色）。
- **机制确认（`dsh web --help`）**：`/api` 上有 **browser-trust fence**；`--trusted-host <authority...>` = fence **额外接受**的 authority（host 或 host:port，可重复）。表面障碍 = Host 校验，非端口/网卡。
- **实测结论（本机，dsh 0.1.2-rc.1，`web` profile 已存在）——反代可行**：
  | 场景 | 结果 | 读法 |
  |---|---|---|
  | root 无 token | **401** | token 门 |
  | 直连 Host=回环 `127.0.0.1:8799` | **404** | fence 放行（路由无此端点）|
  | 直连 Host=`evil.example.com` | **403** | **fence 拦** |
  | 反代·Host 重写为回环 | **401**（≠403）| **fence 放行 → 反代有效** |
  | 反代·Host 原样透传 | **403** | 仅透传无用（对照）|
  | 服务加 `--trusted-host evil.example.com`：直连 Host=evil | **401**（≠403）| **官方口子生效** |
  | 同上 + 反代透传 | **401**（≠403）| 官方口子对反代同样生效 |
- **→ 两条路都通**：① `--trusted-host` 显式放行；② 反代时把 Host 重写为回环（社区普遍做法）。**"唯一已知障碍"实为可绕过的 Host 校验，不是真阻断。**
- **旁证（非实测，采信留边界）**：`ref/tmp_awesome.md.bak` 里已有**数十个**独立第三方反代/网关插件，明确写"Host/Origin rewrite through the loopback trust fence, WebSocket upgrades included"、"no --trusted-host needed" 等 → "可行"与"省事"两头均有社区实作支撑。
- **本轮未覆盖**：WebSocket 升级经反代（只测了 HTTP `/api`）；完整 token→cookie 登录流（cookie 未取到，故 401 vs 404 的路由差异未完全归因）；`--trusted-host` 的**安全性**（未评估）—— 只测了"通不通"，未测"安不安全"。
