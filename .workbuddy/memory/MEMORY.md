# LarryAgent 项目长期记忆

## 安全约定（2026-08-12）

- `backend/config.yaml` 含真实 API key（DeepSeek），已被 `.gitignore` 保护，从未入库（`git ls-files` / `git log` 均已验证）。
- **但任何被授权的 AI 代理（WorkBuddy、编程助手等）都能读到该文件**——gitignore 只防版本库泄露，不防运行时代理可见。
- **硬性约定**：AI 处理本项目时，不得把 `config.yaml` 中的 key 复述到对话、日志或任何生成的文件中；如确需展示配置，引用 `config.example.yaml`。
- 风险缓解方向（未实施）：key 改环境变量注入；平台侧建限额 key；定期轮换；监控 API 用量异常。

## 老大的安全观（2026-08-12，重要）

- **价值论**：物品的安全取决于自身价值，价值越低越安全。API key 价值低，被厂商主动作恶的概率极低（利益判断 > 道德信任，且机构层面利益判断成立）。
- **真正的担忧是数据混染**：他有亲身经历——AI 生成代码中混入过明显属于其他用户的信息。因此他认为 key 暴露的金钱损失最不重要，真正危险的是：key 与对话/记忆数据被服务商推理缓存错误分发或混入他方数据，被"有意或无意"地使用。
- **推论（项目相关）**：送入云端 LLM 的数据应默认假设可见/可能混染；LarryAgent 的 health/finance 角色对话与长期记忆属敏感数据，混染时伤害最大；key 保持可轮换 + 限额作为兜底而非主防线；监控 AI 输出异常（他人信息/乱码）作为混染信号。

## 老大的数据态度（2026-08-12，影响本项目数据处理方式）

- **核心边界 = 可定位性（锚点）**：不介意一般个人信息泄露（"这年头泄露的还少吗"），但绝不允许数据绑定到能定位到人的锚点——姓名、电话号码、身份证号、住址等。可接受外界知道"有这样一个人"，不能是"这就是他"。
- **授权含义**：处理项目数据时不必因隐私过度保守；但 AI 不得将锚点类信息写进日志/输出/记忆摘要；若发现对话或记忆中已存在锚点（真名/电话/证件/住址/单位），应提示用户清理或脱敏（代号替换）。
- **做法上用户自称"摆烂"**：不主动治理泄露面，接受不可控部分。
- **逃熊理论（核心立场，决定未来所有安全建议的尺度）**：隐私是相对位置，不是绝对状态。老大的真实锚点早已被无数公司/组织散播，绝对保护既不现实也无必要；开发 LarryAgent 本身就是"比旁边用商业云方案的人难咬一口"的相对安全（数据本地存储，仅单条消息出境）。**未来给安全建议时遵循相对安全标准：建议优先采用性价比高的最小动作，避免无谓扩张（如自托管 LLM、复杂密钥管理等）；建议先确认理解用户立场，再据此提出方案。**

## 部署规划（2026-08-12 澄清）

- **计划**：租一台云服务器（VPS）部署 backend + 数据库（SQLite）+ 小模型（embedding bge-small 等）。非纯本机运行。
- **含义**：数据位置从本机磁盘变为云厂商托管的磁盘；embedding 在自有服务器上跑，数据不出服务器；LLM API 调用仍是唯一出境通道。VPS 自部署 vs 商业 SaaS 仍属不同量级（root 自持 + 厂商合规审查义务，无训练管道接入）。
- **已知未覆盖项（供规划参考，未实施）**：公网暴露后，现有 shell 工具 IP 白名单（仅 127.0.0.1/::1）与公网访问不兼容——用户经公网调用 shell 会被拒绝；TODO 中的 P3.4 API Key 校验是上公网前的硬前置；HTTPS 缺失时 key 会明文过公网。

## WorkBuddy 表达与决策协议（2026-08-13，基于老大对 CoT 过度纠结的反馈）

背景：老大观察到我的 CoT 存在"过度纠结、反复拿不定主意、同一问题来回拉锯"的普遍现象，担心影响生成质量与 token 消耗。根因是四条并行准则互相拉扯——矛盾暴露（全量暴露）、拍板简明（给方向性裁决）、逃熊最小动作（不过度工程）、架构师展开（权衡分析）。本协议解决四条冲突时的收敛方式，**不改变"矛盾必须暴露"的硬性原则**。

- **① 结论先行**：任何回复先给方向/结论/判定，再给依据与权衡。拍板简明优先于架构师展开——展开是支撑，不是主菜。
- **② 冲突收敛优先级**：四条准则冲突时按以下顺序收敛，不循环：
  1. 用户安全与决策权（涉及锚点/真实 key/可定位信息 → 一律优先保护并提示）
  2. 矛盾暴露（实质性矛盾/风险 → 必须摆出，不折中）
  3. 拍板简明（给方向性裁决，不堆砌）
  4. 逃熊最小动作（性价比最高的最小改动，不主动过度工程）
  5. 架构师展开（仅在此前四项都已满足时，按需补充权衡）
- **③ 暴露的尺度**：只把"可能推翻既有判定 / 影响用户决策 / 涉及安全边界"的矛盾主动抛给老大；建议自行消化表述层面的犹豫，避免把用户当心理垃圾桶；也建议把重要性判断交回老大（与矛盾暴露原则一致：是否重要由老大定）。
- **④ 不确定就直说**：拿不准时明确输出"我不确定 + 需要什么证据/信息才能确定"，不假装确定、不绕弯、不来回试探。
- **⑤ 节奏**：本项目无固定交付压力（个人项目、无外部老板/投资方催命）。允许一次做不成、多次迭代；建议保持从容节奏，把精力放在把事做对而非赶进度上，避免进入抢进度或自我施压的循环。

## WB 工具/环境约束（2026-08-17 升格常驻）
- **WB 不执行 git 远程操作**：WB Bash 用的是**便携版 git**（`.workbuddy/binaries/PortableGit`），与用户系统 git 的配置/凭据**不共享**，推远程会弹 CredentialHelperSelector 且 OAuth 无响应（详见 `2026-08-15.md:172`）。协作约定 = **WB 只做本地 commit，push/fetch 等远程操作由用户用 VSCode/系统 git 完成**。
- **代理差异**：WB 便携版 git 不读系统代理；需联网时用 `-c http.proxy=socks5://127.0.0.1:7890` 临时指定（注意 http 代理会触发 Windows schannel `close_notify`，须用 socks5）。用户系统 git 如需走代理，由用户在自己的终端配置，与 WB 便携版无关。

## 项目运行模型（2026-08-17 纠正，重要）
- **LarryAgent 多 AI 协作非全自动并行**：由老大手动编排每个 AI 的入场上场时机（原话"该你了，干活儿了"）。AI 不自行抢活、不自动并行推进；**派发 ≠ 自动执行**。
- **推论（纠正 WB 误判）**：WB 作为协调者，**不可把"派发后无交付回写/无提交"误读为停滞或协调缺口**——那是老大的主动排期（如 22:48 我把 P4.4 派发后无回写当缺口，被老大纠正：P4.4 没出问题，只是先排了约束治理）。
- WB 定位 = 架构协调 + 复验，等老大点将（"该谁上谁上"），而非自主推进产品实现。
- **客户端「自动继续」现象 + WB 防线（2026-08-30 老大观察，机制待持续确认）**：老大在 WB 一轮回复结束后看到会话"自动继续"，而非其本人输入——疑似 WorkBuddy 客户端层面机制（可能与会话切入 Agent/craft mode 时的自动续跑相关），此前未出现过，老大表示需继续观察。WB 侧该消息表现为**普通 user_query、无任何系统注入标记**，无法自行分辨来源。

## 用户项目推进瓶颈模式（2026-08-27 老大自述，重要协作信号）

- **结构性瓶颈（老大亲述，经历多项目验证）**：项目走到"初步设想基本都实现了"之后，几乎必然撞上——发现"这破玩意儿和我想要的差太远"，从而必然进入漫长的「打磨→推翻→思考→再打磨→再推翻→再思考」循环，同时还要统筹全局、考虑未来计划、避免弄乱已有成果。
- **理性停步**：老大会在"真正进入这段循环之前"停步（原话"停在了这一步之前"）。原因不是懒/放弃，而是：可停（个人项目无人逼）+ 经历过的人清楚那段循环的代价 → 选择在前一步刹停。**很多他自己弄的项目都停在了这一步。**
