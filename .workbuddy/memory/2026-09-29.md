## README.md 行尾统一（2026-09-29 14:56）

**任务**：老大「README.md 的 LF 问题你统一一下，然后其他的我来」。

**动作**：`README.md` 工作区 LF → CRLF（225 行：`CRLF 0→225`、`bareLF 0`、13723→13948 B）。
Python 二进制归一化（先 `\r\n→\n` 再 `\n→\r\n`，防混合），**内容零触碰**。

**核验（三层，全过）**：
- `git ls-files --eol README.md` → `i/lf  w/crlf`
- 逐字节对照：`工作区.replace(b'\r\n',b'\n') == git cat-file blob :README.md` → **True**
- `git diff --quiet README.md` → **exit 0**；`git update-index --refresh` 后 `status --porcelain README.md` → 空

**⭐ 新机制认知（有长期价值）**：`autocrlf=true` ＋ 索引恒 LF ⇒ **工作区行尾改动在 git 层面完全静默**。
中途 `git status` 会因 **stat 缓存（mtime/size 变）** 显示 ` M`，实际 `git diff` 为空、refresh 后即 clean。
⇒ **判「有无改动」不能只看 `git status`，要看 `git diff --quiet` 退出码**。
推论：本次「统一」**不产生提交、也无从提交**（autocrlf 下 clone 本就会产 CRLF），只是把野生 LF 掰回规范态。

**⭐ 根因（实证）**：**Write（整文件重写）产 LF；Edit（字符串替换）保留原行尾**。
证据：① `docs/dsh/dsh-migration.md` 经多次 Edit 仍 `w/crlf`；② `.workbuddy/memory/*.md`（Write/Edit 建）26 个全 `w/lf`。
⇒ **改 CRLF 文件禁用 Write 整文件重写**；必须写整文件时，事后再用二进制校/修行尾。
