## §二 「是否暂停一个月再推进」（老大 06:07 提出）—— WB 判断：不成立

> 老大原话要点：「现在对齐的 012 几乎可以肯定是一个很多特性过期的版本；而另外一面，或许再过一个月，015 也会变成现在的 012 一样是一个很多特性过期的版本，所以或许我把这个项目丢着放一个月再来看说不定是一个更好的选择？」

### 1. 前提要纠一半

「0.1.2 很多特性过期」——若指**上游加了很多新功能**，成立；若指**我们依赖的面过期了**，**实测不成立**：
- `packages/sdk` **src 零改动**（只有 README / i18n / 测试 / 版本号）⇒ 3.1 / 3.3 依赖的面没过期
- 3.2 靶子（`core/agent` collision 边界 `enter()`）**两版逐字同构** ⇒ 没过期
- `storage` / `sandbox` 改动 +84 / +67 行 ⇒ 小
- **真正大变的是 `packages/session`（+28,494 / −9,711 + 5 个新包）—— 而它变的正是「session 格式版本化 + 迁移器体系」，我们还没开始产 session 数据 ⇒ 这些新特性的适用对象目前是空的**

⇒ **上游是「加东西」，不是「我们用的东西坏了」。** 两者对基线的含义相反。

### 2. 「等」有两个逻辑漏洞

- **无限递归**：「等到不过期」的**时刻不存在** —— 上游无 GA 时间表（全部 release 为 prerelease，文档 `dsh-migration.md:90`），且 09-10 **一天出两个 rc**。若「过期就该等」成立，则永不启动（一个月后 015 过期 → 再等 → 无限）。
- **差值发散而非收敛**：0.1.2→0.1.5 已是 **6774 文件 / +208,236 / −58,164**；停一个月差值只会更大。⇒ **等待不会让「追上去」变便宜，只会变贵**（除非中间发生 GA / 冻结）。

### 3. 「什么时候才真该等」—— 三条可操作判据（顺带补上 `:872` 哨兵缺的量化标准）

1. 上游出现 **GA** 或 **release 线冻结**；
2. **破坏性变更收敛**（连续 N 个 0.1.x 版的破坏性清单为空）；
3. DSH-3 从**关键路径**降级为**可等待**（现在不是 —— 它决定「迁移路线成不成立」，是产品架构地基）。

⇒ 现状 **三条全不满足**。

### 4. 老大焦虑的真答案：分账（不是「等」）

真实焦虑 =「我是不是在一个注定过期的版本上白干？」
**答案：机制结论不作废，只有实现代码易碎。**

- ⭐ **DSH-3 现在一行实现代码没写 ⇒ 正处在「只攒机制、不攒实现」的最佳窗口**
- ⇒ 正确姿势不是「停」，是「**把机制验证做完，把实现留到基线定死之后**」

### 5. ⭐ 成本论推不出行动（对称句式）

## §9 第三轮：WB 的错误被老大戳穿 → 撤回 → 改判（2026-09-15 06:2x）

### 9.1 🔴 WB 的错误（必须留痕，勿重犯）

§8.2 那条「**历史 16 个 tag 零 stable ⇒ 等 stable 的等待对象不存在**」，被老大一句话戳穿：「**按你这个理论，DSH 永远不会有 stable 了不是吗**」。

**错误性质 = 截尾数据（right-censored）误读为终局判断**：
- 「历史上没有 stable」这条证据，**在 stable 出现之前的任何时刻都成立** ⇒ 它是个**自证/永真命题**，不携带任何关于「会不会发」的信息。
- 任何项目在发出第一个 stable 前都是「零 stable 先例」——用它否定未来，就是把「尚未发生」说成「不会发生」。
- 补强：DSH npm 首发 `0.0.1-rc.1` = 08-10，**至今仅 36 天**；且其 `.agents/notes/` 里最早架构笔记为 **2026-06-11**（实际开发史更长）。**36 天没发 stable 什么信息都没有。**

**⇒ 该"反证"作废、撤回。**

### 9.2 查到的三条真正有信息量的事实（换到「读他们的声明」通道）

**① stable 是**明文预留的通道**（🟢 `dsh-v0.1.5-rc.2:.agents/notes/implemented/process/2026-08-10-npm-release-sequences.md`）**
> 「`dsh` publication maps `alpha` and `canary` to their matching npm dist-tags, maps other prereleases including `rc` to `next`, and **leaves stable versions to npm's `latest` default**」
> 「…every prerelease is lower than **the stable version**」
`release:dsh` 命令接受 `major` / `minor` / `patch` / 显式版本 ⇒ **发 stable 只是"把版本号写成不带 prerelease 的形式"，机制完备，缺的只是产品判断。**

**② rc 不是草稿，是承担正式义务的发布（🟢 `dsh-v0.1.5-rc.2:docs/session-format-status.md:23`）**
> 「An alpha, beta, or release-candidate product publication **establishes released Session-format obligations**. GitHub's prerelease flag does not make persisted user data disposable.」
⇒ **rc 已确立「已发布 Session 格式义务」** ⇒ 我们锁的 `0.1.2-rc.1` / `0.1.5-rc.2` **都是有正式承诺的版本**，不是临时快照。

**③ profile 的 DSH 版本是「精确 pin」（🟢 本机实测）**
```
.dsh-home/profiles/sdk/package.json   dependencies:
  "@deepseek-ai/dsh-base":    "0.1.2-rc.1"     ← 精确，非 ^、非 latest
  "@deepseek-ai/dsh-sdk-app": "0.1.2-rc.1"
实际安装：94 个 @deepseek-ai 包 = 0.1.2-rc.1（+ cordis 系 vendor 包 1.0.x/1.8.3/3.18.2、landlock 0.1.1）
.dsh-home/profiles/larry 同样精确 pin 0.1.2-rc.1（+ link:harness/packages/plugin-probe）
```
⇒ ①「我们跑的就是 0.1.2-rc.1」**成立、无漂移**；② **迁移到 0.1.5-rc.2 = 改两个版本号 + 重跑 install**（94 个传递包自动跟上）——**成本比 §5 估的更低**。
