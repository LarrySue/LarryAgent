## 老大提出「会话状态策略」洞察 —— memoryV2 到 memoryV3 的性质重述

**背景**：WB 问「生产平时同时开几个会话」（为了收口 2G/4G 的最后一个变量）。老大以真实使用视角重述问题——侧栏长期存在十几二十个会话（和 DeepSeek、千问 App 一样），用户懒得归档。

**⭐ 老大的核心洞察（正确，且推翻了我提问的前提）**：
> 这并不是需要回答"几个"的经验事实，而是 **retrieval/retention policy** —— 由我们的 UI 层自己决定。

**三层区分（老大提出，WB 确认并精确化）**：
| 层 | 内容 | 是否由策略决定 |
|---|---|---|
| ① 一次 stripping 全部 history | Storage granularity（粒度） | ✅ UI/产品决策 |
| ② retrieval 时不要求 storage 驻留 | Retrieval policy | ✅ UI/产品决策 |
| ③ storage 常驻所有 active session | Retention policy | ✅ UI/产品决策 |

**关键类比（老大）**：邮件客户端 full text search + 异步 continuing load
- 原始邮件 stochastic 压缩在磁盘，**查询时无需全部解压**
- 只在要"看某封全文"时才异步加载 → **retrieval 时只需 hit selecting clicks**
- 未点开的邮件永不全文加载 → **冷会话不占内存**

**由此推出**：这个现象远比想的重要，只是**被 `tools.call_llm` 综述设定掩盖**了。

**WB 的修正补论（提交给老大确认）**：
1. **确认三层都是 UI 层决策** ✅ —— DSH 侧storage baseline 本来就是"按需读取"（`collection.get(id)` 零物理 IO 已在那时命中 sophistication 机制）
2. **但老大推论"电子满足条件后可以排除 4G/2G 之分"需要一个前提补充**：
   - 侧栏 20 个会话全部"冷" → 确实几乎不占内存 ✅
   - **但"会话热起来"的成本因此更值得单独度量**：
     - 每次点冷会话 → 要重建 context / 恢复 history
     - 这涉及**时间延迟**而非内存
   - 所以真正变成的问题是：**Winchester 的驻留选择**（内存 vs 延迟的取舍），而不是内存本身消失
3. **memoryV2 到 memoryV3 的性质变化**：

## 午间 · ⭐ 推翻自己昨天的「多会话 = 多子进程」结论（2G/4G 之争收口）

**起因**：老大问「侧栏长期挂十几二十个会话，算不算并发？」—— 这个提问直接暴露了我昨天结论的错误前提。

**⭐ 我昨天写进文档的假设被证伪**：sdk 路线「多会话 = 多子进程、内存线性上涨」。

**反证 1 — 官方契约**（`dsh-sdk-client/lib/index.js` L608-609 原文）：
`DeepSeekHarness` owns **one** runtime subprocess **across many sessions`；`session()` 注释「no wire traffic; the runtime creates the session on its first prompt」。

**反证 2 — CVM 三组实测**（`~/harness/multi-session-probe.mjs`、`mspp.mjs`、`lcp.mjs`）：
| 实验 | 结果 |
|---|---|
| 开 20 个 session 句柄 | 进程恒为 1，**RSS 增量 0.00 MB**，client heap 仅 5.4MB |
| 6 会话各跑真实 prompt | 128→150.7MB，**边际 2.24 MB/会话**（递减），外推 20 会话 ≈ **182MB** |
| 单会话连跑 18 轮 | 131→154MB，**turn16 突降 -17MB**（有回收），内存**有界** |
| close 后 | 残留进程 **0** |

**→ 结论：多会话 ≠ 多进程。2C2G 够，2G/4G 之争收口。**

**踩坑**：① ESM 脚本里用 `require()` 会因 top-level await 报 ERR_AMBIGUOUS_MODULE_SYNTAX（改 `import`）；② **改了本地脚本忘了重新 scp**，远程跑的仍是旧版 —— 白跑一轮。

**边界（不外推，已写进文档）**：解 session 文件统计，compaction 事件计数 = **0**，故 turn16 的 -17MB **无 compaction 佐证，最可能归因 V8 GC**，**不能声称"DSH 自带 compaction"**。另取到硬数据 **`contextWindow = 1,000,000` token** → 18 轮远未触顶，"未观测到 compaction"应解释为"未到阈值"而非"无机制"。

**次级更正**：`dsh-migration.md` 曾把 Gateway 的「单进程多会话」列为相对 sdk 的优势 —— **该优势论据失效**（sdk 同样是单进程多会话）。Gateway 独有的仍是会话树/fork/cancel/历史分页/重连追赶。

## 深夜 · git rm / 目录消失问题系统排查（跨 9/10-9/11，01:30 收工）

### 结案项 1：`git rm` 删"空目录链"——官方特性，非 bug（已结案，不再深究）

**现象**：`git rm <深层文件>` 时，若该目录链因此变空，**整条链被删**。

**权威依据（网络核查所得）**：
- 2018-06-06 git 官方邮件列表（`lore.kernel.org/git/`）原始报告，标题 "git rm bug"（Thomas Fischer）
- 可追溯到 2006 `d9b814cc97`（**Linus 本人的提交**），Linus 当年即知此副作用并讨论过是否加开关，最终未加
- git 官方立场：**不是 bug** —— "Git cannot track empty directories"，整条链是唯一内容则必须删
- 官方文档 12 年未改（2.13.7 → 2.50.0），**未记载此行为**（`<pathspec>` 段只讲"给目录名要加 -r"）
- 附带：`git checkout` 切分支删掉最后一个文件时同样会删空的父目录链

**老大判定**：*"空目录要不要保留可能见仁见智，但既然 git 官方认为不需要保留，那就是特性而非 BUG"* → **gitemtest 系列测试判定为无参考价值，结案**。
