## 老大定调：S 侧是根基，C 侧是薄层（架构权重分配）

- **老大原话意**：「S 侧只要不出问题，C 侧怎么都好做——无非几个界面几个简单功能模块，哪天想推翻重做都没问题。**S 侧是根基、重中之重：数据、模型、记忆、知识、配置、归档、会话都在那边**」。
- **WB 认同，且该判断有据可依**：C 侧重做成本 ≈ 界面 + 少量模块；S 侧出问题 = 数据/记忆/会话/归档全盘受损，两者不可比。**与 A-framework 主战场一致**（贴近的是 DSH 核心层，核心层在 S 侧）。
- **⚠️ 该定调成立的前提（WB 补，须守住）**：**C 侧不得承载 DSH 运行时**。若端侧执行器走 DSH 的 Windows sandbox（+ answerer 回调 + 事件流），C 侧就从薄层变成"嵌了框架运行时的宿主"，**推翻重做成本与 S 侧绑定**，老大的定调随之失效。
- **由此推出的建议（待老大定）**：**2.10.2 端侧执行器走 Tauri 原生自做，不引 DSH Windows sandbox**。
  * 收益：C 侧保持薄层（符合定调）；绕开 Windows segfault / fail-closed / 提权流程一整坨；DSH 部署面收敛为纯 Linux server
  * 代价：三档沙箱策略（read-only / workspace-write / danger-full-access）+ 一次性提权审批须自做（工作量一次性、可控）
  * 连带解决：DSH-2 退出条件③ 的权重倒置（③ 可降级为局部选型项，不再触发全局重估）、承接总表 2.10.2 格内自相矛盾
- **性质标注**：以上建议是**从老大的权重定调推得**，非"技术上必须"——走 DSH 沙箱技术上也可行，只是与定调冲突。
