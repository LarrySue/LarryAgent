## 老大定调：S 侧是根基，C 侧是薄层（架构权重分配）

- **WB 认同，且该判断有据可依**：C 侧重做成本 ≈ 界面 + 少量模块；S 侧出问题 = 数据/记忆/会话/归档全盘受损，两者不可比。**与 A-framework 主战场一致**（贴近的是 DSH 核心层，核心层在 S 侧）。

## 探讨：DSH 纳入后的「开发时」项目结构（老大提问，边聊边定）

- **git 范围 = 只包含我们的部分**：进 git 的是 `harness/`（TS 插件源码）+ `client/` + `mobile/` + 文档区；**不进**的是 DSH 本体（npm 依赖）、`DSH_HOME`（装配点）、`node_modules`、编译产物。与现在（Python 依赖不入库）无性质区别。
  * **真正变了的点**：现在 clone 下来 `pip install` 就能跑；将来 clone 下来**跑不起来**——DSH 是**宿主**不是依赖（numpy 不装顶少少个函数，DSH 不装是整个东西不存在，无入口）。
- **工程数量没变多，但关系变了**：现在 backend + client = 2 个独立进程、HTTP 互通、各自可独立启动调试；将来 harness 不是进程，是**注入 DSH 进程的插件**，不能独立启动。
  * **调试多一层**（宿主层，我们看不见内部）：client devtools → 通信层 → **DSH 宿主进程（新增）** → cordis 加载 → 我们的插件（Node inspector attach）
  * **压缩办法（设计原则）**：**纯逻辑 + 薄适配层**——纯逻辑（记忆提取/角色组装/参数校验/检索排序）走 Vitest 单测**不起 DSH**；只有适配层（`ctx.tools` 注册 / 事件订阅 / answerer）才需要 DSH 环境。这也是 DSH-2.4 测试基建单列的理由。
- **🟢 新发现（查锁定版源码）：DSH 自带完整 C/S 应用骨架**——`host/`（HTTP server + SPA dist server）／`api/`（Client→Host typed remote calls + forwarded events）／`client/`（browser transport）／`apps/cli` 启动 `dsh-base` bundle serve `apps/web/`。即"后端+前端+远程 API 契约"它全都有，与我们的结构同构。
  * **但这不改变既有判定**：§3.6 前端路线已定死「**保留 Vue/Tauri，走 sdk / acp profile 对接，不采用 DSH Web-GUI**」→ 开发态与 PC 单机走 **stdio**（Tauri 起 DSH 子进程），**不过 HTTP**；只有上云才需 HTTP/WS 网关，而 §3.3 已定云端自做。**WB 一度误以为"S 侧 HTTP 层用谁的"是个待定分叉，实为查漏——已向老大更正。**

## UI 自由度边界定界（同日，老大追问"能不能全部重写、自由替换"）

- **结论：能全部重写，且边界可精确划定。** 三条机制事实：
  1. **浏览器端插件运行时加载**：`dsh-client-modules` 的 node half **扫描 cordis 插件树** → 组合 `window.__DSH_BOOT__` → 服务 **`/plugins/<id>/client.js`**。→ **自写插件带 browser half 即被自动装配进官方前端 shell**。
  2. **UI 是插件 roster 组合，非单体**：`dsh-web-app/cordis.patch.yml` 里 30+ 个 `client-ui-*` 各占一行（theme/layout/renderer/session/sidebar/settings/chat/approval/plan/goal/brand…）→ **改 roster = 改 UI**。
  3. **brand 是显式插槽**：装配文件原话 *"Official occupants for the generic sidebar and conversation **brand slots**"* —— 官方只是 occupant，第三方可占位。
- **三层自由度**：L1 换皮（theme + 占 brand slot，成本最低）／L2 换或增删单个部件（roster 换行）／L3 换整个前端（自做前端**直连 `/api`**；connection 的 node half 把 gateway 挂在 `/api`，browser half 是 **fetch/SSE**）。
- **硬边界**：① 前端 shell dist **不作为用户配置**开放（"never user config"、dist 缺失即停、**无 source-serving fallback**），能否整体换 dist 待验（测试提到 "fallback seat"）；② 鉴权必须过（token→签名 cookie，实测 401）；③ 传输是 **HTTP unary + SSE，不是 WS** → 自做客户端成本低于此前预期；④ L2 反向工具执行仍须自做。

## 【讨论中·待老大确认后落档】中转 vs 直连：对称性论证不成立

老大提出：① 迁移复杂度两边差不多 ② 双向迁移概率差不多 → 若成立则选哪边无所谓。**WB 判：两条都不成立**，且**若对称性真成立，数学上反而指向直连**（见下），所以必须说清为什么它不成立。

- **纯期望成本推导（诚实摆出来）**：设 A = 中转多付的 API 层成本，F = 切换时前端改造成本，p = 迁移概率。中转 = A + p·F；直连 = p·A + p·F。**p<1 时中转更贵（多付 (1-p)A）** → 对称性成立则应选直连（推迟付费）。
- **推翻它的四条非对称**：
  1. **【最硬】不确定性关在哪 —— 改动表面积不对称**：中转把 DSH 的 preview 期漂移**关在 B 段（服务↔DSH，一处）**；直连把漂移**暴露给前端（PC + 移动多端）**。→ 中转让前端**更晚被锁定**，这是"延迟决策"价值，不是成本。
  2. **C 段反向通道**：中转下指令走「我们的服务↔C 侧」，不经 DSH，自然；直连下消息流走 DSH、本地工具走我们服务 → **两条通路并存，别扭**。
  3. **协议漂移隔离**：中转的 API 层是防腐层，官方 Typert 漂移不冲击前端。
  4. **多端一致性 / 状态聚合**：中转天然可做，直连需另行解决。
- **反向不对称（对直连有利，是中转的真实代价，勿回避）**：直连下前端可**复用 41 个 `dsh-client-*` 官方组件**（L1/L2 自由度）；中转下官方组件要连 Typert，用不了 → **前端只能 L3 全自做**。
- **概率不对称**：直连→中转的驱动力是**必然需求**（服务端业务层必然存在，LarryAgent 有 23 项产品语义层要自做）；中转→直连的驱动力是**可选优化**（成本/复用诱惑）。→ p(直连→中转) >> p(中转→直连)。
- **推论（关键）**：**「纯直连」实际上不存在**——业务层迟早要服务端，直连会自然演化成「消息流直连 + 业务中转」的混合。**真正的选项不是二选一，是"消息流走哪条"。**
- **A 的重估**：中转的额外成本其实只有 **A' = 消息流 API 层**，不含业务服务端（两种方案都需要）。差距比表面小。
