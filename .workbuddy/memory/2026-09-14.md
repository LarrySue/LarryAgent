## 七、老大问「backend/config.yaml 废了吗 / 是否统一写 .dsh-home」（第 1 条 Key 的追问）

**结论**：`config.yaml` **没废**；且这不是"迁移"，是**两条轨各一份**。

1. **`config.yaml` 是 backend（现役 Python agent）的配置中心** —— 被 8 个子系统（models / tools / services / memory / rag / api / db / middleware）+ 测试广泛引用；**不止装 LLM Key**（还有 roles / server / database / embedding / search）。
2. **两条轨各读各的载体**：backend 轨 → `backend/config.yaml` 的 `models.deepseek.api_key`（✅ 已填、服务正常）；DSH 轨 → `$DSH_HOME/.credentials.yaml` 的 `refs.DEEPSEEK_API_KEY`（❌ 未填）。
3. **并存是设计**：`dsh-migration.md` 回退条款"旧 Python 后端在 DSH-6 验收通过前保持可用、可回退" ⇒ **`config.yaml` 那段 Key 在此前不得移除**（移除 = 现役后端直接起不来）。
4. **终态收敛为一处**（DSH-6 后 backend 退役）。
5. **取值**：同环境两轨填**同一把**（Key 按环境分、不按轨分 ⇒ 本机两处都用 `larry-dev`）。

**⭐ 本轮新发现的关键坑：本机有两个 DSH home**

## 九、CVM 凭据落位复验 —— 发现并修掉一个「静默降级」缺陷

### A. ⚠️ WB 一次判断失误（老大戳穿：「你不是都能操作那个 CVM 吗」）

- **误因**：查 `describe_key_pairs` 返回空 ⇒ 推"只能密码登录" ⇒ 推"我没密码 ⇒ 上不去"。

- ⭐ **方法论（与既有纪律同源，这是又犯一次）**：`describe_key_pairs` 的判据**只覆盖"经控制台绑定的密钥对"这一条路径**；拿它推"SSH 不可用" ＝ **用一条通道的判据去下另一条通道的结论**。⇒ **判"我能不能操作 X"，先实试通道，别用间接元数据推断。**

### B. 复验发现真缺陷：冒号后缺空格 ⇒ 静默降级

老大说"我改好了"后实连复核（只读三查 + 结构 dump）：

- **表面全对**：`ls -l` = 600 / 222 B；`grep '^[A-Za-z]'` 得 `version`+`records`+`refs`；`grep -c 'DEEPSEEK_API_KEY:'` = 1

## 十四、3.3 审批依赖缺边 —— 细说（三层实测证据）

### A. 缺的是什么

一条**从 DSH 运行时长出来的反向请求**（server→client request），用于把 `approval/request` 送出 B 段、经 A 段到达人。

### B. 三层证据（今日实测，补齐文档已有判据的机制层）

1. **SDK 协议面：3 请求 + 4 通知，无反向请求**（`dsh-sdk-protocol/lib/types/types.d.ts` 原文）
   - client→server：`initialize` / `session/prompt` / `shutdown`
   - server→client：`session.event` / `session.status` / `subagent.started` / `subagent.finished`
   - ⚠️ **但这两个 Map 是"已实现"的清单，不是"传输层能力上限"**
2. **⭐ 传输层本来就支持双向，且官方明说留给审批**（`dsh-sdk-protocol/README.zh.md` 已知限制原文）：
   > "**server→client 请求是未使用的功能** —— 传输层支持，但服务器**从不发送**；**Python SDK 的应答接口为未来审批流程预留**。"
   ⇒ **不是"协议不可能"，是"官方留空给使用者补"** —— 而且它自己点名留给"审批流程"。
3. **⭐ ACP 侧真实会发这条请求**：本仓探针 `harness/scripts/cvm-probes/cvm-acp-probe.mjs:46-52` 已在处理
   ```js
   // server -> client request (needs a response)
   if (msg.id !== undefined && msg.method) {
     if (msg.method === 'session/request_permission') { ... 回 allow_once ... }
   }
   ```
   ⇒ **同一条能力，在 DSH 里真实存在（ACP 侧已验证），只在我们选定的通道（SDK）上被留空。**

### C. 但 ACP 不能因此改走

`dsh-migration.md:373/380` 已判：acp 明写 **"never private DSH presentation data or methods"**、**"不适合 UI"**，无 fork/replay，正确用途是**子代理/测试集成**。⇒ **不能因"ACP 有审批"就推翻 B 段走 SDK。**

### D. WB 建议：拆开，而不是择一

3.3 现判据把两件事焊在一起：**(a) interaction/answerer 接入是否成立**（DSH-3 该验的）＋ **(b) 审批请求能否到达真人**（依赖 A 段协议，属 3.8）。
⇒ 拆开：(a) 用**CVM 就地 answerer 插件**验（五用例 fail-closed + 摘掉 answerer 的负向对照）；(b) 显式挂到 **3.8 的验收项**（A 段协议须含"审批请求双向中继"）。
⇒ **不把 3.3 改成"等 3.8"** —— 3.8 是 DSH-3 最大工作量（流式/会话/鉴权/多端/补帧全自实现），挂上去等于整个阶段收口被拖。

### E. TS SDK client 侧现状

`dsh-sdk-client/lib/types/client.d.ts` 公开面 = `initialize` / `prompt` / `request(method,params)`（**发**）/ `subscribe`（收**通知**）/ `close` —— **未见"注册入站请求处理器"的口**。⇒ 若走路②（自补），客户端要么自己拿传输层搭、要么自写 client（协议是 newline JSON-RPC，文档化）。**Python SDK 有应答接口，TS 没有** —— 与 README 那句"为未来审批流程预留"吻合。
