### 一、凭据机制（权威源：`dsh-credentials-local/README.zh.md`，本机已装包）

**DSH 的模型 key 不走 `config.yaml`，走独立的 credentials seam。四层来源，先有值者胜出：**

| 优先级 | 位置 | 可写 | 备注 |
|---|---|---|---|
| 1（最高） | 启动环境 `DEEPSEEK_API_KEY=… dsh` | 否（只读，写入被拒） | 环境层是**启动时拍摄的快照**，启动后 export 看不到 |
| 2 | 受管存储文件 `$DSH_HOME/.credentials.yaml` 的 `refs:` | 是（GUI 或手编） | 手编**自动热重载**；写入保留注释与排版，同刻并发修改会被并入而非覆盖 |
| 3 | 项目 `.env`（`<invocation cwd>/.env`） | 不在此处（只读后备） | 优先于第 4 层 |
| 4 | 主目录 `.env`（`$DSH_HOME/.env`） | 不在此处 | 无 |

- **模型适配器**：`dsh-llm-deepseek` 的 `apiKeyEnv` 默认 `DEEPSEEK_API_KEY`，"先经凭据 seam，再到环境变量"，**按请求解析**（换 key 无需重启）；`baseURL` 默认 `https://api.deepseek.com`，`$DEEPSEEK_BASE_URL` 优先。
- **无 CLI 子命令**：全仓搜 `credentials set|unset|…` 零命中 → 只能用配置界面或直接编辑文件。
- **存储文件格式**：`version:` / `refs:`（按环境变量名存值）/ `records:`（按 `<owner>/<id>` 存插件凭据）。**只放凭据**——非 mapping 根、未知顶层键、空值、类型错、重复键、YAML 错一律**启动时失败**；运行期热重载失败则保留最后可用快照 + 告警。
- ⚠️ **POSIX 强制权限**：产品会**拒绝加载任何"其他用户可读"的文件**（报错提示 `chmod 600`）；Windows 无 mode 可查故跳过。→ **CVM 是 Linux，scp 上去若为 644，DSH 启动会直接失败**（部署必踩）。
- ⚠️ **agent 可读（官方原话）**："agent 不是另一个用户：它的工具进程以你的身份运行，因此它们读这个文件与读你拥有的任何其他文件毫无二致。产品绝不把文件路径交给 agent，也绝不把文件载入环境……**这是审慎，不是边界**：必须让提供方密钥远离自身 agent 的部署**无法靠文件权限做到**。" → 对本项目形态有直接含义：DSH runtime 带 file_ops/shell 工具，**key 对它天然可读**。

### 五、老大追问：是否需要建 Linux 测试环境？WSL 能否承载？（15:22）

**前提澄清**：老大表述「我们只有一个 Linux 环境，用来作为生产环境」。核对 → **CVM 现在不是生产环境**（项目未发版、无生产数据、无用户），它是"唯一一台 Linux 验证机"，将在第一版发版时成为生产。所以"保护生产"这个动机目前**尚未到期**。

**实测发现（推翻我的初始假设）**：本机 WSL **早已装好**，不是"没装"。
- 发行版：**Ubuntu-24.04**（WSL2，DefaultUid 1000，与 CVM **同发行版**）
- 数据：`%LOCALAPPDATA%\wsl\{3cf082f8-...}\ext4.vhdx` = **2.44 GB**，目录创建 09-09 17:10、最后写入 09-09 **18:59** ⇒ 装完有实际使用痕迹
- **内核：6.18.33.2-microsoft-standard-WSL2**（读 `C://Program Files\WSL\tools\kernel` 二进制里的版本串，非推测）
- ⇒ **landlock ABI V7**（V3=6.2 / V4=6.7 / V5=6.10 / V6=6.12 / V7=6.15 / V8=7.0）→ **高于 CVM 实测的 ABI 4 两级**
- ⇒ DSH sandbox 所需的 `LL_FS_REFER`(≥2) / `LL_FS_TRUNCATE`(≥3) 全满足且富余；CVM 缺的 ABI v5（设备 ioctl）WSL 反而有
- ⇒ **"WSL 扛不住 sandbox 判定"这个判断，技术上不成立**（WSL 有 landlock 由微软官方内核公告 + landlock.io 官方背书）

**WSL 的三个真实短板**（不是 landlock）：
1. 🔴 **WB 够不着它**：`wsl.exe` 在**程序黑名单**内，WB 完全无法调用（对比 CVM 可直连 ssh）⇒ 所有 WSL 操作须老大手动，自动化闭环断掉。
2. 🟡 **文件系统陷阱**：工作副本放 `/mnt/<盘>`（9p/virtiofs）会 **flock 失效 + inotify 缺失 + 小文件 IO 指数级变慢**；必须放 WSL 内部 ext4（`~/`）。**DSH 有 session 锁 + node:sqlite，恰恰最怕锁失效** ⇒ 放错会得到一堆"看起来像 DSH bug"的假故障。
3. 🟡 **两处待实测**：① WSL 的 PID 1 独占 seccomp USER_NOTIF（DSH 若走 seccomp 退路会 EBUSY；走 landlock 则无碍）；② systemd 默认关闭。

**WB 判断（建议）**：
- **不为此专门再买一台 Linux** —— 生产尚不存在，"生产/测试分离"的真正时点是**第一版发版前**，那时需求更清楚。
- **WSL 直接当"可销毁实验场 + 跨机装配验证场"用**（零成本，已在手上）——尤其**跨机装配验证**（`link:D:/...` 硬伤）这条判定**本来就要求"第二台干净机器"**，WSL 比 CVM 更合适（可 `--unregister` 重来，不污染 CVM）。
- **但不能当生产替身**：判定环境仍只能是 CVM（判据不得取自替身运行时）。
- **生产数据保护**用 **CVM 快照**（lighthouse 工具集含 `create_instance_snapshot` / `create_disk_backup`），比第二台机器便宜得多。
