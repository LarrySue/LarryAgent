## 一、结论（TL;DR）

1. ✅ **架构本质 = 云脑 + 本地手**。C/S 里 C（客户端）承载"有本地副作用"的能力，S（云端）承载"无本地副作用"的能力。选 C/S 而非 B/S 的根因，就是 S 需要驱动 C 本机的**命令行 / 文件系统 / 文件记忆 / 工作空间 / 本地数据库**。
2. 🔒 **云端**：LLM 路由 + 对话编排 + 云端长期记忆（SQLite 真相源 + ChromaDB 索引）+ web_search + 鉴权 / HTTPS。
3. 🟡 **客户端**：Tauri UI（✅ 已落地）+ 本地执行器（shell / file_ops / 本地文件记忆 / 工作空间 / 本地数据库）（🔒 未落地，见 §八）。执行器是后续版本能力，本文只定边界。
4. ✅ **两个环境**（⚠️ **术语钉死**：本文所有「本机」一律指**跑 backend 进程那台机器的回环命名空间**，不等于「老大手边那台设备」——二者只在现态重合）：
   - **开发测试态（现态）**：单机，client + backend 全在本机 `127.0.0.1`，**已鉴权（`server.api_key` dev 侧已设，2026-10-29 甲案）＝🟡 上锁已落、HTTPS 仍无**。
   - **生产态**：backend 上云（VPS），多台 PC 客户端经 HTTPS 访问。⇒ 届时 `127.0.0.1` 是**云机自己的回环**，"只监听回环"不再等于"只有用户可达"；公网与能力之间的屏障换成 **Nginx 反代 ＋ `server.api_key`**（见 §五）。🔒 未实施。
   - 🔗 **三种会打破「回环 = 只有我」的形态**（备查，✅ 三条机制均实测在册）：
     ① **backend 上云**——即上面那行，前提整体失效；
     ② **改绑局域网给手机／其他设备访问**——WSL 网络形态实测为**宿主网卡镜像、非 NAT**，在 WSL 内绑 `0.0.0.0` 等于暴露整段 LAN（🟢 两通道实测，`docs/test-env.md` §6〈WSL 网络形态〉；防火墙 Public profile 只是挡了一部分，不是设计边界）；
     ③ **DSH 侧同构**——官方 UI/API 出厂也只听 loopback，外部接入必须反代 ＋ `--trusted-host`（`docs/dsh/dsh-migration.md` §4〈上游结构性约束〉）⇒ 「云脑 ＋ 本地手」的回环是**两段各自**的边界，端到端不成立。
5. 🟡 **上云硬前置（不满足别上）**：`server.api_key` 鉴权（✅ dev 已落／🔒 云侧待设）+ HTTPS（🔒）+ shell/file_ops 能力重划（🔒，见 §4.3）。
6. ✅ **渐进路径（重要，避免错误预期）**：不是"一上云就云脑+本地手全套"，而是——
   - 阶段 1（现态）：单机全功能。
   - 阶段 2（第一版上云）：云端只提供脑能力 + web_search；shell / file_ops 暂**禁用或仅本机模式可用**。
   - 阶段 3（本地能力下沉后）：完整的"云脑 + 本地手"。
7. ✅ **CVM 不是下一个落点**（老大 2026-10-29 裁定）：只在「上云」那一刻才成为落点，**不在当前这条线上、不阻塞**。依据与证据等级见 §5.4。

## 二、云 / 端边界划分

| 模块 | 现位置（开发测试） | 目标位置（生产） | 状态 | 说明 |
|---|---|---|---|---|
| LLM 路由 / 对话编排 | backend 本机 | **云端** | 🔒 迁移未做 | function calling 循环，无本地副作用 |
| 会话管理（conversations） | backend 本机 | **云端** | 🔒 迁移未做 | SQLite 表，多端共享 |
| 云端长期记忆（SQLite + ChromaDB） | backend 本机 | **云端** | 🔒 迁移未做 | 多端共享的单一真相源 |
| Embedding（local bge-small / openai） | backend 本机 | **云端 VPS 跑 local** | 🔒 迁移未做 | LLM API 是唯一出境通道 |
| web_search | backend 本机 | **云端** | 🔒 迁移未做 | 纯网络，无本地副作用 |
| 角色 / 模型清单 | backend 本机 | **云端** | 🔒 迁移未做 | config.yaml 下发 |
| API 鉴权 | 未启用 | **云端** | 🟡 **dev 侧已上锁（2026-10-29）**，云侧未设 | 上云硬前置；机制定性见 §5.1 |
| HTTPS | 无 | **云端** | 🔒 未实施 | 与鉴权是一对硬前置（§5.1） |
| **file_ops（读写文件）** | backend 本机 | **客户端（下沉）** | 🔒 未下沉 | 操作本机文件，必须端侧执行 |
| **shell（执行命令）** | backend 本机 | **客户端（下沉）** | 🔒 未下沉 | 操作本机命令行，必须端侧执行 |
| **本地文件记忆系统** | 未实现 | **客户端** | 🔒 未实现 | 未来本地能力；归属边界见 `docs/la-space/`，分层问题属未决（`exchange/deployment-architecture.md`〈记忆系统分层〉） |
| **工作空间 / 本地数据库** | 未实现 | **客户端** | 🔒 未实现 | 未来本地能力 |
| Tauri UI | client 本机 | client 本机 | ✅ | 不变 |
| Tauri 壳（进程守护） | client 本机 spawn 后端 | client 本机 spawn 本地执行器 | 🟡 前半已落、后半🔒 | 现状 spawn 后端 → 未来 spawn 本地执行器 |

> **关键洞察（✅ 定性，⛔ 不是已实施）**：**现状的单机 backend 在目标架构里会"裂变"成两个角色**——
> ① 云端 backend（大脑）：LLM 编排 + 云端记忆 + web_search；
> ② 本地执行器（手）：file_ops + shell + 本地文件记忆 + 本地库。
> 由于现有 backend 已是一套完整的"工具执行 + 记忆"引擎，本地执行器最省力的落地方式就是**复用现有 backend 以"瘦身本地模式"继续跑在客户端机器上**，而不是把工具逻辑重写进 Tauri 原生 command。**该路径本身尚未定案**（A/B/C 三选 ⇒ 见 `exchange/deployment-architecture.md`〈本地工具下沉的实现路径〉，⚠️ 未定案）。

## 三、两种形态对比

```
【开发测试态 · 现态 · 单机】
┌──────────────────────────── PC ────────────────────────────┐
│  Tauri 壳 ──spawn──▶ uvicorn main:app (127.0.0.1:8000)     │
│   Vue3 UI ──/api──▶ FastAPI + SQLite + ChromaDB + tools    │
│        （Bearer 已注入）    (file_ops / shell 操作本机)     │
└─────────────────────────────────────────────────────────────┘

【生产态 · 云后端 + 多 PC 客户端】
                ┌────────────── 云端 VPS ──────────────┐
                │  Nginx (TLS 终止 + 反代)             │
                │     └─▶ uvicorn (127.0.0.1:8000)      │
                │           FastAPI + SQLite + ChromaDB │
                │           + web_search + 鉴权         │
                │           （不碰本机文件/命令）        │
                └──────────────────┬───────────────────┘
                                   │ HTTPS (Bearer API Key)
          ┌────────────────────────┼────────────────────────┐
          ▼                        ▼                        ▼
   ┌─────────────┐          ┌─────────────┐          ┌─────────────┐
   │  PC 1 客户端 │          │  PC 2 客户端 │          │  手机(未来)  │
   │ Tauri UI    │          │ Tauri UI    │          │  HTML5 B/S   │
   │ +本地执行器  │          │ +本地执行器  │          │ (无本地能力) │
   └─────────────┘          └─────────────┘          └─────────────┘
```

要点：

- ✅ 云端 backend **只监听 `127.0.0.1`**，由同机 Nginx 反代对外（backend 不直接暴露公网）。⚠️ **注意该行的实现形态**：现由**启动命令**决定、非配置（§4.1 `server.host` 无消费点）。🔒 Nginx 反代未建。
- 🔒 多端共享同一份云端 SQLite / ChromaDB，无数据一致性难题（单一真相源）——**前提是多端存在**，现态单机。
- ✅ 移动端走 B/S 直连云端，天然无本地能力（浏览器沙箱），与 PC 端能力不对称是**预期内的**（"是否需要云端 workspace 平替"属未决 ⇒ `exchange/` §七.4）。

## 四、配置方案

### 4.1 后端 config.yaml（两环境对比）

| 配置项 | 开发测试 | 生产（云） | 状态 | 说明 |
|---|---|---|---|---|
| `server.host` | `127.0.0.1` | `127.0.0.1` | 🔒 **无消费点** | 生产也保持本机回环，公网经 Nginx 反代。⚠️ 该项当前**不被代码读取**（`main.py` 不含 `uvicorn.run`；复算见下方〈配置消费点复算〉），实际监听地址由启动命令决定（`Makefile` 的 `run`／`dev` 靠 uvicorn 默认值；Tauri 壳显式 `--host 127.0.0.1`）⇒ **本行是目标态**：**要么实现它，要么把它从配置表挪成"启动参数约定"**（二选一未决，见 §八）。 |
| `server.port` | `8000` | `8000` | 🔒 **无消费点** | 不变。⚠️ 同上，现由启动命令 `--port 8000` 决定，配置值不生效 |
| `server.api_key` | **已设（43 字符，`client/.env.local` 同值）** | **强随机长 key** | 🟡 dev ✅ 已落（2026-10-29 甲案）／🔒 云侧未设 | 上云硬前置，空 = 无鉴权暴露。机制定性见 §5.1 |
| `database.path` | `data/larry.db` | 持久化卷路径 | 🔒 | VPS 磁盘，务必挂载/备份 |
| `vector_store.enabled` | `false`/`true` | `true` | 🔒 | 长期记忆开启 |
| `embedding.provider` | `local` | `local` | 🔒 | VPS 跑 bge-small，不额外出境 |
| `tools.enabled_tools` | 全开或列明 | **见 4.3** | 🔒 | 上云初期剔除 shell / file_ops |
| `tools.shell_allowed_ips` | `127.0.0.1`/`::1` | 见 §五 | 🔒 | 与公网访问不兼容 |
| `tools.file_ops_workspace` | `~/larry_workspace` | 见 §五 | 🔒 | 端侧执行后按设备隔离 |
| `machine_id` | `desktop-01` | 按设备区分 | 🔒 | 多端身份标识（未决 ⇒ `exchange/` §七.3） |

> ✅ **key 按环境分（dev／WSL／CVM 三把各走各的），⛔ 不共用**（老大 2026-10-29 定口径）。dev 侧现态只落 dev 那把，**这不构成「云侧也已设 key」的依据**。
>
> ⚠️ **落过的坑（2026-10-29 实测）：yaml 里 `api_key:` 后的引号必须成对。** 只写尾部一个 `"` 时 YAML 不把它当引号、而是**算进值里** ⇒ 值变成 44 字符、末位是 `"`，后果是客户端发出的 Bearer **恒不匹配 → 永远 401**，而症状（"长度对、字也对"）完全不指向格式问题。`client/.env.local` 同理，或干脆不加引号。
> **自查判据（比数引号可靠）**：⛔ 不看原文有没有引号，**看 yaml 解析后的值**——成对引号解析时会被剥离，落单的才会留在值里。等价检查：解析后逐个字符串值判 `startswith('"') or endswith('"')`，命中即污染。
>
> **配置消费点复算**（仓根执行，改 yaml 是否生效只看这三条）：
> ```
> git grep -n "config\.server\.host\|config\.server\.port\|uvicorn\.run" -- backend/   # 现态零命中 ⇒ host/port 无消费点
> git grep -n "config\.server\.api_key" -- backend/middleware/auth.py                  # 命中 ⇒ api_key 是唯一随时可生效的闸门
> ```

### 4.2 客户端连接配置：**两个独立改造，⛔ 别读成"一路都没做"**

> ⭐ 本节讲的是**两件不同的改造**。2026-10-29 落地的是**前者**，后者仍未开始：
> - **改造 A：API Key 的构建期注入 —— ✅ 已落地**（`VITE_API_KEY` → `client/src/api.ts::authHeaders()` → `Authorization: Bearer …`；复算：`grep -c "headers: authHeaders" client/src/api.ts` = **15**，与 `grep -c "await fetch(" ` = **15** 一一对应）。
> - **改造 B：`API_BASE` 从相对路径改可配置 —— 🔒 未实施**（`api.ts` 首行仍是 `const API_BASE = "/api";`）。
> 下面「现状问题 ＋ 目标」两段说的都是**改造 B**。

**现状问题**：前端 `client/src/api.ts` 的 `API_BASE = "/api"` 是**相对路径**。dev 靠 Vite proxy 打到 `127.0.0.1:8000`；但 Tauri 生产打包后 webview 的 origin 是 `tauri://localhost`（非后端地址），`fetch("/api")` 会直接断链——这正是"打包方式见鬼"的一个具体病灶。

**目标（🔒 改造 B 未实施）**：`API_BASE` 从相对路径改为**可配置的绝对地址**，两路注入：

1. **构建期默认值**：Vite 环境变量 `VITE_API_BASE`（dev 默认 `http://127.0.0.1:8000`，产线默认云 URL），打进 bundle。⚠️ 现**未使用**该变量（key 走的是 `VITE_API_KEY`，两者不同物）。
2. **运行期覆盖**：客户端设置页填写「服务器地址 + API Key」，存本地配置，优先于构建默认值。设置页即 `TODO.md`〈UI/UX〉里「设置入口页面（复活）」的落地用途之一。

### 4.3 本地工具的过渡期配置（🔒 未实施）

上云初期（阶段 2）本地执行器未就绪时，**云端 backend 必须显式禁用 shell / file_ops**：

```yaml
tools:
  enabled_tools: ["web_search"]   # 上云初期：只开无本地副作用的工具
```

理由（✅ 定案）：若云端仍注册 shell / file_ops，LLM 会"以为能执行命令/读写文件"，实际操作的是**云端机器**而非用户 PC——这是比"没这功能"更危险的误导（用户亲历过的"数据混染"同类风险）。宁可明确禁用，不可静默错位。

⚠️ **本条只在「backend 真上了云」时才有触发点**：现态 backend 跑本机、`server.host` 无消费点 ⇒ 不存在"手滑就对外"的路径（§5.4）。

### 4.4 便捷切换方式

- ✅ **后端（通道已具备）**：复用已支持的 `LARRY_CONFIG` 环境变量指向不同 profile，如 `config.dev.yaml` / `config.prod.yaml`。启动命令 `LARRY_CONFIG=config.prod.yaml uvicorn main:app`。该通道**已被测试隔离验证可靠**（消费点 = `backend/config.py::load_config()`；Tier 0 红线即靠它，见 `docs/test-env.md`）。
- 🔒 **客户端（未实施）**：设置页「连接目标」切换 `本机 / 云端`，一键改写 `API_BASE` 与 API Key，无需重打包。属 §4.2 改造 B ＋ §6.1 改进点 2 的同一件事。

## 五、隔离手段（安全边界）

| 层 | 手段 | 现状（2026-10-29） | 上云动作 |
|---|---|---|---|
| 传输 | HTTPS / TLS 终止 | 无 🔒 | Nginx + 证书（Let's Encrypt 或云厂商） |
| 鉴权 | `server.api_key` Bearer 校验 | 🟡 **dev 已设 key、客户端已带证**（空 key 透传仅描述代码分支，**不再是现态**） | 云侧**必须设置强随机 key**（AuthMiddleware 已就绪） |
| 网络暴露 | backend 只监听 127.0.0.1 | ✅ 已如此，但**由启动命令决定、非配置**：`Makefile` 的 `run`／`dev` 靠 uvicorn 默认值；Tauri 显式 `--host 127.0.0.1`（`client/src-tauri/src/main.rs::spawn_agent`）。⚠️ **`config.server.host` / `port` 无消费点** ⇒ 改 yaml 既放不开也收不紧 | 由 Nginx 反代对外，backend 不直接开公网 |
| 本地命令 | shell IP 白名单 | `127.0.0.1`/`::1` | 端侧执行（caller_ip=本机）；云端不注册 shell |
| 本地文件 | file_ops workspace 限定目录 | ✅ 已有 | 端侧执行，按设备/会话隔离（配合 `TODO.md`「会话指定工作空间」） |
| 命令安全 | ShellTool 黑名单加固 | 字符串包含匹配可穿透 | 随本地能力下沉升级正则/词法解析（端侧执行器，云端不注册 shell） |
| 凭据 | config.yaml 不入库 | ✅ 已 `.gitignore` | 保持；云端用环境变量/独立配置文件注入 |
| 数据 | SQLite/ChromaDB 落云厂商磁盘 | 本机 | 明确"数据落云"风险已知 + 定期备份 |

### 5.1 鉴权机制定性（✅ 已定原则）

- **形态 = Bearer ＋ 对称共享密钥**：客户端与后端持有**同一把** key，请求头带 `Authorization: Bearer <key>`，后端逐请求比较。⛔ 不是 SSH、不是 JWT、不含签发／过期／会话态语义。
- ✅ **`Bearer` 不配 `TLS` 等于没设**：明文 HTTP 下 Bearer 头随请求裸奔，被截即被复用。**两者是一对硬前置，⛔ 不得单独落一侧**（上云 checklist 里同一条的两个面）。
- ✅ **闸门只挡 `/api/`**：`backend/middleware/auth.py::AuthMiddleware._do_dispatch` 对非 `/api/` 前缀直接透传 ⇒ **`/health` 永不鉴权，属契约而非疏漏**（Tauri 壳启动依赖 `/health`；复算：`git grep -n 'startswith("/api/")' backend/middleware/auth.py`）。⚠️ 该契约下 `client/src-tauri/src/main.rs::health_get()` 的手写 `TcpStream` HTTP 解析**不需要配钥匙**；若将来加 HTTPS／反代，那段手写解析须重估。
- ✅ **空 key 分支的行为**：`config.server.api_key` 为空 ⇒ 完全透传（本机不校验）。这是**代码分支**，⛔ 不是现态陈述。⚠️ 有一条"把该分支改成仅放行回环来源"的结构性方案**尚未裁决** ⇒ 见 `TODO.md`〈延后〉段，⛔ 本文件不写成定案。

### 5.2 边界口径（✅ 已定，2026-10-29 更新）

上表「网络暴露」与「鉴权」两行合起来看，结论是——**监听地址没有配置通道（`server.host` 未被消费），所以 `server.api_key` 是唯一与部署形态无关、且随时可生效的闸门**。

> ✅ **已裁（2026-10-29 甲案）：dev 上锁 ＋ 配发钥匙，同日已落地并复验闭环。**
> **落地内容**：`backend/config.yaml` 的 `server.api_key` 已设（43 字符），`client/.env.local` 的 `VITE_API_KEY` 同值（值不经任何 AI 通道），`api.ts` 全部 15 处 fetch 经 `authHeaders()` 带证。
> **硬约束（⛔ 原「设与不设对本机行为无差别」的说法作废）**：设 key **必须与客户端 Bearer 注入同时落地**，否则 `/api/` **全 401**。中途只上锁不配钥匙 ⇒ dev 直接不可用（本次实测留档，见 `archive/roadmap-history.md`〈2026-10-29 办结〉段）。
> **复验读数（WB 2026-10-29 自建临时实例独立复跑，不采信完成声明）**：无 header **401** ／ 真 key **200** ／ 错 key **401** ／ 无 `Bearer` 前缀 **401** ／ `/health` **200** ／ `/chat.html` **404** ／ 单测 **90/90** ／ `vue-tsc` exit 0 ／ Vite 已注入 `VITE_API_KEY`。

### 5.3 前端出口唯一（✅ 已定原则）

- ✅ **前端只许一个出口**：不管套不套壳、套几层，对外是一个整体（老大 2026-10-29 定原则）。
- ✅ **`client/chat.html` 已退役并删除（2026-10-29）**：它是 391 行调试页、自带**第二套 `fetch` ＋ 第二套 SSE 解析**，功能被 SPA 完全覆盖。给它"配钥匙"＝维护两套 UI 的鉴权、将来设置页要做两遍 ⇒ 正是「一个出口」要防的事，故**删除而非兼容**。
  - 依据：`HUMAN.md`〈本项目需要坚持的原则〉「临时调试、测试、验证用的小 DEMO …不得为保住它而调整产品设计；须放在能整体删除的位置，不进构建产物、不注册路由、不共用产品出口」。
  - 复算：`git grep -n "chat\.html"` 只剩 `exchange/` ／ `archive/` 的历史表述；`main.py` 无 `FileResponse` 托管路由；`curl /chat.html` → **404**（⚠️ 若非 404 即路由没摘干净）。
- 🔒 **第三处出口的边界（本轮不动，⛔ 不是待办）**：`client/src-tauri/src/main.rs::health_get()` 手写 HTTP 解析属**健康检查**、不是业务出口，跨语言无法共用代码，受 §5.1 的 `/health` 契约保护。

### 5.4 安全观与 CVM 判定

- ✅ **安全观**：key 价值低，真正风险是**数据混染**与**能力错位**。上云后最危险的不是"key 泄露"，而是"云端 backend 误以为在操作用户本机"。隔离的重心放在**能力边界清晰化**，而非堆叠复杂密钥管理。
- ✅ **CVM 判定（老大 2026-10-29 认可）**：**CVM 不是下一个落点，只在「上云」那一刻成为落点**；不在当前这条线上，**不阻塞**。云机上**没有 `/api/` 这个面** ⇒ 那把 key 空着**没有暴露面**，不是隐患。
  - **依据（🟡 文档推定，⛔ 非实测）**：① `docs/production-env.md` §12.7 表载现役 `backend` 凭据载体为 `backend/config.yaml`、跑在**本机**；② 云机跑的是 DSH／harness 探针（S0 环境裁定「CVM 单跑」）；③ 上云未做——`TODO.md`〈部署调试试运行〉段「本地 → 上云 server」未勾，退出条件未达成。
  - **唯一会把它变成阻塞的路径**：有人把 `backend/` 搬上云机、或反代过去。**该动作现在不会自动发生**（`make dev` 在本机、uvicorn 默认绑 `127.0.0.1`、`config.server.host` 无消费点）。
  - ⚠️ **证据等级**：本判定为 🟡。**要升 🟢 需一条 ssh 只读探针**（`ss -lntp` 查 `:8000`／`:3000` 监听 ＋ 看云机目录实况），**需老大批出站**、当时未跑 ⇒ 登记在 `TODO.md`〈延后〉段按触发处理，⛔ 不因此把判定写成实测。
