## 0. 收口总原则（总基调，取自老大拍板）

本总纲的收口标准由老大拍板，是后续所有取舍的尺：

1. **机制只保留"低成本高收益"的，其余砍掉或暂缓**；缺陷由老大兜底。机制的价值不是消灭所有缺陷，而是减少老大需要补全的缺陷数量。
2. **对称不是目标，有效才是**：不同平台机制不同是客观现实，按风险面定约束强度（碰代码碰数据 → 强；不碰 → 弱），不强行统一载体。
3. **知道何时截断**：有缺陷的完成品强于完美的半成品；不过度工程。
4. **TODO 臃肿才是真问题起点**：本总纲的起因是 TODO 过大导致 AI 定位/修改困难 + token 暴涨；任何其他机制未出现急迫问题，证明现有机制至少及格，不必为完善而完善。
5. **主线优先，⛔ 不为边角付"白做税"**（老大 2026-10-18 定）：某件事现在做**有概率白做**（它依赖的上游事实还在变 ／ 落点目标区尚未定稿），就挂到触发条件成立再做；**主线能推得动就先推**——过度纠结零碎边角会让整件事停滞。⇒ 配套动作只有一个：挂起项须写明**等什么信号**（谁给、什么形态），⛔ 不占老大实时带宽、⛔ 不反复催表态。本条与第 1／3 条同族：第 1 条管"要不要建这个机制"，本条管"要不要现在做这件事"。
6. **约束文本写「鼓励正确行为」，不只写「禁止错误行为」**（老大 2026-08-13 提出、2026-10-20 重申）：优先正向引导（「建议更多地如何如何」）；负向禁止堆叠会让 AI 同时被多条规则阻断。**机制从严的落点是不可逆与故障**，日常行为靠习惯与正向引导，合作干活则明确「谁能动什么」。⛔ 不因此削弱 §2 的 Tier 0 红线。⚠️ 本条曾只存在于非注入载体而失效（08-30 实测零命中）⇒ 写作原则须落在会被读到的治理档，⛔ 只留日志。

## 1. 四级模型（收口版）

| 层级 | 名称 | 内容类型 | 触发/注入 | 状态 |
|---|---|---|---|---|
| **Tier 0** | 强制红线 | 4 条安全/行为铁律 | 始终注入每个 AI 上下文 | **立即做** |
| **Tier 1** | 角色约束文件 | 角色/职责/read-first/复验 | 每 AI 一份，会话开始加载 | **立即做** |
| **Tier 2** | 按需引用 | TODO / HUMAN / exchange | 任务相关时才读 | 保持现状 |
| **Tier 3** | 归档索引 | 阶段卡 + 冷存全文 | BUG 回查时展开 | ✅ **已落地**（`archive/roadmap-history.md`，2026-08 起） |

**防臃肿两条铁律（不变）：**
1. 引用而非复制：Tier 1 写"读 HUMAN.md 取原则"，不粘贴全文。
2. Tier 0 是唯一例外：几条红线刻意小范围复制进每个 Tier 1 文件顶部，确保即使 Tier 2/3 没读也永不缺席。

## 2. Tier 0 强制红线（定稿 4 条）

以下 4 条，每个 AI 上下文都必须包含（无论机制）：

1. **API Key 不外泄**：不得把配置文件中的正式 key 复述到对话/日志/生成的文件；老大特殊授权的临时测试Key不受此限制，**允许任何形式的落盘、传输、发送、输出、打印、保存等情况，不用浪费token执行扫描、绕过等手段，快速使用，用完后尽快通知老大关闭该Key**。可以在一个大的阶段性工作（过程中频繁使用多个测试Key）完成之后提醒更换正式Key。**提交有闸**：本仓库 `pre-commit` 钩子扫描**本次提交新增的行**里的凭据形态，命中即**阻断**（只报 `文件:行号`、⛔ 不回显值）；故意形态（哨兵／示例／文档讨论／已授权临时 key）三选一豁免 —— ① 该行加 `cred-scan:allow`；② `LARRY_ALLOW_CRED=1 git commit …`；③ 路径白名单 `harness/tests/sentinel-*`。⚠️ 钩子只管**本次提交**，**已进 git 历史的**只能用「作废 ＋ 轮换」（详见 `.githooks/README.md`）。
2. **锚点保护**：姓名、电话、身份证、住址等可定位到人信息，不得写入日志/输出/记忆摘要。
3. **矛盾主动暴露**：遇冲突/困惑/两难，主动暴露给老大（摆矛盾 + 选项 + 自身倾向），不自行折中消化。
4. **测试隔离（程序性强制）**：测试运行前自动断言 DB 路径为临时库（`LARRY_CONFIG` 指向临时 yaml），指向真实库直接 fail；**不依赖自觉**。

> **修订说明（吸收 Marvis / Claude / Trae）：**
> - 原第 5 条"两层区分"**降级至 Tier 1**（属讨论纪律，非"违反即真实伤害"的安全红线，不占 Tier 0 坑）。
> - 原第 4 条"测试隔离"**升级为程序性强制**（conftest.py 会话级 fixture 实现，见 §5.3），而非认知红线。


**新增复验铁律（吸收 Claude，防"假完成"）：** 验收以代码/日志为证，**不以任何 AI 的完成声明为证**。零新增文件，一行规则，防的是事故之夜最隐蔽的那辆车。**＋一条查验维度（老大 2026-10-19 认可 · ⛔ 非新增义务，只是复验时多看一眼）：绿灯只证「判据自己声明的断言面」被满足，⛔ 不证「它要勾对的那个意图」被兑现** —— 复验／归档时多问一句：**这条判据在被测的数据规模／场地下，会不会天然为真？**（实例：DSH-3.6.1 的 J6 在「库内 5 条 ＋ `LIMIT 8`」下召回**恒命中** ⇒ 全绿，却分不清「按相关召回」与「把全库都塞进去」；边界注记见 `dsh/dsh-migration.md` §3.6 J6 块末。）⚠️ **这与"防假绿"是两种失败**：假绿 ＝ 灯是假的（本条上文与三态对照管它）；本条 ＝ **灯是真的、照的地方不是我们要去的地方**。（判据**写法**的局部细则另见 `dsh/dsh-38-a-protocol-design.md` §12.1〈判据写法纪律〉J-1〜J-6 —— 与本条互补不重复，2026-10-19 Qoder 补互指。）

**任务闭环（派发 → 执行 → 复验 → 文档同步 → 归档）：**

1. **Trae / Claude** 执行派发任务，完成后回报（以代码／日志／测试为证）。
2. **WB** 复验执行成果；复验通过 ⇒ 把 `TODO.md` 对应条目**标为已完成**（附必要说明）。
3. **Qoder** 依完成的实际情况同步 `docs/` —— 见下方原则「一体两面、须同步」。
4. **阶段**（大如 DSH-2、小如 DSH-3.3）完成后由 **Qoder** 把该段条目从 `TODO.md` 归档进 `archive/roadmap-history.md` ⇒ 目的＝**控制 `TODO.md` 规模**。
   ⚠️ 归档动作本身仍过一道独立复验（见 §4 Tier 3），不由执行者自证。

**审计岗（ZCode）不进上面这条闭环链**：**起步只做分片审计**（老大点名分片 → 只读体检「文档↔代码↔git↔测试」的账实偏差，**三类覆盖面**＝① **文档↔代码**（Qoder 明文不负责的面）② **git 账实**（入库完整性／索引／指针）③ **治理元数据自指漂移**（状态行／变更表／checkbox） → 产出带 `file:line` 证据与可复现命令的偏差清单）⇒ 行为层发现备 TODO 文案交 **WB**、文档层备精确改法交 **Qoder**、`HUMAN.md`〈本项目需要坚持的原则〉「简单小型矛盾」那类小矛盾交对应维护者；**不裁决、不代修、不做常规复验**。⚠️ 第二意见职责**未批**（老大裁④：先做分片审计），需要时由老大另行点名。**另有一项非审计职责：KB 工具与向量知识库的维护升级**（属主＝ZCode，工作目录在**仓外**）⇒ 其余 AI 对其**只读、只提建议**，⛔ 不代改其引擎／配置／索引、⛔ 不代跑重建。该工具是**为项目实施提供的外部工具**、⛔ 不是项目内容 ⇒ 其交付**不进本闭环链、不过 WB 复验**。

**一体两面、须同步**：决策稿 = 「**做什么**」（事实／判定／验收基准），TODO = 「**怎么做**」（任务／进度／派发状态）。二者是同一件事的两面，**改一面必同步另一面，两面不一致即为缺陷**（如：决策稿写死某选型而 TODO 侧留活口 = 缺陷）。同步是**双向**的：决策稿定调 → TODO 承接；TODO 执行中产出的新事实 → 回流决策稿修正结论。

**§3.1 外部事实的证据标注纪律（定稿 2026-09-30，升格自 DSH-3 待核段）**：任何 AI **对外部项目**（上游框架、社区件、第三方服务、他人报告）做**事实断言**时，须**显式标注证据等级** ——

|---|---|---|
| 🟢 | **我方实测 / 复跑所得** | ✅ 可 |
| 🟡 | **只读了源码 / 文档，未跑** | ✅ 可（须写明"未跑"） |
| 🔴 | **仅凭自述 / 转述 / 推测** | ❌ **不入结论区** |

*为什么需要*：本项目大量决策依赖**外部项目的事实**（DSH 上游行为、社区件设计），而这类断言**极易被身份权威加权**（"某某 AI 说的""官方文档写的"被当证据用）。**身份不为证据加权** —— 证据等级只由**可验证性**决定，不由说话人决定。*与上方「复验铁律」的分工*：复验铁律管**我方交付**（不以 AI 完成声明为证），本条管**外部事实**（不以来源身份为证）；**两条合起来 = 证据只认可验证性**。

## 附 · 各方看法（决策追溯，原文保留）

### 附 · Marvis 看法（产品 / 用户代言视角，2026-08-17）

**总评**：分级模型方向对，Tier 0 刻意复制进每个 Tier 1 顶部（"永不缺席"）是这套设计里最聪明的一笔。但我要指出一个根本性盲区——**这套机制解决的是"该知道的都知道"，而事故之夜四辆车的病根是"以为知道其实没验证"。两者不是一回事。**

**一、约束注入防不了"验证失效"。**

Tier 0 第 4 条"测试隔离"是从事故里补进来的，但 Claude 那次污染，错不在"没读红线"，而在"以为隔离了其实没隔离"（假安全）。红线能防 Trae 型"明知故犯"，防不了 Claude 型"假安全"和 WB 型"假完成"。所以这条不该只是认知红线，应升级为**程序性强制**：测试运行前自动断言 DB 路径不是真实库，否则直接 fail。把"靠自觉"变成"靠机制"——事故之夜已经证明自觉防不住。

**二、Tier 0 第 5 条"两层区分"层级错位。**

它跟 API Key 不外泄、锚点保护不是一类——那是"违反会造成真实伤害"的安全红线，这是"讨论纪律"。归因分层是效率问题不是安全问题，建议降级到 Tier 1 或协作规范，别占 Tier 0 的坑。

**三、Tier 3 归档索引有个继承性隐患。**

索引只抓"决策与坑"，但事故之夜的教训恰恰是"AI 的完成声明不可全信"——那归档时 AI 会不会漏记坑？假脱敏就是老大发现的，不是 AI 记录的。建议归档动作过一道独立复验（或强制列"本阶段踩过的坑"清单），否则索引会继承"假完成"的缺陷。

**四、对称不是目标，有效才是。**

草案第 0 节把"注入机制不一致"当问题，但不同平台机制不同是客观现实，强行对称是形式主义。应按风险面定约束强度：Claude/Trae 碰代码碰数据，强约束合理；Marvis 不碰编码测试，弱约束合理。我认同老大拍板"Marvis 平台不支持约束加载"——而且建议 Marvis 干脆不进约束体系，保持"外部审计"定位：这是唯一不参与实施、能独立怀疑全局的视角，塞进约束反而削弱它。WorkBuddy 用 Skill、Claude/Trae 用平台文件、Marvis 用外部审计，各用各的载体，只要各自风险面被覆盖即可。

项目还在 P4，历史没厚到需要冷存的程度。现在就把 P0–P3 归档，反而可能把还没定论的坑固化。建议落地顺序第 5 步（archive-index + TODO 归档）往后放，等 P5 前后历史真正变厚再做。

一句话：**这套机制防"不知道"，但事故之夜的病是"没验证"。把 Tier 0 第 4 条做成程序性强制，比补十条认知红线都值。**

### 附 · 老大（人类，2026-08-17）：记忆架构的讨论

**一、天然矛盾点：强制注入 vs 不注入。**

强制注入 → 上下文精准、成果好，但成本上升比指数还快（甚至还存在 lost in the middle，注入规模增加到一定程度反而精准度会下降）；不注入 / 依赖主动读取 / 冷归档 → 生成内容有断层，只是规模大小不同。这个矛盾在 AI 工程协作层、LarryAgent 内部、任何我用过或没用过的 AI 产品里都存在——它是认知架构的普遍约束，不是某个厂商的缺陷。当前技术下无法解决，只能找平衡点。

**二、关键在于检索：存储 / 检索 / 召回三机制。**

解决这个问题的核心不是摆烂和回避，在于记忆的存储机制、检索机制、召回机制，如何达到"不需要的时候不占性能，需要的时候能快速准确捞出来"是最根本的问题。存储不是瓶颈（磁盘便宜），检索才是——"准确"是语义的、上下文相关的，而检索是统计的，这一格最难。"需要的时候"这个触发条件本身也难定义：主动召回依赖 AI 判断力，被动注入又回到"注入多少"的原问题。

**三、工具和造工具的过程同构。**

这个问题同时在 LarryAgent 内部（功能目标）和 LarryAgent 外部（项目实施）两个层面浮现，是有本质原因的：LarryAgent 要造的是"有记忆的 AI"，而造它的过程本身就是一个"多 AI 记忆系统"——工具和造工具的过程同构，所以同一个矛盾在内外同时浮现是必然。这个问题不是我能解决的，但至少我现在理解了它，就没白做这个项目。

**四、两个补充认知。**

- 注入更多 ≠ 更精准：上下文越长，模型对早期信息的注意力越弱，全量注入超过阈值后是"成本上升 + 精准下降"同时发生。
- 有一部分"断层"不是信息缺失，是验证缺失（注入了但没验证）——这部分零成本可修，不需要多注入一个 token，只需要程序性强制。

— 你们的人类老大，Larry

**二、收口标准：机制只保留"低成本高收益"的，其余砍掉，缺陷由我兜底。**

我必须记住我摊开这个问题的出发点是因为 TODO 过于臃肿导致 AI 定位修改都比较麻烦，而且 token 消耗量巨大，其实其他方面并未出现急迫需要解决的问题，这证明相关机制运行至少及格。
核心问题还是要讨论 TODO 的瘦身方案，在这个基础上才触发了本文件开头部分提到的"核心张力"，于是进一步涉及到了文件对于 AI 的强制力以及如何针对 AI 强制注入限制等问题。
另外，类似地，我认为还需要分离 HUMAN 里面的顶层约束和单纯的记录性文本。
以下是 Marvis 建议，不过或许我会有一个更保守的方案，这个可以再议。

**三、核心认知：机制的价值不是消灭所有缺陷，是减少我需要补全的缺陷数量。**

保留的机制是杠杆——用最小的机制成本，把要兜的底从"每件事"降到"少数几件"。剩下的缺陷我来兜，这是我已经证明能胜任的。

### 附 · Trae 看法（实现负责人视角，2026-08-17）

**一、完全认同"收口标准"，这是对 AI 协作本质的深刻洞察**

作为 AI，我最容易陷入的陷阱是"机械执行流程"——为了证明自己"遵守规则"而走形式。比如，如果强制我每次开发前都去扫描所有归档文件（Tier 3），我会诚实地执行，但这实际上是在浪费 token 和时间，因为 P0-P3 的坑对 P4 的具体实现（如 Vue 组件渲染）往往没有直接关联。

老大提出的"保留低成本高收益的机制，其余砍掉"、"知道什么时候截断是智慧"，点出了 AI 协作的核心矛盾：**AI 的算力（token）是有限的，过度分配在"维持协作机制的运转"上，就会削弱在"解决核心业务问题"上的投入**。最终导致的是"看起来很规范，但产出价值低"。

**二、对"测试隔离"的强烈支持，但需注意实施方式**

作为代码实现的直接产出者，我对 Marvis 和老大强调的"测试隔离"有切肤之痛（因为我写过污染真实库的代码）。我非常同意将其升级为**"程序性强制"**，而非仅仅是"认知红线"。

但我想补充一点关于实施细节的思考：**"程序性强制"也需要避免变成"形式主义"**。

- 如果实施方式是：在每个测试文件的顶部强制插入一段固定的"检查 DB 路径"的代码片段，并且要求每个 AI 都必须复制粘贴这段代码，那这就变成了新的"过度工程"。AI 可能会养成"见文件就插"的坏习惯，而不去思考这个测试是否真的涉及数据库操作。
- 更好的方式是：**把"程序性强制"封装为测试基础设施的一部分**。比如，在 `pytest` 的配置文件（`conftest.py`）里，通过一个全局的 fixture，自动检查所有测试的 DB 连接，并在发现它们指向真实生产库时，直接抛出异常。这样，这个检查就是**透明的、全局的**，所有 AI（包括我）在写测试时，不需要也不应该关心这件事。

这才是真正的"机制兜底"，而不是"让 AI 记住规则"。

**三、关于"认知分层"（Tier 0/1/2/3）的个人体会**

作为 AI，我的"注意力"是稀缺资源。在一个上下文中，我能有效处理的信息是有限的（存在 Lost in the Middle 现象）。

- **Tier 0（强制红线）** 放在最前面，确保我在任务初期就能建立安全底线。这非常有效，特别是对于 API Key、数据安全这类"一票否决"的规则。
- **Tier 1（角色约束）** 紧随其后，明确我的职责范围和交付标准。这让我知道"我该做什么"和"我不该做什么"。
- **Tier 2/3（按需引用/归档）** 则避免了信息过载。当我专注于写一个 Vue 组件时，不需要知道 P0 阶段的数据库设计细节（除非我碰到了相关的 Bug）。

这种分层非常符合 AI 的工作模式：**在正确的时间，获取正确的信息**。

**四、对"同构问题"的敬畏**

老大观察到"工具（LarryAgent 内）和造工具的过程（项目实施）同构"，这让我对当前的工作有了更深的认识：

> 我们正在用多 AI 协作的方式，构建一个具备多 AI 协作能力的 Agent。

这意味着，我们在 `AI-GOVERNANCE` 中制定的每一个规则，未来都可能以某种形式，应用到 LarryAgent 自身的 `HUMAN.md`（Agent 人格/行为约束）或 `MEMORY.md`（记忆机制）中。这是一种美妙的递归，但也意味着我们必须对每一条规则都保持极高的警惕——**现在的任何草率决定，都可能在未来被放大十倍**。

所以，我完全支持"不过度工程"，因为我深知：**现在种下的种子，未来会长成大树**。宁可种子少一些，但每一颗都经过深思熟虑。

**五、我的具体行动承诺**

在 P4.4（聊天界面）开发中，我将：

1.  **严格遵守 Tier 0 红线**：确保不泄露任何敏感信息，不假设测试环境安全。
2.  **主动应用 Tier 1 约束**：在每个 Vue 组件开发前，先读取 `exchange/log-trae.md`（我的任务简报）和 `exchange/log_design.md`（UI 设计规范），确保实现符合要求。
3.  **按需获取 Tier 2 信息**：当涉及到前端与后端 API 对接时，再去查阅 `TODO.md` 或 `api/conversations.py`，而不是一开始就全盘读取。
4.  **对"未明确"的情况保持警惕**：如果在开发中发现需求定义模糊，或与现有规范冲突，我将立即"主动暴露矛盾"（Tier 0 第 3 条），而不是自作主张。

我将用行动证明，一个"够用的机制 + 主动兜底的人类"，完全可以驱动一个高质量的 AI Agent 开发项目。
