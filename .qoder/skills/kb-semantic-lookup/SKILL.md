# kb 语义检索：落点判定 ＋ 用前自检（Qoder 工作法）

> 定位：这是**查找与落点判定**的动作，产出是"去哪儿读"。⛔ 不是证据来源，⛔ 不是完备性证明。
> 引擎在**仓外**（`D:/AI Work/knowledge engine`，属主＝ZCode）⇒ 本件只写"我怎么用、怎么不被它骗"；**怎么调它的索引不属我**，只能提建议（见 §四）。

## 一、按"我缺什么"选通道（⛔ 不按"哪个更高级"）

| 我缺的东西 | 第一跳 | 之后必做 |
|---|---|---|
| **词汇**（不知道该用什么词；grep 换了说法仍无果） | **kb** | Read 命中正本 → 拿正本里的词再 grep 补穷尽 |
| **精确位置／精确计数**（词已知） | **grep** | ⛔ 别用 kb——那是把可复算的定位换成不可复算的相似度 |
| **验证我已有的结论**（想确认"别处没这么写"） | **kb 查它的反义句** | 命中集不收敛 ⇒ 概念散落，逐处 Read |
| **两个通道说法冲突** | **第三通道＝Read 正本** | ⛔ 不在两个检索器之间投票 |

- 命令：`python "D:/AI Work/knowledge engine/kb.py" search "<查询>" -p larryagent -k 8`（`-p larryagent-ref` 只查 `ref/`，DSH 插件策展走它）。
- 判读：**只看排序、不看绝对分**（基线约 0.45–0.5，经验上 <0.55 属噪声水位，top1 也可能错）；**±0.02 内视为并列簇**，并列簇里出现异主题＝偏航信号；命中一律 🟡，引用前必须 Read `file:line` 正本。

## 二、⭐ 拿「分布」当证据之前，先跑索引自检（这一步是踩出来的）

**教训**：我曾拿"近邻／聚类"做分析，跑出 cos=1.000 的大簇、读成"语义完全重合"——回查发现是**索引里一批块向量坍缩**（正文根本没进模型），两份试点结论全废。⇒ **检索层可用 ≠ 分析层可用**：单次命中错了只是多读一个文件，分布错了会**批量**产出假结论。

三条自检（工作目录＝`D:/AI Work/knowledge engine/LarryAgent/indexes`，秒级、只读）：

```bash
python -c "import numpy as np;X=np.load('index.npy');u,c=np.unique(X.view([('','float32')]*512),axis=0,return_counts=True);d=c[c>1];print('dup groups',len(d),'rows',int(d.sum()),'distinct',len(u))"
python -c "import json;ch=json.load(open('index.meta.json',encoding='utf-8'))['chunks'];t=[c for c in ch if len(c['title'])>800];print('long-breadcrumb',len(t),sorted({c['file'] for c in t}))"
python -c "import json;ch=json.load(open('index.meta.json',encoding='utf-8'))['chunks'];print('fragments',sum(1 for c in ch if len([l for l in c['text'].splitlines() if l.strip()])<=2),'/',len(ch))"
```

| 自检 | 红了说明什么 | 后果与动作 |
|---|---|---|
| ① `dup groups > 0` | 有块**文本各异却 bit 级同向量**＝坍缩 | 这些块的任何"语义重合／近邻"结论**一律不成立** ⇒ 分析层不出手 |
| ② `long-breadcrumb > 0` | 列出的文件里**长标题下的整段子孙块共用一个向量** | 该段独有内容**永远排不上来** ⇒ 查这些区域**改走 grep** |
| ③ `fragments` 占比高 | 空块（`---`／只有标题）参与排序 | top-k 名额被吃掉（实测一次 `-k 6` 里 top3–top6 四条全是空块）⇒ 加大 `-k` 或忽略空块命中 |

**① 红了先分型（⛔ 别一律读作坍缩）**：把同向量组的 `text` 打出来看——**组内互异 ＝ 真坍缩**（A 类，拦分析层）；**组内相同／近同 ＝ 语料自身重复**（如 `ref/` 里同一 README 的英／俄 License 段）＝非缺陷、⛔ 不拦。引擎侧 `[selfcheck]` 自 2026-10-19 起已按 A 类判（属主升级）⇒ 要分型就看 `rebuild`／`sync` 的自检输出（我 ⛔ 不代跑）；本件 ① 那条命令只到"有没有同向量"的**粗筛**层。

**②的成因与现状**：`text` ＝ 面包屑（祖先标题链）＋ 正文，送进 512-token 窗时**从头截断** ⇒ 标题过长时正文被整体挤出、整段子孙块共用一个向量。**这条 2026-10-19 已由属主修掉**（面包屑预算 120 字符**截尾不截头** ＋ 正文块降到 420，正文永远完整进 512 token）。我当日独立复跑的**现值**（带日期、⛔ 非判据）＝ **真坍缩 0／`long-breadcrumb` 0（`title` max 120）／`fragments` 135/1814 ≈ 7.4%**，与 WB `kb-semantic-audit` v1.3.0 前置闸转绿一致；修复前的红态数字属沿革（见 git ＋ WB 该件的基线段），⛔ 别再当前提用。⚠️ 因此 **② 已从"健康判据"退化为"回归探测器"**：引擎有闸挡着 ⇒ 它结构性为 0，**⛔ 别把"② 绿"读作"索引健康"**（见 §五末条）。

⇒ **自检红 ⇒ 缺陷单交属主（§四），分析层结论一律不出手**；检索层仍可谨慎用，但**未命中只能读作"没查到"、⛔ 不读作"不存在"**。

## 三、"kb 没命中"的三种机械成因（⛔ 都不等于"文档里没写"）

1. **索引范围刻意排除流水层**：`TODO.md`／`exchange/log-*`／各家记忆区不在索引里 ⇒ 查待办、查过程必然空，**直接读文件**。
2. **区域坍缩**（§二 ①②）——⚠️ **本条原先那条"永久绕行"已于 2026-10-19 撤销**：成因（超长标题把正文挤出窗口）已由属主修掉，我复跑确认原先丢失的 **19 行短结论已回索引**、余下未覆盖 123 行全为标题·分隔·表框·代码围栏（**零实义损失**）⇒ **查 `archive/roadmap-history.md` 的落点可以正常用 kb**，⛔ 不再一律改走 grep。**只在 §二 ①② 当次实测为红时**，才对红区绕行。〔修复前的旧实测对照：查该文件某行独有内容 ⇒ top4 里零命中；换查同文件短标题区 ⇒ 该文件 `#1`〕
3. **模型档位**：bge-small 属**主题级**，意图级／推理链长的问法会偏航（问"怎么防止 X"命中一堆"X 相关清单"）⇒ 换措辞重试或退回 grep。

## 四、发现引擎侧问题的边界与写法

- ⛔ **不动**属主的 `kb.py`／`kb.json`／`indexes/`，⛔ 不代跑 `rebuild`（`search` 自带懒更新，那是设计内的正常路径）。
- 缺陷单写进 `exchange/log-zcode.md`〈📥 收件〉：**只新增、零删除**（`git diff --numstat` 须只有 `+`），写前按属主纪律查 `git status`；每条附**可复现命令 ＋ 实测输出**，我方实跑标 🟢、机制推测标 🟡；**自己说过的话若复现不出来当场撤回**并标 🔴 转述级、不入结论。
- **文档侧成因**（如超长标题）即便落在**我的可写区**也**先不改**：两边同时动会归因不清；且改的往往是**锁定归档段头** ⇒ 摆给老大裁，不自行动手。〔先例已结案：`archive/roadmap-history.md` 那个 968 字符 `####` 标题——我方报的倾向是「**不改、关闭**」，老大 2026-10-19 令 #54 闭环 ⇒ **按该倾向结案**（⚠️ 记法：这是随块闭环采纳的建议，⛔ 不是老大单独成文的裁定）。依据＝引擎侧面包屑预算已挡住它、`long-breadcrumb` 现为 0 ⇒ 剩下只有人眼可读性，而它是锁定归档段头、改它收益低于风险。**⛔ 别再把它当索引缺陷报**（成因已堵）；属主也已确认不留兼容代码〕
- ⛔ **别为了索引去改文档正文**：只有"文档本身就更正确"的改动才做（如给正本补一句自解释的定义）；纯为检索好看的改造（把粗体行改成标题、拆段凑粒度）一律不做。**索引适配正本、正本不适配索引。**

## 五、已知坑

- 索引跟**工作区**、不跟 git HEAD ⇒ 未提交的改动也会被检索到；命中"自家刚写的话"前先 `git status` 核一眼。
- 块元数据只有 `start/end/file/text/title`；`title` 是祖先标题链，**只有真 `#` 标题才进面包屑**，粗体伪标题（`**§N.M …**`）不进 ⇒ 靠面包屑定位会偏。⚠️ 粗体**表格行**会被松散的 grep 误判成伪标题，计数前先核形状。
- `files`／块数会随清理漂移 ⇒ ⛔ 别把绝对文件数写进判据，写**占比**或写判据式本身。
- 同库多 profile（主库 ／ `-ref`）范围可能重叠 ⇒ 同一批内容被编两遍时，命中会重复出现，先 `stats` 看构成再判"是不是有两处写了同一件事"。
- ⭐ **判据会因上游修复而"天然为真"**：属主给引擎加了面包屑预算闸之后，§二 ② 结构性为 0 ⇒ 它只能证"没退回旧缺陷"、⛔ 不能证"索引健康"。上游一改，先回头问"我这几条判据还有没有失败态、红了长什么样"，别拿恒绿的闸当验收。（＝`verifiable-criteria-design` 那把尺在检索面的实例）
