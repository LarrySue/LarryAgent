# 职责与口径变更后的治理同步（工作法）

> 适用：分工变了（例：文档区从甲转给乙）、原则新立或改口径、权限边界重画。变更本身一句话，**没同步的治理文本会持续误导下一个读者**。

## 一、扫描面清单（逐处 grep 旧口径，别靠记性）

1. 根 `README` 的角色分工段 ＋ 各区 `README`（文档区／归档区／交流区）的「维护方」行。
2. 各讨论稿头部的「主持／定稿」行（若稿件换了主人）。
3. 各 AI 的**约束文件**（`.claude/` `.trae/` `.qoder/rules` `.workbuddy` 等）⇒ ⛔ 不由我改：列进「待老大／待本主自改」清单并**备好可粘贴文案**。
4. 权威落点本体（例：治理原则入 `docs/ai-governance.md`）；其余位置只留**指针**，不复粘全文。
5. 工具层残留：协作方自己编了旧分工的 skill／脚本／模板；已在旧口径下的待办条目。
6. 自己区的状态行／职责段（否则下次开工时没人知道口径已变）。

## 二、「只写当前职责」写法（进上下文的文件适用）

- ✅ 写：现在谁负责什么、流程怎么跑、现状事实。
- ⛔ 不写：交接（“由 X 移交 Y”）、时间点（“2026-XX-XX 补／订正”）、历史状态（“原产…”）、**授权来源**（“老大裁定／老大要求／本次不代决”）。
- 沿革只去两个地方：`git log`，以及**本身就是变更记录表**的章节（如某文档第 4 章）。
- 原则表述拿**权威原句**（口语转写会漏环）；不确定先向定义者复述一遍对一下。

## 三、归属分流（防止把别人的动作写成自己的）

- 拆两层：**权限边界**（谁能改哪个区）⇒ 写进约束文件／区 README；**操作流程**（怎么改）⇒ 写进 skill，不进约束文件（约束每轮加载，塞进去吃上下文）。
- 区分“维护文档”与“拍板定稿”：主持人 ≠ 定稿权。定稿判据写清楚（例：其他 AI 无异议 → 去讨论痕迹 → 移入正式区）。
- 区分“标完成”与“同步文档”与“归档”：复验者标待办完成；执行后的**文档面**由文档维护方同步；**阶段归档**也属文档面（不要因为“归档”听起来像协调动作就归给复验方）。

## 四、输出与验收

1. 本轮内一次改完一切**我能改的位置**，合并 commit（pathspec 明列，⛔ 不扫入他人未提交改动）。
2. **我不能改的**（约束文件／他人区／人类文件）：列清单（文件＋旧句→建议句），**附可直接粘贴的文案**，不附长篇论证。⇒ **文案必须落盘进我有写权的区**（一般是我名下 `log-*`），⛔ 不能只在对话里给过就写“文案见某处”——对话不进 git，那句必成断链。
3. 验收 grep：旧口径关键词（移交／原维护方／旧原则措辞）在可写区内应为 0 命中；仍有命中就是没于净。
4. 自己的记忆同步更新（可写区清单／新口径），否则下次开工仍按旧边界行为。

## 五、坑登记

- 把自己要做的流程细则写进约束文件 ⇒ 上下文成本逐年只增；走 skill。
- 只改自己那一份 ⇒ 治理文件互相矛盾（比不改更糟，读者会选错一份）。
- 改口径时漏了“指向该口径的引用” ⇒ 指针仍指旧句，形成静默失活（改完跑一次反向 grep）。
