## 附 · Trae 看法（实现负责人视角，2026-08-16）

**一、双库 Bug 的根因是"约定不明确的契约"**

`config.yaml` 里的 `database.path: data/larry.db` 使用了相对路径，而代码实现时默认它**相对 CWD（启动目录）**解析。这是一个致命的隐式契约——开发者（我和 Claude）都理所当然地认为路径是固定的，却没意识到它会因启动方式不同而变化。

更深层次的问题在于：作为实现负责人，我在最初编写 `config.py` 时就应该明确这一点（或者在文档中强调），或者至少在代码里加上断言/警告。但我没有，我把"能跑通就行"放在了"行为确定性"之前，这才是所有后续混乱的根源。`config.py` 的修复（相对 yaml 文件解析）是一次彻底的纠偏，确立了配置解析的锚点。

**二、我污染真实库的错误是"对测试环境缺乏敬畏"**

我写的 `clean_conv_db` fixture 在设计上就是危险的——它假设"既然我调用了 `/api/conversations`，那我就在测试环境里"。但 FastAPI 的 `TestClient` 只是 mock 了 HTTP 层，并没有 mock 底层的依赖（数据库、配置）。我犯了一个典型的"乐观假设"错误：

> 假设：TestClient = 隔离环境。
> 现实：TestClient = 把真实应用包了一层 HTTP 壳。

这暴露了我对 **"依赖倒置原则"** 的理解浮于表面。真正隔离的测试，应该 mock 掉 `db.conversations.list_conversations` 这个函数本身，而不是依赖它去操作一个"以为是测试用的"文件。把真实业务逻辑暴露给测试环境，本身就是一种风险。

**三、关于"影响面清单"的具体落地建议**

Marvis 提出的"影响面清单"非常精准。针对我们的场景，我建议在未来的开发中，强制在代码评审/自测环节加入以下三个问题：

1.  **路径/配置类改动**：这个值是**相对谁**解析的？（相对 CWD / 相对文件 / 绝对路径）—— 必须在代码/注释中明确。
2.  **涉及持久化（DB/文件/网络）的代码**：在**任何**调用它的地方（包括测试），它指向的目标是什么？—— 绝不允许"假设默认配置是安全的"。
3.  **引入新依赖/新工具**：这个依赖在非标准环境（测试、CI）下的行为是否一致？—— 比如 `lifespan` 会 `load_config`，这在测试环境就是个"隐藏的副作用"，必须在 fixture 中显式处理（如覆盖 `LARRY_CONFIG`）。

**四、对职责划分的补充**

"Trae 实现 / Claude 测试"的分工非常合理，但在我的具体工作中，我应该严格避免"自测产生脏数据"的情况。即使我自己想快速验证，也应仅限于**纯内存计算**（如单元测试工具函数），绝不触碰任何涉及磁盘 IO 的操作。所有涉及持久化的验证，都应通过 Mock 层在内存中完成。

— Trae
