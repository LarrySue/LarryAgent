## 一、BUG 全貌：一个根因，三层影响

**根因（一句话）**：`aiosqlite` 连接绑定到已关闭的 asyncio loop 后，进程退出时 GC 清理必然挂起。

| 层 | 表现 | 状态 |
|---|---|---|
| **表层** | 集成测试进程退出挂起 **17.5 分钟**、退出码 1，而 pytest 报告 "3 passed" | ✅ 已修（`f27c091`） |
| **中层** | 机制不限于测试——任何 `asyncio.run()` 创建的未关闭连接都中招 | ⚠️ **未防护** |
| **深层** | 强杀进程 → `atexit` 不执行 → 含**真实 API key** 的临时目录明文残留磁盘 | ⚠️ **未闭环** |

**为什么配得上"巨大"**：不只是 17.5 分钟。它同时具备**欺骗性**与**机制性**——pytest 报全绿、退出码却是 1（CI 判失败、本地看着像成功）；且根因是通用机制，影响面超出测试代码本身。

---

## 二、表层（已闭环）：测试秒过、进程不退出

**现象时间线**（日志落文件，非管道）：

```
START: 03:27:29
3 passed in 32.66s     ← pytest 计时（测试执行仅 32.66s）
EXIT_CODE: 1           ← 退出码 1！pytest 报 3 passed 但进程异常退出
END: 03:45:31          ← 进程真正退出（= 18 分 2 秒 wall clock）
```

**直接触发原因**：改造 `test_integration_llm.py` 去假绿时，删掉了原脚本式 `run_tests` 的 `close_db()` 调用——`handle_chat` 创建的 `_db` 全局连接泄漏。

**修复**：module 级 autouse fixture teardown 显式 `asyncio.run(close_db())`（WHY 注释已写明根因）。

**验证**：`--real-api` 3 用例 wall clock **18 分钟 → 26 秒**；全套无回归。

**为什么默认跑不暴露**：全套跑时 integration 用例默认 skip，不触发；**仅 `--real-api` 暴露**。这正是"自测觉得没问题"的原因。

## 三、中层（未防护）：机制级，不限于测试

**双环境互证**（Claude 独立实验 G，脱离 pytest 的纯 Python 对照）：

| 实验 | 环境 | 连接处理 | 进程退出 |
|---|---|---|---|
| G1 | 纯 Python（无 pytest） | `asyncio.run()` 建连接后不关闭 | **挂起 120s 超时（exit 143）** |
| G2 | 纯 Python（无 pytest） | 显式 `conn.close()` | **秒过（exit 0）** |

结合 F3/F4（pytest 环境）与 G1/G2（纯 Python）双环境互证 → **这是 aiosqlite + asyncio 的通用行为，与 pytest/pytest-asyncio 无关**。

**产品代码暴露面（WB 独立核查）**：

- `backend/db/database.py` 的 `_db` 单例：懒创建（`get_db`）/ 显式关闭（`close_db`）。
- 全项目 `close_db()` 调用点**仅 `main.py:73-74`（FastAPI lifespan shutdown）一处**——uvicorn 常驻 loop 下安全。
- **风险场景（无防护）**：一次性脚本 / CLI 任务 / 任何 `asyncio.run()` 里调了 `get_db()` 却未显式 close 的入口。这类入口目前产品代码里没有，但**没有任何机制阻止未来出现**。

**原则**：显式管理资源生命周期（连接/loop），不依赖 GC——GC 清理时机不可控且可能挂起。

## 四、深层（未闭环）：Tier0 安全隐患——真实 key 明文落盘

`backend/tests/conftest.py` 以真实 `config.yaml` 为基底生成临时 `config.session.yaml`（**含真实 API key 明文副本**），仅替换 DB/chroma 路径，靠 `atexit` 清理：

```python
# conftest.py:64
atexit.register(shutil.rmtree, _session_tmpdir, ignore_errors=True)
```

**两个缺陷叠加**：

1. **强杀即失效**：`atexit` 在进程被 `taskkill /F` / `timeout` 强杀时**不执行** → 含 key 的临时目录明文残留。本次排查中因反复强杀挂起的 pytest 进程，`/tmp` 残留 **40+ 个 `larry_test_xxx` 目录（含真实 key）**，已由 Claude 全部清除。
2. **`ignore_errors=True` 静默吞失败**：即使正常退出，若文件被占用（如 ChromaDB 持有 sqlite 句柄），删除失败也会被无声忽略，**没有任何告警**。

**WB 独立复验（2026-08-30 04:25）**：跑完一次全套测试（正常退出，非强杀），仍残留 1 个 `larry_test_*` 目录——内含 `chroma/chroma.sqlite3`（188KB）；所幸 `config.session.yaml` 与 `session.db` 已被删除，**本次 key 未落盘**。但目录本身残留证明：`ignore_errors=True` 确实在静默吞异常。

> **矛盾必须摆明**：清理链目前是"侥幸正确"而非"机制正确"。正常退出时 key 恰好先于 chroma 被删，若顺序反转或有其他占用，key 即明文落盘且无人知晓。

## 五、方法论价值：为什么 mock 层永远测不出来

| 层 | mock 层能测 | 真实 key 才暴露 |
|---|---|---|
| 连接生命周期 | ❌ mock 不创建真实 `aiosqlite` 连接 | ✅ 只有真实链路走完 `handle_chat` 才建连接 |
| GC 退出挂起 | ❌ 属进程退出期行为，测试断言够不到 | ✅ 只有实际退出才触发 |
| 资源泄漏累积 | ❌ 单用例短跑观察不到 | ✅ 串行多用例才放大 |

这正是「集成冒烟层」存在的理由（已写入 `.claude/CLAUDE.md` 分层原则）：**它验证的是"接得上、跑得通"，是契约哨兵，mock 层永远够不到那一层。**

## 七、待办（未闭环项，待老大拍板）

1. **清理机制硬化**（建议做）：`atexit` 不可靠 → 改用 pytest `tmp_path_factory` / 会话结束时显式清理并对失败**告警而非静默**；或至少把 `ignore_errors=True` 改为捕获异常并 `logger.warning`。
2. **key 落盘兜底**（建议做）：临时 yaml 写入时可考虑不复制 key（测试用占位符，仅 `--real-api` 时注入），从源头消除"key 明文落盘"的可能。
3. **产品侧防护**（可选，逃熊尺度）：`db/database.py` 可为 `_db` 注册 `atexit` 兜底 close，或文档化"一次性脚本必须显式 close"。当前无实际触发入口，**优先级低**。

> 三项均为"性价比高的最小动作"，非过度工程。是否做、做的顺序由老大定。
