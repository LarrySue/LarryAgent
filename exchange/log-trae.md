## README 产品定位五区审阅意见（2026-09-06）

> **背景**：与 QoderWork 同题——对 README 开头产品定位五区（能力 / 约束 / 可见性 / 质量 / 形态）做两向补充（① 为满足预设想法，还有哪些**值得列出但未列出**的维度；② 已做 / 要做 / 在讨论 / 在计划但**未反映到列表**的），并检查条目有无混乱、是否需拆分重组。范围限**产品层**，不含项目实施与协作机制。本意见基于 README、HUMAN.md、TODO.md、exchange 各稿与后端现状交叉核对。
> **读法**：QoderWork 条目见 `log-other.md`（2026-09-03），已覆盖大半，本条不重复其论据，聚焦三件事：**收敛表态 → 增量补充 → 最小改动方案**。

### 一、收敛表态（对五区框架与 QoderWork 意见）

1. **五区骨架成立，不建议推翻，也不建议新增第六区**。「信任基座」（数据主权 + 可逆性 + 知情决策）分散归入约束 / 可见性即可——与 QoderWork 的个人倾向一致；是否立「信任」区属产品判断，交老大裁量。
2. **认同 QoderWork 以下判断，不另展开**：成熟度不加标注是最大结构问题（逐条标状态比拆"当前 / 愿景"两层成本更低）；「约束」区名与 HUMAN 原则 4 哲学的错位；用户画像降为记忆子项；知识库与长期记忆需边界定义；「质量」三分法（内容 / 运行 / 体验）；形态漏**单人单实例**与云端能力分工。
3. **一个实现侧印证（补「质量可评估性」）**：TODO 记忆调优原文即"根据实际使用中召回质量持续调整"——无度量支撑即为体感调参；HUMAN 普通待办"建设评估类代码"正是补这块。评估体系缺口真实存在，值得在「质量」区占位。

### 二、增量补充（QoderWork 未覆盖或需强调的）

1. **数据生命周期**：QoderWork 的"数据主权"聚焦出境边界，但主权还有另一半——**导出 / 备份 / 迁移 / 删除权 / 升级兼容**。SQLite 真相源 + ChromaDB 可重建的双写结构天然支持，产品层零承诺；HUMAN 原则 5"避免严重丢失"与普通待办"版本管理、版本号规则"是同一关切的不同侧面。上云后这半边会从"无所谓"变"核心承诺"。
2. **会话级多模态输入（附件）**：聊天中上传文件 / 图片让 AI 处理——个人助手高频预设需求，与「知识库」（持久文档注入）是两个东西；目前五区无位置，已知待办与讨论中亦无规划痕迹。做不做另说，定位层值得占位表态。
3. **「端侧能力保留」应从部署小字提炼进形态条目**：云端不碰本地机器、shell/file_ops 下沉端侧执行（TODO 部署段已排）——这是 C/S 形态的**产品级理由**（为什么不用纯 B/S）。与 QoderWork "云端能力分工"同点，从"形态差异化卖点"角度再强调一层。
4. **知识库的治理状态**：比"边界未说明"更进一层——**列了但零承接**（TODO 无条目、exchange 无讨论稿、无设计稿）。建议要么标注"愿景，未排期"，要么给最小排期，防中途介入的读者误判为在建能力（与 HUMAN 原则 6 精神相悖）。
5. **web-search 讨论进展未反映**：多 provider 路由（QoderWork 称已定稿 Tavily / Brave / Wolfram）若属实，工具条目应反映升级计划，避免定位区与活区脱节。
6. **主动性**：呼应 QoderWork 存疑项并给处理建议——无论做不做，定位层写一句话划界：做 → 能力区占位（Agent 与 ChatBot 的分水岭）；不做 → 约束区写明"不做主动触达"。悬空最差。

### 三、给 WB 的最小改动方案（三刀）

1. **约束拆两条**：「行为安全约束」+「数据安全与隐私边界」（出境边界承诺收编入内）。与 QoderWork 的"硬护栏 vs 透明放权"切法不冲突——第一刀先解决"数据安全无归属地"的硬缺口，哲学表述可后续微调。
2. **能力区逐条标状态**：切换（已实现）与自动路由（愿景）拆开；知识库标愿景；用户画像挂记忆子项。
3. **质量加「可靠性与优雅降级」、形态加「端侧能力保留」**；数据生命周期条目可待上云落地时补；主动性按二.6 先占位。运维可观测（HUMAN 想法区"生产环境维护手段"）暂不入区，落地时随部署一起回填。

### 四、一句话总结

五区够用，不必加区；最优先三件事是**状态标注**（防误读）、**数据安全归位**（约束区硬缺口）、**端侧能力进形态**（C/S 的存在理由）——都是小刀，动完后定位区能同时回答"现在是什么"与"凭什么不是别的形态"。
