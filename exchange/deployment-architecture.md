# LarryAgent 云部署架构方案

> 定位：统一「上云部署」的架构边界与落地路径，整合 TODO 既有上云计划（现归「部署调试试运行」段）。
> 状态：**方案（待老大确认后派发执行）**，非实施文档。本文只定「哪些上云、哪些在客户端」的边界与配套，不展开本地客户端能力的具体实现。
> 最后更新：2026-09-03（WorkBuddy，对照 backend / client 实况梳理）

---

## 一、结论（TL;DR）

1. **架构本质 = 云脑 + 本地手**。C/S 里 C（客户端）承载"有本地副作用"的能力，S（云端）承载"无本地副作用"的能力。选 C/S 而非 B/S 的根因，就是 S 需要驱动 C 本机的**命令行 / 文件系统 / 文件记忆 / 工作空间 / 本地数据库**。
2. **云端**：LLM 路由 + 对话编排 + 云端长期记忆（SQLite 真相源 + ChromaDB 索引）+ web_search + 鉴权 / HTTPS。
3. **客户端**：Tauri UI + 本地执行器（shell / file_ops / 本地文件记忆 / 工作空间 / 本地数据库）。执行器是后续版本能力，本文只定边界。
4. **两个环境**：
   - **开发测试态（现态）**：单机，client + backend 全在本机 `127.0.0.1`，无鉴权、无 HTTPS。
   - **生产态**：backend 上云（VPS），多台 PC 客户端经 HTTPS 访问。
5. **上云硬前置（不满足别上）**：`server.api_key` 鉴权 + HTTPS + shell/file_ops 能力重划（见 §五）。
6. **渐进路径（重要，避免错误预期）**：不是"一上云就云脑+本地手全套"，而是——
   - 阶段 1（现态）：单机全功能。
   - 阶段 2（第一版上云）：云端只提供脑能力 + web_search；shell / file_ops 暂**禁用或仅本机模式可用**。
   - 阶段 3（本地能力下沉后）：完整的"云脑 + 本地手"。

## 二、云 / 端边界划分

| 模块 | 现位置（开发测试） | 目标位置（生产） | 说明 |
|---|---|---|---|
| LLM 路由 / 对话编排 | backend 本机 | **云端** | function calling 循环，无本地副作用 |
| 会话管理（conversations） | backend 本机 | **云端** | SQLite 表，多端共享 |
| 云端长期记忆（SQLite + ChromaDB） | backend 本机 | **云端** | 多端共享的单一真相源 |
| Embedding（local bge-small / openai） | backend 本机 | **云端 VPS 跑 local** | LLM API 是唯一出境通道 |
| web_search（Brave） | backend 本机 | **云端** | 纯网络，无本地副作用 |
| 角色 / 模型清单 | backend 本机 | **云端** | config.yaml 下发 |
| API 鉴权 / HTTPS | 未启用 | **云端** | 上云硬前置 |
| **file_ops（读写文件）** | backend 本机 | **客户端（下沉）** | 操作本机文件，必须端侧执行 |
| **shell（执行命令）** | backend 本机 | **客户端（下沉）** | 操作本机命令行，必须端侧执行 |
| **本地文件记忆系统** | 未实现 | **客户端** | 未来本地能力（类比 WorkBuddy `.workbuddy/memory/`） |
| **工作空间 / 本地数据库** | 未实现 | **客户端** | 未来本地能力 |
| Tauri UI | client 本机 | client 本机 | 不变 |
| Tauri 壳（进程守护） | client 本机 | client 本机 | 现状 spawn 后端 → 未来 spawn 本地执行器 |

> 关键洞察：**现状的单机 backend 在目标架构里会"裂变"成两个角色**——
> ① 云端 backend（大脑）：LLM 编排 + 云端记忆 + web_search；
> ② 本地执行器（手）：file_ops + shell + 本地文件记忆 + 本地库。
> 由于现有 backend 已是一套完整的"工具执行 + 记忆"引擎，本地执行器最省力的落地方式就是**复用现有 backend 以"瘦身本地模式"继续跑在客户端机器上**，而不是把工具逻辑重写进 Tauri 原生 command（详见 §七 待议项）。

## 三、两种形态对比

```
【开发测试态 · 现态 · 单机】
┌──────────────────────────── PC ────────────────────────────┐
│  Tauri 壳 ──spawn──▶ uvicorn main:app (127.0.0.1:8000)     │
│   Vue3 UI ──/api──▶ FastAPI + SQLite + ChromaDB + tools    │
│                       (file_ops / shell 操作本机)          │
└─────────────────────────────────────────────────────────────┘

【生产态 · 云后端 + 多 PC 客户端】
                ┌────────────── 云端 VPS ──────────────┐
                │  Nginx (TLS 终止 + 反代)             │
                │     └─▶ uvicorn (127.0.0.1:8000)      │
                │           FastAPI + SQLite + ChromaDB │
                │           + web_search + 鉴权         │
                │           （不碰本机文件/命令）        │
                └──────────────────┬───────────────────┘
                                   │ HTTPS (Bearer API Key)
          ┌────────────────────────┼────────────────────────┐
          ▼                        ▼                        ▼
   ┌─────────────┐          ┌─────────────┐          ┌─────────────┐
   │  PC 1 客户端 │          │  PC 2 客户端 │          │  手机(未来)  │
   │ Tauri UI    │          │ Tauri UI    │          │  HTML5 B/S   │
   │ +本地执行器  │          │ +本地执行器  │          │ (无本地能力) │
   └─────────────┘          └─────────────┘          └─────────────┘
```

要点：

- 云端 backend **只监听 `127.0.0.1`**，由同机 Nginx 反代对外（backend 不直接暴露公网）。
- 多端共享同一份云端 SQLite / ChromaDB，无数据一致性难题（单一真相源）。
- 移动端走 B/S 直连云端，天然无本地能力（浏览器沙箱），与 PC 端能力不对称是**预期内的**。

## 四、配置方案

### 4.1 后端 config.yaml（两环境对比）

| 配置项 | 开发测试 | 生产（云） | 说明 |
|---|---|---|---|
| `server.host` | `127.0.0.1` | `127.0.0.1` | 生产也保持本机回环，公网经 Nginx 反代 |
| `server.port` | `8000` | `8000` | 不变 |
| `server.api_key` | 空 | **强随机长 key** | 上云硬前置，空 = 无鉴权暴露 |
| `database.path` | `data/larry.db` | 持久化卷路径 | VPS 磁盘，务必挂载/备份 |
| `vector_store.enabled` | `false`/`true` | `true` | 长期记忆开启 |
| `embedding.provider` | `local` | `local` | VPS 跑 bge-small，不额外出境 |
| `tools.enabled_tools` | 全开或列明 | **见 4.3** | 上云初期剔除 shell / file_ops |
| `tools.shell_allowed_ips` | `127.0.0.1`/`::1` | 见 §五改造 | 与公网访问不兼容 |
| `tools.file_ops_workspace` | `~/larry_workspace` | 见 §五 | 端侧执行后按设备隔离 |
| `machine_id` | `desktop-01` | 按设备区分 | 多端身份标识（伏笔，见 §七） |

### 4.2 客户端连接配置（关键改造点）

**现状问题**：前端 `client/src/api.ts` 的 `API_BASE = "/api"` 是**相对路径**。dev 靠 Vite proxy 打到 `127.0.0.1:8000`；但 Tauri 生产打包后 webview 的 origin 是 `tauri://localhost`（非后端地址），`fetch("/api")` 会直接断链——这正是"打包方式见鬼"的一个具体病灶。

**目标**：`API_BASE` 从相对路径改为**可配置的绝对地址**，两路注入：

1. **构建期默认值**：Vite 环境变量 `VITE_API_BASE`（dev 默认 `http://127.0.0.1:8000`，产线默认云 URL），打进 bundle。
2. **运行期覆盖**：客户端设置页填写「服务器地址 + API Key」，存本地配置，优先于构建默认值。设置页即 TODO 里「设置入口页面（复活）」的落地用途之一。

### 4.3 本地工具的过渡期配置

上云初期（阶段 2）本地执行器未就绪时，**云端 backend 必须显式禁用 shell / file_ops**：

```yaml
tools:
  enabled_tools: ["web_search"]   # 上云初期：只开无本地副作用的工具
```

理由：若云端仍注册 shell / file_ops，LLM 会"以为能执行命令/读写文件"，实际操作的是**云端机器**而非用户 PC——这是比"没这功能"更危险的误导（用户亲历过的"数据混染"同类风险）。宁可明确禁用，不可静默错位。

### 4.4 便捷切换方式

- **后端**：复用已支持的 `LARRY_CONFIG` 环境变量指向不同 profile，如 `config.dev.yaml` / `config.prod.yaml`。启动命令 `LARRY_CONFIG=config.prod.yaml uvicorn main:app`。测试隔离已验证此通道可靠（Tier0 红线即靠它）。
- **客户端**：设置页「连接目标」切换 `本机 / 云端`，一键改写 `API_BASE` 与 API Key，无需重打包。

## 五、隔离手段（安全边界）

| 层 | 手段 | 现状 | 上云动作 |
|---|---|---|---|
| 传输 | HTTPS / TLS 终止 | 无 | Nginx + 证书（Let's Encrypt 或云厂商） |
| 鉴权 | `server.api_key` Bearer 校验 | 空=透传 | **必须设置强随机 key**（AuthMiddleware 已就绪） |
| 网络暴露 | backend 只监听 127.0.0.1 | 已如此 | 由 Nginx 反代对外，backend 不直接开公网 |
| 本地命令 | shell IP 白名单 | `127.0.0.1`/`::1` | 端侧执行（caller_ip=本机）；云端不注册 shell |
| 本地文件 | file_ops workspace 限定目录 | 已有 | 端侧执行，按设备/会话隔离（配合 TODO「会话指定工作空间」） |
| 命令安全 | ShellTool 黑名单加固 | 字符串包含匹配可穿透 | 随本地能力下沉升级正则/词法解析（端侧执行器，云端不注册 shell） |
| 凭据 | config.yaml 不入库 | 已 `.gitignore` | 保持；云端用环境变量/独立配置文件注入 |
| 数据 | SQLite/ChromaDB 落云厂商磁盘 | 本机 | 明确"数据落云"风险已知 + 定期备份 |

**安全观**（沿用既有结论）：key 价值低，真正风险是**数据混染**与**能力错位**。上云后最危险的不是"key 泄露"，而是"云端 backend 误以为在操作用户本机"。隔离的重心放在**能力边界清晰化**，而非堆叠复杂密钥管理。

## 六、打包与部署

### 6.1 客户端打包

- 现状：`npm run build:tauri`（Tauri build），产出 Windows 可执行/安装包。用户已评价"见鬼的简陋方式"。
- 改进点（按优先级）：
  1. `API_BASE` 可配置（§4.2）——否则打出来的包连不上云端，是硬伤。
  2. 设置页落地（服务器地址 + API Key + 本机/云端切换）。
  3. Tauri 壳 spawn 目标从"全套 backend"演进为"本地执行器"（阶段 3，配合 §二裂变）。
  4. 版本号规则（HUMAN.md 待办）——发版前需定。

### 6.2 后端部署

两选项，倾向 A：

- **A. 裸 uvicorn + Nginx + systemd（推荐）**：契合"单人低频 + 自身有运维能力"的现状，透明可控，不引入额外抽象。Nginx 反代 + TLS + 静态文件托管；systemd 守护 + 开机自启；SQLite/Chroma 落本地磁盘 + 定时备份。
- **B. Docker 容器化**：标准化、可迁移，但引入镜像/编排/存储卷维护成本。用户对"省运维/开箱即用"类价值不敏感，单人项目收益有限。**暂不采用**，除非未来多环境/多机复制需求出现。

部署脚本与文档即 TODO「部署调试试运行」的 `Nginx 部署脚本示例 + 部署文档 + 安全加固`。

## 七、关键待议项（暴露矛盾，本次不展开）

1. **本地工具下沉的实现路径**（最大技术难点）：
   - A. **双向通道**：客户端↔云端常驻 WebSocket，云端 LLM 决策调本地工具时下发指令、客户端执行后回传，继续云端循环。
   - B. **本地 agent 运行时（倾向）**：复用现有 backend 以"瘦身本地模式"跑在客户端机器，专职 file_ops / shell / 本地记忆 / 本地库，作为云端 backend 的"手"。
   - C. 混合。
   - 需专项设计 + 权衡后定，建议单独立项，不与云部署捆绑。

2. **记忆系统分层**：云端长期记忆（SQLite+ChromaDB 事实真相源，多端共享）与本地文件记忆系统（按天日志式，端侧独立）的关系与边界——两者会不会重复/冲突，归属谁，待定。

3. **多端设备身份**：`machine_id` 已存在但记忆层未消费。多端下是否需要"按设备隔离/标注记忆来源"待定。注：设备维度（machine_id）与角色维度（source_role）是两个正交维度，后者已归 TODO「多场景 AI 架构」的「场景间信息同步策略」。

4. **移动端能力不对称**：B/S 无本地能力，与 PC 端能力差是预期内还是需要"云端 workspace 平替"，待产品层面定。

## 八、落地顺序建议

1. **先钉硬前置**（不依赖本地能力下沉，可立即派）：`server.api_key` 强制 + HTTPS + Nginx 反代 + shell/file_ops 上云禁用（enabled_tools）。
2. **客户端可配置化**：`API_BASE` 环境变量 + 设置页（连接目标 + API Key）。
3. **打包与部署脚本**：Tauri 打包改进 + 后端裸部署脚本/文档。
4. **本地能力下沉**：单独立项（§七 第 1 条），与云部署解耦。
