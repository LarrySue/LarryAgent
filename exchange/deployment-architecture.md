## 一、四条真未决（正文逐字承自原稿 §七，⛔ 未作改写）

1. **本地工具下沉的实现路径**（最大技术难点）：
   - A. **双向通道**：客户端↔云端常驻 WebSocket，云端 LLM 决策调本地工具时下发指令、客户端执行后回传，继续云端循环。
   - B. **本地 agent 运行时（倾向）**：复用现有 backend 以"瘦身本地模式"跑在客户端机器，专职 file_ops / shell / 本地记忆 / 本地库，作为云端 backend 的"手"。
   - C. 混合。
   - 需专项设计 + 权衡后定，建议单独立项，不与云部署捆绑。
   - 📌 **主持注（2026-10-29，Qoder 一家之言，待汇总）**：上云侧已把该事项登记为**目标态第 7 条**（`docs/deployment-architecture.md` §八），"倾向 B"仍只是**本稿内的倾向**、⛔ 未成定案；定案时须一并回答 `docs/` §二 那句"裂变"的成立条件。

2. **记忆系统分层**：云端长期记忆（SQLite+ChromaDB 事实真相源，多端共享）与本地文件记忆系统（按天日志式，端侧独立）的关系与边界——两者会不会重复/冲突，归属谁，待定。

3. **多端设备身份**：`machine_id` 已存在但记忆层未消费。多端下是否需要"按设备隔离/标注记忆来源"待定。注：设备维度（machine_id）与角色维度（source_role）是两个正交维度，后者已归 TODO「多场景 AI 架构」的「场景间信息同步策略」。

4. **移动端能力不对称**：B/S 无本地能力，与 PC 端能力差是预期内还是需要"云端 workspace 平替"，待产品层面定。
