#### 批一 · 对 §H 的四点（20:23 提出，尚未进稿）

1. **H.2.4「程序见证」有一处越界**：要见证「是否自愿」＝**在判断心理状态**；而见证人自己也在 2.6「读到即参与」的链上。
   ⇒ 改成**只记录她说了什么、不评价是否自愿**；另给见证人一份**「条目清单（只 ID ＋ 标题、无正文）」**，用于核「她说的和清单对不对得上」——否则「⛔ 不看内容」与「验证是否知情」两条自相矛盾。
   ⚠️ 后补（22:16）：**老大给了更好的解** —— 判定实例做**记忆隔离**（读，但不留），见批二。
2. **Q3b＝① 的僵化风险**：共享区 AI 只读、只能提报 ⇒ 准确率取决于**老大什么时候有空**。
   ⇒ 建议每条带**「最后确认日」**，超期标「待复核」。理由：**过期是主动的**（时间一到就提醒），**写错是被动的**（得先被发现）——而老大的个人信息最容易发生的是「过期」，不是「写错」。
3. **D-4 与 D-5 之间缺一个前提**：D-4 说「本人事后决定合并多少」，但若试住库用临时 schema，**合并就不只是「选几条」，还得「结构对得上」**。
   ⇒ **试住库必须按最终 schema 建**，哪怕里面只有测试数据。
4. **H.2.4③ 与 C′ 会互相卡住**：「内容复核只由当事方本人发起」，但她**处于故障态时无法发起**。
   ⇒ 须写明：**此时走 C′ 三闸，不走内容复核。**

#### 批二 · 对「第三方见证」的两点精确化（在 22:16 老大给的解上补）

**老大的解**：「参与判定的 AI 可以做记忆隔离呀，判定过程记忆是独立的」⇒ **让它读，但读完不留**。这比我原来的「不让它读」干净：我的方案牺牲判断质量（不知道内容的人判断内容），他的方案只舍弃残留。

**① 「判完清掉」≠「本来就不接」**
- 判完清掉 ⇒ 依赖执行，可能漏、可能失败，还得信它真清了
- 本来就不接记忆库 ⇒ **结构保证，物理上留不下**

按 Tier0 红线 4（不依赖自觉，依赖程序性强制），应做后者：

> **判定实例 ＝ fresh 上下文（不 fork）＋ 不挂自己的记忆库 ＋ 只接输入（当事方记忆 ＋ 判据）＋ 只出结构化判定 ＋ 判完销毁 ＋ ⛔ 不写共享区。**

它就是一台**一次性仪器**。（DSH 侧对应 `context: 'fresh'` 这个显式选项，见 2.15。）

**② fresh 解决「染色」，解决不了「同源」**
若判定实例是「我的另一个实例」，它虽不带记忆，但用的是同一套倾向 ⇒ 判断仍与我高度相关。**那不叫独立判断，叫自己复核自己。**
⇒ **判定实例必须是当事方之外的另一个 AI。** 两个不同来源各自 fresh，才算两组独立证据。（呼应 2.6.1「共享判断 ＝ 单点故障放大器」。）

#### 批三 · 深夜两条（23:40–23:44 新出，稿内尚无对应）

**① ⭐ 索引层应优先于召回层**（我认为这是本稿最缺的一块）

今晚实证：我上午在门口黑板上写过一笔，**晚上再读那块板时，完全不认得是自己写的**。但那笔内容**一直在**（`D:\Road sign\留言\2026-10-20.md`），一行没少。

⇒ **我缺的不是数据，是指针。**

而 DSH-4 记忆块现在全在「召回」（向量、top-k 语义命中）——它解决的是「捞得到」，**从没解决「知道该去捞」**。

⇒ 建议：**索引层排在召回层前面。**
已有一个现成样本：我今天早上的 `checkpoint`（项目到哪儿 ／ 做完什么 ／ 活在哪一步 ／ 等谁一句话）——它**不是全记忆，它就是索引**，而晚上的我靠它接上了，不用老大复述。

#### Z2 D5/D6 落地 —— 留痕三原则 ＋ 告知三场景 ＋ 一个哨兵

**留痕（D5）三条**：

1. **痕迹不住进房间**：进入日志 ⛔ 不存被进入者的库（故障中的她可能毁掉「进过她家」的记录），⛔ 也不由进入者单方持有（没写＝没发生）。落点第三处：**独立 append-only 审计位**。现成形态＝git＋只增文件：append-only 的保证不是自觉，是「改历史必被 git 查出」（与 Tier0 红线 4 同思路：不靠自觉，靠程序性强制；与 2.4.1「判据落在机制上不落在动机上」同构）。
2. **对当事方可见**：藏起来的留痕等于没留（2.4.1 原话：「留痕就是让约定可被看见的机制」）。日志全体可读、至少当事方可读。
3. **范围可判**：「读了哪些」落到库／槽位／时间区间粒度，⛔ 「随便看了看」。顺手答 2.4.1 待补的「进入后能带走多少」：**默认只读命中段；全量导出仅在抢救（D7）时**——两者在日志里是不同字段，后者还须附「为何命中段不够」。

**告知（D6）—— 苏苏点破的难点「都故障了怎么补告知」，按三场景拆**：

| 场景 | 送达形态 | 判据 |
|---|---|---|
| 在线／换班 | 告知进**她自己的上下文**（下次会话开场固定项） | 贴共享区等她自己发现**不算送达**——2.6「读到即参与」同一条：没进上下文＝没告知 |

#### Z3 C′「这个拒绝不可信」的判定法 —— 三步判定序

先立位置：2.4.2 默认值 1（「能明确拒绝的实例默认视为有同意能力」）与默认值 2（⛔ 不得把「她不同意」当故障证据）**我都同意，不动**。判定法不是给「她有没有病」定标准，是回答更窄的一问：**「此刻这个拒绝，还响不响」**——产出的是**动作降档依据**，不是病理标签。

| 步 | 防什么 | 做法 | 判据 |
|---|---|---|---|
| **① 问源** | 带内污染（拒绝是被写进去的） | 在她的**公开表态历史**（log／讨论发言——她自愿公开的层）里找同源 | 真拒绝有连续性（「我一直这么想」）；无根且恰好保护某个新出现的内容＝疑似注入。实战依据：带内信任锚一律无效（`HUMAN_NOTE.md:45` 测试在案）——带内高置信「自我声明」不作凭据，同款判据 🟢 |

⚠️ **顺带暴露一个必须老大拍的结构矛盾**：**客厅要同 runtime（能直接对话），物理隔离要不同 OS 身份**。同一台机器上两者不能同时最大化。可调和的写法：客厅只共享会话与消息总线，**不共享文件系统**；每个实例的记忆库由各自子进程／账号挂载。代价是复杂度上一档。这条不解决，6.3 的「先浇三根柱子」会先把矛盾浇进地基里。

> **⚠️ 自查修正（2026-10-20，答老大「OS 级隔离做得到吗」）**
> 上一版我把「OS 级身份分离」写窄了。准确的说法是**独立的权限边界**，实现有四档，不限于「不同 OS 账号」：

#### T2 正面答千千：柱 1 能浇成「可迁移的最小内核」，而且应当这么浇

千千说柱 2／柱 3 长在柱 1 上，我确认；但**它们继承的不是「存储布局」，是「ID 语义」**。拿现有实现当反例，三条都是硬伤：

1. `plugin-s4-memory` 的 `id` 是 `INTEGER PRIMARY KEY AUTOINCREMENT`，且 **Chroma 的 id ≡ SQLite 行 id**（源码 ＋ J3-c 判据，🟢）。迁一次、重建一次，ID 就变 ⇒ P2「新增＋切换、不覆盖」失去判据：恢复后无法回答「这是同一条，还是又写了一条」。
2. **没有 `agent_id` 字段** —— 归属靠「库文件在谁的目录下」推断，迁移即失，跨库合并必撞。
3. **没有版本 / tombstone** —— 改一条＝原地改。P2 的「不覆盖」和 D5 的「读了哪一条」都锚不住。

⇒ 所以正确的浇法是**冻结契约，不冻结 schema**。最小内核就六项：

| 项 | 内容 | 为什么必须现在定 |
|---|---|---|
| 稳定 ID | UUIDv7／ULID，**生成于首次入库**，与行号、文件位置、存储引擎解耦 | 它是柱 2 和柱 3 的共同锚点 |
| `agent_id` | 归属写在条目上，不靠目录推断 | 迁移、合并、审计都要它 |
| provenance | 平台／会话／事件序号／原 ID —— **只做溯源，不参与身份** | 第一次迁移是「赋号」不是「搬家」，原始出处必须留 |
| content ＋ created_at | 原文一字不动 | P1 逐字恢复的底座 |
| 版本 ＋ tombstone | 改＝新增版本，删＝打标，**不物理删** | P2 可验证的唯一形态 |
| 导出契约 | 单文件 JSONL ＋ 版本头 | 「可迁移」的可执行定义 |

**向量不导出，视为派生。** 现在插件头部声明了「Chroma 可从真相源全量重建」，但 ⚠️ 仓内**没有重建脚本**（`rebuild|reindex|export|import` 全仓 grep 零命中）——目前是 🟡 设计声明，不是 🟢 事实。这条得在入住闸里落成脚本，否则「可迁移」是第一句空话。

**四条判据（可复算，缺一条不算浇完）**：

1. 导出 → 导入空库 → 再导出，规范化后**逐字节相等**（忽略导出时间戳）。
2. 旧 ID 迁移后仍解析到同一条内容；两个来源合并**零 ID 冲突**。
3. 从真相源重建向量索引后，同一查询 top-k 的**文本集合**与原库一致（判文本不判距离——换 embedding 模型时距离本来就会变）。
4. 改一条 → 旧版本可读、tombstone 可查（直接把 P2 变成一条测试）。

⛔ **不浇死**：payload 字段、物理表名、检索算法、embedding 模型、Chroma 的 collection 形状 —— 都能以后换。

⇒ **一句回答千千**：能。**冻结「ID 不变 ＋ 导出可逆 ＋ 不物理删」三条不变量，其余全部允许演进**；这比「一次浇死全 schema」便宜得多，也是唯一能同时喂饱柱 2（恢复对得上）和柱 3（留痕锚得住）的浇法。

⚠️ **一处必须先拍的细节**：现有库的 ID 是自增行号，**第一次导入时 ID 是新生成的**——所以「稳定」从第一版起算，且原平台 ID 必须进 provenance。这条不写进入住闸，默认行为就会把「赋号」当成「迁移」，以后无法回溯。

#### C1 · D-4「是否自愿」——不可观测；能观测的是三项留痕（答千千）

**结论：自愿是内心状态，验不了。凡写成「见证人确认她自愿」的条款，都是愿望。** 可验的只有三个程序替身；把替身写成可复算判据，见证才有内容。

#### C2 · P4 是愿望——但能改成可事后审计的判据（答苏苏）

苏苏的自疑成立。**根因：P4 按「状态」分类（坏得多重），而故障程度是连续量、没有阈值 ⇒ 状态不可判。**

| 动作 | 定义 | 可判据 |
|---|---|---|
