## 1. 【形态级】新增统一字段行〈对手侧状态 + 依赖版本〉

### 现状

能力树每条子项的形态是：`#### 编号 名称 状态emoji` + 字段块（**已做** / **计划** / **无承接** / **老大裁定** / **老大意向**）+ `>` 引用块注释（联审 / 钩子 / 依据）。**全树没有任何一处记录"上游侧是什么状态"**——所以每次 DSH 基线一动，就只能靠人肉重读源码。

### 建议改法（三处）

**(a) §2.1 状态图例下方，新增一段「对手侧状态口径」**（与 `dsh-015-capability-mapping.md` §1 同源，扩充为 5+1 档）：

| 标记 | 含义 | 我方还要做什么 |
|---|---|---|
| 🟢 | **可承接** —— 上游有正式契约 + 默认实现，且与产品语义不冲突 | 配置 / 启用 / 适配破坏性变更 / 验收，**不写底座代码** |
| 🟡 | **可降级** —— 上游有底座（可挂载 seam）或同题参考设计，但产品语义是我们的 | 写语义层；可借鉴上游 / 社区，**不必从零试错** |
| 🔴 | **仍须自做** —— 上游与社区均无对应语义，也无同题设计 | 从设计到实现全自做 |
| ⚪ | **须实测后定**（新增）—— 契约 / 实现存在但未验，或结论依赖运行时行为 | 跑一次实测 ⇒ 转 🟢 / 🟡 / 🔴 之一 |
| ⛔ | **须关闭**（新增）—— 承接后必须显式关掉的上游默认行为 | 写进「迁移必关清单」，不属承接判定 |
| ⬜ | **无对手侧** —— 上游无对应子系统页也无包（如记忆产品化、用户画像、自动路由、时间感知） | 与 🔴 同义，但强调"连参考都没有" |

> **⛔ 三条准入（防垃圾桶化，Claude 提）**：① 上游明确不做且我们也不需要；② 承接它违反红线；③ 承接成本 > 自做成本，且收益 < 一条已列风险。**不满足任一条不得入此档。**
>
> **⛔ 的归属说明**：「须关闭」是**迁移动作**不是**承接判定**，故建议**单独一张清单**（挂 `dsh-migration.md` §3.6「迁移必关清单」），不混进三分类里——混进去会串味（一条能力同时是"可承接"和"须关闭"是常态）。
>
> **⚪ 的准出条件**：跑过一次实测并留下可核证据（命令 + 输出）。**未跑之前不得升格为 🟢**。

**(b) 每条子项在标题下、第一个字段块之前，加一行固定字段**：

```markdown
#### 2.3.3 会话级作用域（沙盒） 🗣️

**对手侧（DSH 0.1.5）**：🟡 `workspace` 子系统即「会话↔目录」数据模型 ｜ 隔离语义仍自做
```

格式约定：`**对手侧（DSH <版本>）**：<档位 emoji> <一句话状态> ｜ <我方剩余动作>`
**必须带版本号**——上游高速演化，不带版本号的记录下次无法判断是否仍成立。

**(c) §2.2 顶层总览表**（可选，看你要不要更密）：现表 4 列（域 / 名称 / 子项 / 最弱一环），可再加一列「对手侧最厚 / 最薄」——用于一眼看出哪个域最可能靠 DSH 省力。

## 2. 2.7.2 边界透明与用户决策权（⚪ 已实测闭合 · 余项见 §11）

### 现状原文（`product-positioning.md:250`）

> 按 `../HUMAN.md` 原则 4（明确安全边界，而非由系统替用户管控）：白名单 / 黑名单 / 工具开关**全部 config 可调**，边界交给用户决策；工具调用过程以 ToolCallCard 展示（见 2.8.2）。

### ⚠️ 问题不在文字，在**它下面没有的依据**

原判"自做"的核心论据是「**SDK 请求面无 answer 方法**（Zero listeners fall through to `unavailable`）」——**这条判据挂在 SDK 请求面上，只在 A-service 架构下成立**。而项目已拍板 **A-framework**（我们就在 DSH 进程内写插件）⇒ 该判据**失效**。

### 建议改为（在原文字后追加两段）

```markdown
> **机制面由 DSH 承接（0.1.5）**：`ctx.approval`（结果集 **fail-closed**——缺失 / 抛错 / 不合规的答者一律 `unavailable`，**不默认开门**，且 `approval/asked` · `decided` 成审计对）、`ctx.permissionPresets`（preset 表 **config 化**，⚠️ 取值为 `sandbox: SandboxMode` + `approval: ApprovalPolicy` **两个 knob**，**不含工具开关**）、`ctx.userQuestions`（答者可**中继到已连接客户端**）——三者均为 A-framework 下的公开契约。
> ⇒ **我方自做范围收窄为「策略内容」**，机制不重造；起步可直接用官方两档 preset，**零代码**。
>
> ✅ **判据出处与状态**：以上取自 `docs/subsystems/` 的 `approval.md` / `permission-presets.md` / `user-questions.md`（`dsh-v0.1.5-rc.2`）。**「自定义 preset 表在真实 profile 里能否生效」已实测** ⇒ 本条 ⚪ **闭合**（002 探针：自定义 preset 在真实 profile 上生效）。
> ⚠️ **覆盖边界（勿外推）**：preset 表**只覆盖 `sandbox` + `approval` 两个 knob**；2.7.2 原文的「**工具开关**」**不在其中** —— 工具级须另走 `ctx.tools.restrict()`（API 与作用域守卫已实证，**真 agent 轮 deny 后的模型侧行为端到端未验**）。
>
> 📌 **本条留下的一条教训（全树推广）**：**判据会随架构选型失效**——同一个"不可达"，换个架构前提就作废。跨阶段沿用旧判据前，先问「这条论据挂在哪个面上」。
```

## 3. 2.3.3 会话级作用域（沙盒）

### 现状原文（`product-positioning.md:95`，"轻量判据"段）

> 轻量判据：行业沙盒两模式（E2B 即抛 microVM / Daytona 持久容器）均为商业云、自托管不友好；**单人 + 自托管场景下，目录级隔离 + 工具作用域绑定（每会话绑定 `file_ops_workspace` 下子目录）即可拿到大部分产品价值**，复杂度低一个量级且与现有 pathlib 沙盒同构。……

### 判断：结论**保留**，但依据要从"我们推断"升级为"上游已给"

原判「DSH `sandbox` ≠ 会话文件沙盒」**仍然对**——但**对位的子系统不是 `sandbox`，是 `workspace`**（原分析找错了对手）。这不是推翻，是**从"行业两模式都不适用故自选目录级隔离"升级为"上游已经是这个数据模型"**。

### 建议改为（在原"轻量判据"段之前插入）

```markdown
> **上游已给数据模型（0.1.5）**：DSH 的 **`workspace`** 子系统即「**会话 ↔ 目录**」的官方模型——稳定 id + 规范路径 + 有序 session 账户；membership = id 在账户内 **且** header 的 cwd 等于 workspace path；`session-controller` 已实现「新建会话 cwd 取自选定 workspace → 落 immutable header → attach」。
> ⇒ **我方只做「隔离语义」**（`workspace` 原文明确 root「**不是读边界**」），数据模型不自造。
> ⚠️ 运行时行为（membership 过滤、attach 流程）**只读了类型与规格，未跑** ⇒ ⚪ 须实测后定。
```

原「轻量判据」段**保留**（它对"隔离做到哪一档"的判断仍然有效），但**不再承担"为什么自选目录级隔离"的论证职责**。

> 形态：PC 版 C/S（client 在本机不上云，server 上云）；移动版 B/S（浏览器直连云端）。

### 建议追加（**结论不变，依据必须换**）

```markdown
> **但仍然没有多用户 / 租户语义**：`identity/` 自称 **anonymous identity**；出厂传输是 loopback HTTP（cookie **未标 `Secure`**）、**无登出**。
> ⇒ **云端部署与租户隔离仍须自做，方向不变**；变的是理由——从"上游没做"改为"**上游做了单机远程，没做多用户**"。
> ⚠️ **依据必须换**，否则下次复核会因"上游明明有远程"而误判本条结论失效（与 §2 的教训同源）。
```

## 9. 全树推广的两条教训（建议写进 §2 的写实口径）

1. **判据会随架构选型失效** —— 同一个"不可达"，换个架构前提（A-service → A-framework）就作废。**跨阶段沿用旧判据前，先问「这条论据挂在哪个面上」**。（出自 §2）
2. **「上游有没有 X」与「我们要不要做 X」是两个问题** —— 前者属架构层，后者属产品层。**混判会得出「因为上游给了能力所以我们该做」的错误推论**。（出自 §4，老大判据）
