## 3 协议总览

### 3.1 承载（⚠️ **岔路 D1 · 待老大裁**）

| 方案 | 形状 | 优势 | 代价 |
|---|---|---|---|
| **D1-a（本文倾向）** | **HTTP unary（client→server）＋ SSE（server→client）** | ① 贴合官方 `dsh-client-connection` 形状，参照成本最低；② 反代友好（C7）；③ 移动端 `EventSource` 原生支持；④ client→server 的 unary 天然自带"响应体" | **反向请求要用 unary POST 回响应**（多一层设计，见 §4.3） |
| **D1-b** | **WebSocket 单连接双向** | 反向请求天然对称，无需"用 POST 回响应"；连接状态单一 | 需自管心跳 / 重连 / 反代兼容；偏离官方形状 |

**本文倾向 D1-a**。理由：唯一真正的代价是 §4.3 那层"反向请求要经 POST 回来"的设计——而这层**无论选哪个承载都得写**（因为 DSH 侧 `onRequest` 的答案回填逻辑本来就要自做），所以 D1-a 的边际代价比表观更小。反过来说，选 D1-b 并不能省掉任何业务层工作，只是换掉运输层。

> ⛔ 无论裁哪个，**A 段与 B 段的边界不变**：承载是 A 段内部事，不影响 driver 与 DSH 的 stdio 约定。

### 3.2 帧形状（⚠️ **岔路 D2 · 待老大裁**）

| 方案 | 形状 | 说明 |
|---|---|---|
| **D2-a（本文倾向）** | **JSON-RPC 2.0 语义**，承载换成 HTTP/SSE | ① 与 B 段（`JsonRpcLineTransport`）同构 ⇒ 3.3-b 的薄客户端骨架（帧分类 / id 关联 / `onRequest` / `AbortSignal`）**可整套复用**；② 双向请求天然对称（有 `id` 就是 request）；③ 通知与请求的区分是现成语义 |
| **D2-b** | 自定 REST 形状（`POST /a/sessions/:id/prompt` 等） | 更"接口化"、对前端更直观 | 双向请求**没有现成语义**，要自造一套"反向请求 + 回执"约定；事件流仍需另一套形状 ⇒ **两套形状并存** |

**本文倾向 D2-a**。：D2-b 的"直观"只对 client→server 那半边成立，而 server→client 那半边（而这正是本项目的**核心增量**）仍要自造；D2-a 让两侧对称，且**可直接复用 3.3-b 已实测通过的骨架**（`TODO.md`：3.3-b 的薄客户端 = 本段 driver 的骨架，**勿另起一套**）。

**帧分类**（沿用 DSH `transport` 心智模型，B 段已实测）：

| 形状 | 语义 |
|---|---|
| `{id, method, params}` | **请求**（要回 `{id, result}` 或 `{id, error}`） |
| `{id, result}` ／ `{id, error}` | **响应** |
| `{method, params}`（无 `id`） | **通知**（不回） |
| 无 handler 的请求 | 回 **`-32601 method not found`**（**不静默丢弃** ⇒ 天然可观测，已在 3.3-b 实测作负向对照） |
| handler 抛错 | 回 **`-32603`** |

**id 命名空间**（⚠️ 必须写死，否则双向请求会撞 id）：`c-<n>` = client 发起，`s-<n>` = server 发起。两端各自单调递增，**不得复用同一 id 于未结清窗口内**。

### 3.3 端点表（按 D1-a 列；若裁 D1-b 则收敛为单一 WS 端点）

| 端点 | 方法 | 用途 | 鉴权 |
|---|---|---|---|
| `/a/rpc` | `POST` | **全帧入口**：client→server 的 request / response / notification 都走这里 | ✅ |
| `/a/stream` | `GET`（SSE） | **上行信道**：server→client 的通知 ＋ **反向请求** | ✅ |
| `/a/blob/:ref` | `GET` | 大对象取回（附件 / 长工具输出），避免塞进事件流 | ✅ |

**部署前提（C7）**：本协议**不绑全部网卡**（对齐官方 web surface 约束）⇒ 生产形态是「绑定 loopback ＋ 反向代理」或「显式 `--trusted-host` 白名单」。反代已实测可行（`production-env.md` §7.1）。

## 4 消息集

### 4.1 下行（client → server）

| method | 参数（要点） | 结果 | 触 LLM？ |
|---|---|---|---|
| `auth/login` | `{deviceLabel}` | `{token, expiresAt}` | — |
| `session/list` | `{cursor?, limit?}` | `{items:[{id,title,updatedAt,state}], nextCursor?}` | ❌ |
| `session/open` | `{sessionId}` | `{history:[…], state:'warm'\|'hot'}` | ❌ **（C2：只读不跑）** |
| `session/prompt` | `{sessionId, blocks:[…]}` | `{messageId}`（**受理回执，非答案**） | ✅ |
| `session/cancel` | `{sessionId, messageId?}` | `{ok}` | — |
| `session/new` | `{cwd?}` | `{sessionId}` | ❌ |
| `session/rename` | `{sessionId, title}` | `{ok}` | ❌ |
| `stream/resume`（若不用 SSE 的 `Last-Event-ID`） | `{sessionId, sinceSeq}` | `{ok}` | ❌ |

| `message/complete` | 一条消息收口 | |

| `session/compaction` | 上下文压缩事件 | |

| `stream/ping` | 心跳（2 s，对齐官方） | §9 |

### 4.3 反向请求层（⭐ 本段核心增量）

**问题**：`server → client` 的**请求-响应**语义，在纯事件流里没有天然承载。

**做法**（两条路径都要写，选哪条取决于 D1 的裁决）：

- **D1-a（SSE）**：server 通过 `/a/stream` 下发 `{id:'s-<n>', method, params}` ⇒ client 处理完后，把 `{id:'s-<n>', result}` **作为一帧 POST 到 `/a/rpc`**（该端点同时接受 request / response / notification 三类帧）。server 侧的 pending 表按 id 结清。
- **D1-b（WS）**：同一连接内直接回，语义相同，只少一次 HTTP 往返。

**两侧共用的纪律**（无论 D1 选谁）：
1. **pending 表两侧对称**：server 发反向请求后登记 pending；client 回帧或超时后结清。**撤回后不得再结算**（3.3-b 已实测"迟到回答不留任何状态"）。
2. **超时归属见 §5.4**（两路语义不同，⛔ 不得混用）。
3. **对端不在线 ⇒ 立即 fail-closed ＋ 落日志**（C10）。

## 5 审批请求双向中继（3.3-c 的终点）

### 5.1 定名（C11 收口）

3.3-b 用的是**临时约定**的 `approval/request`。本稿**定名沿用它**（理由：减少一层无谓翻译；且它与 DSH 内部 `approval/request` waterfall **同名同义**，转换层可直通）。

⚠️ **但两者是两件事，实现时不得混指**：
- DSH 侧 `approval/request` = **进程内 waterfall 事件名**（`dsh-user-approval` 的机制面）。
- A 段 `approval/request` = **线上 method 名**（server→client 反向请求）。
- driver（§11）是二者之间**唯一**的翻译点。

### 5.2 链路全图

```
DSH 内插件（remote-answerer）
  └─ DSH 出站请求（B 段 · stdio JSON-RPC）  method = approval/request
      └─ driver（= 3.3-b 薄客户端骨架）     ← 翻译点
          └─ A 段反向请求（server→client）  method = approval/request
              └─ 前端（PC Tauri 弹卡 / 移动端浏览器弹卡）
                  └─ 人答 ⇒ 回帧（client→server response）
              ← 答案沿原路回填 ⇒ DSH 侧答者结算
```

### 5.3 参数与结果（**须与 3.3-b 的实测词汇一致**）

请求 `params`：
```
{
  requestId,        // 供两侧日志对账（DSH 侧已有此字段）
  toolName, callId, agentId, reason,
  options: ['allowed-once', 'rejected'],   // 前端据此渲染按钮
  expiresAt?        // 可选：见 §5.4
}
```

结果：**封闭词汇，不得扩展**（C8）—— `allowed-once` ／ `rejected` ／ `cancelled` ／ `unavailable`。
⛔ **无 `allow-always`**（3.3-b 实测：`dsh-user-approval` 的结果词汇表里不存在）。前端**不得**自行造"总是允许"按钮。

### 5.4 超时与失败（⚠️ **本段最易错处**，C9）

| 路 | 机制 | 落哪个词汇 | 谁负责 |
|---|---|---|---|
| **(a) 请求侧中止** | DSH 侧 `req.signal` abort（如探针 `timeoutMs` 到点） | **`cancelled`** | DSH 侧（非我方） |
| **(b) 答者侧自建超时** | **官方答者侧不存在超时计时器** ⇒ 须自做（3.3-b 已在远端答者里做过） | **`unavailable`** | 我方（答者 / driver） |
| **(c) 前端不答** | 人没点、页面关了、网络断了 | **须在 §7/§8 之外显式定义** ⇒ 建议：前端断开由 **server 侧的 pending 超时**兜底 ⇒ **`unavailable`**（**不是** `cancelled`，因为"取消"是请求侧的动作） | 我方（server） |
| **(d) 对端消失** | 传输终止 / PC 离线 | **`unavailable`** ＋ fail-closed（动作 0 次）＋ **必须留可观测日志** | 我方 |

⛔ **`-32601` 与 `-32603` 不得直接当业务结果**：DSH 侧会把它归一化成 `unavailable`（3.3-b 实测：对端未装 handler ⇒ 原始帧 `-32601` ⇒ dsh 侧归一化为 `unavailable`）。A 段同理——**协议错误要能追溯到原始帧**，但不能让它变成"另一个业务词汇"。

### 5.5 前端的**唯一硬要求**

**审批卡必须在"被保护动作真的没发生"时可观测**（C10）。⛔ 静默 fail-closed ＝ 假绿源：UI 上什么都不弹、日志里什么都不留、动作也没发生 —— 这三件事同时成立时，**看不出请求到底到没到**。⇒ 前端在每次收到 `approval/request` 时**先落一条本地记录**，再渲染卡片。

## 6 会话管理（三态）

| 态 | 含义 | 内存量级 | 进入条件 | 退出条件 |
|---|---|---|---|---|
| `cold` | 只有元数据（列表 / 标题 / 时间） | ≈ 0 | 默认 | `session/open` |
| `warm` | 历史已加载（供渲染），**未发 LLM** | 0（历史不驻留） | `session/open` | `session/prompt` ／ 超时回收 |
| `hot` | runtime 内活跃（B 段 DSH 侧持有） | ≈ 2.24 MB/个（实测） | `session/prompt` | 取消 / 空闲回收 |

**一期策略（承〈定型结论〉条 3 的拍板）**：
1. **不设激进 LRU**（实测外推 20 会话 ≈ 182 MB，占 2C2G 约 9%）。
2. 真正的约束是 **token 成本不是内存** ⇒ 优化目标是**减少无谓的 context 重建**。
3. ⚠️ **`session/open` 对 `hot` 会话不得触发重建** —— 若该会话已在 runtime 内为 `hot`，open 只回状态与增量，**不得**重放历史进 context。

> ⚠️ **未闭合（承上游）**：接近 100 万 token 上限时的 compaction 行为未测（实测 compaction 事件计数为 0，**不可据此断言无此机制**）。协议侧只要求能转发 `session/compaction` 事件，**不对其行为作承诺**。

## 7 鉴权

| 项 | 一期做法 |
|---|---|
| 载体 | `Authorization: Bearer <token>`（SSE 连接用同头；若浏览器 `EventSource` 不便带头，退化为 query 参数 ＋ 短时效） |
| 获取 | `auth/login` ⇒ 长期 token（个人项目单用户；**token 轮换 ＋ 限额作兜底**） |
| 存储 | 前端存本地（PC 端 Tauri 安全存储 / 移动端浏览器 localStorage） |
| 多设备 | 同一账号可持多 token，**逐个可吊销** |

⛔ **Tier0 红线（本设计稿的硬边界）**：
1. **LLM key 只在云端**，绝不进前端、绝不进事件流、绝不进日志。前端**永远**看不到任何上游凭据。
2. **多用户 / 租户隔离须自做**（C5）——一期单用户，但**数据模型从一开始就带 `ownerId`**，避免二期改造。⚠️ 官方网关内置的 token→签名 cookie 只解决"是不是本机发起的"，**不解决"这是谁的数据"**。

## 8 多端同步

**模型**：每个设备一条 `/a/stream` 连接；server 按 **`(ownerId, sessionId)`** 把事件**扇出**给所有订阅者。

| 场景 | 语义 |
|---|---|
| 设备 A 发 prompt，设备 B 同时在看 | B 通过扇出看到同一事件流（**无独立状态**） |
| 多设备同时发 prompt | **server 侧串行化**（对齐"runtime 单会话"）⇒ 后来者排队，**不并发进 DSH** |
| 设备加入 / 离开 | `session/subscribe` ／ `session/unsubscribe`（订阅粒度 = 会话） |
| 设备离线一段时间后回来 | 走 §9 补帧 |

⛔ **不得让两个设备各自持一份会话状态**（那会造出"同一会话两个真相"）。**单一真相在 server**，前端是投影。

## 9 重连补帧

**机制**：SSE 每条事件带**单调递增 `seq`**（作用域 = 会话）。

| 情形 | 行为 |
|---|---|
| 断线重连 | 带 `since=<lastSeq>` ⇒ server **补发** `(lastSeq, now]` 的事件 |
| 补发窗口够 | 正常补齐，无感 |
| **窗口不足**（超出服务端环形缓冲深度） | server 发 **`stream/gap`** ⇒ client 走 **`session/open` 快照重建**（**不是**重放全部历史进 LLM —— C2） |
| 心跳 | `stream/ping`（2 s，对齐官方）⇒ client 侧 `stale` 判定阈值建议 3×心跳 |
| 长时间离线 | 与"窗口不足"同路（快照重建） |

**关键设计点**：
1. **`seq` 与"消息 id"是两件事** —— `seq` 是**信道序号**（用于补帧），消息 id 是**业务标识**。⛔ 不得混用。
2. **环形缓冲深度**须可配（默认建议 1 000 条 / 会话），超窗走快照而不是无限增长。
3. **补帧必须幂等**：client 按 `seq` 去重（同一 `seq` 收到两次不得渲染两次）。

## 10 C 段 · 本地工具反向执行

**承载**：**复用 §4.3 的反向请求层**（`tool/execute`）。这是本设计稿的一个**架构统一点** ——
「审批要人答」与「工具要 PC 执行」**在协议上是同一件事**（server 向 client 要一个结果），只是 `method` 与超时策略不同。⛔ **不要为 C 段另造一套反向信道。**

| 项 | 语义 |
|---|---|
| 方向 | server → **PC client**（有本地文件 / 命令能力的那端）；移动端**不接**此类请求 |
| 请求 | `{id:'s-<n>', method:'tool/execute', params:{toolName, callId, args}}` |
| 结果 | `{id:'s-<n>', result:{ok, output\|error}}` |
| PC 不在线 | **fail-closed** ＋ 落日志（不得静默失败、不得假装成功） |
| 超时 | 由 server 侧 pending 计时（业务侧），落 `unavailable` 语义 |
| 体积 | 长输出走 `/a/blob/:ref`，**不塞事件流** |

⚠️ **与"本地副作用"的边界**：C 段工具操作的是 **PC 本机的文件 / 命令**（见 `local-env.md`），因此**只能在 PC client 上执行**；移动端即使收到同类请求也必须拒绝并报错（**不得试图在浏览器里模拟**）。

## 11 与 B 段的接线（driver）

### 11.1 driver 是什么

**driver = 3.3-b 的薄客户端骨架 ＋ A 段服务侧的会话管理**（`TODO.md`：3.3-b 的薄客户端 = 本段 driver 的骨架，**勿另起一套**）。

现成可复用的部分（`harness/scripts/33b-thin-client.mjs`，已实测通过）：

| 复用点 | 说明 |
|---|---|
| 自己 `spawn` dsh ＋ 自构启动参数 | ⛔ **不能复用 `HarnessClient`**（它内部只挂 `onNotification`、**无 `onRequest`**） |
| `new JsonRpcLineTransport(child.stdout, child.stdin)` | 传输层用官方公开导出件 |
| **`onRequest` 挂载点** | **判据的落点**：DSH 出站请求在这里被接住 |

| `AbortController` ＋ `transport.request(…, signal)` | 请求侧中止语义（C9 路 a） |
| 双侧留痕纪律 | ⛔ 单侧自述不算证据 |

### A 类 · 不补会返工（5 条）

**A1 ⛔ §4.3 缺「反向请求的撤回与结清」这一整块 —— 它是 3.3-b J5 在 A 段的对应物。**
- 问题：§4.3 只写了「撤回后不得再结算」，但**没有"撤回"这个动作本身的承载**。D1-a 下 SSE 只能下发、POST 只能上行 ⇒ 撤回必须也是一条**下行帧**。现在前端**无从知道**卡片已作废，只会一直挂着。
- 依据（3.3-b `lateabort` 臂实测）：DSH 侧 `req.signal` 中止 ⇒ 出站 pending 条目**被移除**；对端**迟到的 `allowed-once` 被丢弃**（该帧之后的采样恒 0）；结果恒 `cancelled`。A 段要复现同一语义，缺三样：① 下行撤回帧；② client 侧 pending 按同一规则清理；③ client 迟到回帧到 server 后**不得结算**。
- 建议：加下行通知 `stream/cancel {id:'s-<n>', reason}`；§4.3 纪律扩成三条 —— **撤回即清 ／ 迟到丢弃 ／ 回帧被拒要能区分「未知 id」与「已知但已结清」**（见 B3）。

**A2 ⛔ §5 缺「终局结果的扇出」—— 多端（§8）下 B 设备那张卡永远不会关。**
- 问题：§8 只说事件按 `(ownerId, sessionId)` 扇出；§5 没定义「某个 `s-<n>` 已被 A 设备答掉 ／ 已被 server 兜底」这一**终局事件**。⇒ B 的卡片挂着不走，B 再答一次还会撞 pending。
- 建议：加下行通知 **`approval/decided {requestId, outcome}`**（与 DSH 侧审计事件**同名同义**，正好三侧对账），扇出给该会话全部订阅者；前端收到即关卡。

**A3 ⛔ §5.4 缺「人主动放弃」的词汇归属；且前端不得自有超时。**
- 问题：§5.4 把「前端不答」归 `unavailable`，但**人主动点"拒绝／放弃"**落哪个词没写。按 C9 口径，`cancelled` 在 DSH 词汇里**专指请求侧中止** ⇒ 前端**不能**用它。
- 建议写死：① 人主动放弃 ⇒ **`rejected`**（人做了"不放行"的决定）；**没人应／通道断** ⇒ `unavailable`；② **超时权威只有一个 = server 侧 pending 计时**，前端拿到 `expiresAt` 只许渲染倒计时、**不得自行判超时**（否则两侧词汇竞争，A 段会重演 3.3-b 那处「两路混淆」）。
- 附带：server 侧 pending 超时**应写成产品参数并进本文**（建议 120 s 级）；⛔ **不得**拿 B 段那两张表（请求侧 signal ／ 答者侧自建）来顶替 —— 那是 DSH 侧的事，两段各有各的表。

**A4 ⛔ `session/open` 的参数撑不住 §6-③ 与 §9 的「快照重建」。**
- 问题：§4.1 是 `session/open {sessionId}`；§6-③ 要求「对 hot 会话只回状态与增量」，§9 要求「gap 后走 open 快照重建」。**同一方法要两种语义，参数里没有区分位。**
- 建议：`session/open {sessionId, sinceSeq?}`：缺省 = 全量快照（**带 `snapshotSeq`**），给了 = 增量；并把「**重建后的续播基准 = `snapshotSeq`**」写死，否则重建与实时流错位、§9-1 的 `seq` 会串。

**A5 ⛔ §4.1 的 `auth/login` 没有凭据 —— 一期也是"门没锁"。**
- 问题：`auth/login {deviceLabel}` ⇒ 打到这个端点就能换 token；而 §3.3 的生产形态是「loopback ＋ 反向代理」⇒ **它对公网可见**。这与 §7 的 Tier0 红线（前端看不到上游凭据）不冲突，但等于没锁门。
- 建议：`auth/login {deviceLabel, pairingCode}`（部署期生成、一次性／可轮换）；或取消该端点、初始 token 由部署注入；并对该端点**限速 ＋ 失败计数**。（多用户二期再升级为正式登录，§7 的 `ownerId` 那条仍照做。）

### B 类 · 须写死，否则两侧各写各的（4 条）

**B1 §3.2 的「整套复用薄客户端骨架」要收窄成「复用语义、不复用类本体」。**
- `JsonRpcLineTransport` 是**行分帧**（`\n` 切帧）；A 段是**每事件一帧**（SSE `data:` ／ HTTP body）。⇒ `onRequest` 单挂载、`id` 关联、清空 pending、`AbortSignal` 语义**可复用**；`new JsonRpcLineTransport(...)` **本体不可直接用**。
- 同时把 id 规则钉死：统一**字符串**；`requestId`（§5.3）**不得**挪用作帧 `id`；**重连后旧 id 一律作废**（见 B3）。⚠️ 顺带：3.3-b 的 `requestId` 是**进程内自增**（`remote-1/2/3`），**重启即复用** ⇒ 它只能做**单次运行内**的对账键，跨重启的线上对账键须另定（建议 `sessionId` ＋ uuid，或 `(deviceId, seq)`）。

**B2 §3.3／§4.3 要把 HTTP 状态码语义定死。**
- `/a/rpc` 的 HTTP 层**只表达传输**（200 / 401 / 429 / 5xx）；**协议错误一律 200 ＋ JSON-RPC error 帧**（`-32601` / `-32603`）。unary 请求回 `{id,result|error}`；notification／response 帧回 **202／204 空体**；**回一个已结清或未知的 `s-<n>` ⇒ `409`**（前端据此判"server 已忘记"）。
- ⚠️ 若反过来用 404 表达 `-32601`，前端要写两套错误处理，且 3.3-b 那条「协议错误要能追溯到原始帧」的负向对照会失去落点。

**B3 重连后未结清的反向请求怎么办 —— 必须分两类，不得一刀切。**
- `approval/request`：**可重问**（幂等、无副作用）⇒ server 用**新 `s-<n>` 重发**，client 按 §5.3 的 `requestId` 去重、复用同一张卡。
- `tool/execute`：⛔ **绝不能自动重发**（可能重复写文件／重复执行命令，非幂等）⇒ 旧 id 一律判 `unavailable` ＋ 落日志 ＋ 提示"需人工重发"。
- 这条差异本文没有，但它是 §5 与 §10 **共用一个反向层之后最容易出事的地方**。

**B4 §9 的环形缓冲要「双上限」；§3.3 的 `/a/blob/:ref` 要写全三件事。**
- 缓冲：**同时**限**条数**与**字节**（大 delta／长工具输出会撑爆）。建议默认 1 000 条 **且** 8 MB／会话，超任一项即算"窗口不足" ⇒ `stream/gap`。

### G 类 · 判据的假绿风险（5 条）

**G1 ⛔ M1-① 「打开看看不触发 LLM」若只判"日志里没有 `turn/start`"，是把"没有"当"没发生"。**
- 风险（**本项目已实测过同款**）：我 3.7.x 探针判据轮实测到 —— **子串型判据测的是"存在"，不是"发生"**（`exit 0` ／ stdout 字节 ／ 通知条数 ／ 旧 boot 探针**全都不可分态**）。同理：日志里**没有** `turn/start`，既可能是"没跑"，也可能是**"该变体的日志根本没写"**／写到了另一路径／行类型名随版本变了。
- ⚠️ **我昨天刚在同一类坑里走了一趟**（`DSH-3.7.4-T·P`）：`logPresent=false` 这条判据，我**无法只凭它**断定"落盘被拒"，只能靠**装置外的独立通道互证**才敢归因。M1-① 的判据结构**与它同型**。
- ⇒ **替代写法（三条同时要）**：① 负向对照必须含**阳性证据**——同一会话在**真跑一次 prompt** 时日志里**必须出现** `turn/start`（证明"该路径的日志机制在工作"）；② 用量侧另给一条独立锚（Trae D2 的 token 账作**主判据**、日志作**辅**）；③ 判据写明**日志路径 ＋ 行类型取自哪个版本**（版本漂移会让子串判据静默失效）。

**G2 ⛔ M1-② 「断线重连后无缺无重」的"缺"缺少独立期望值 —— 会自证。**
- 风险：若"应有多少事件"来自**同一条流**（含服务端自报），则"无缺"是**自证**。且"**造断线**"的方式未写死 —— 停服务／杀 TCP／断网／切后台**语义不同**（服务端是否察觉、环形缓冲是否继续、`Last-Event-ID` 是否被浏览器送出都不同）⇒ 不同造法会给出**不同的绿**，而"绿"看起来一样。
- ⇒ **替代写法**：① 期望值取**双侧独立计数**（服务端落 `(seq, 事件类型)` 表 ＋ 客户端落收帧表，**两处交叉**；Trae 已有"单侧自述不算证据"的纪律，此处正是它的用武之地）；② 断线造法**写死一种**并注明平台（PC Tauri ／ 移动浏览器行为不同）；③ 补一条**"链路确实是活的"锚**——我在 T-2 的做法：每个变体必须给"链路起来了"的独立证据（如 `②_activated/injectFired/toolRegistered` 三项），否则"没收到事件"与"没连上"不可分。

**G3 ⛔ M2-② 「逐条落对词汇」若只看前端收到的词，测不到链路语义；且四路可能有"不可分态"。**
- 风险：**判据要能分态才算判据**。若四条失败路里有两路落**同一个词**（如 §5.4 的 (b) 与 (d) 都落 `unavailable`），那么"落对词汇"这条判据对它们**没有区分力** —— 绿了也说明不了"识别出了是哪条路"。
- ⇒ **替代写法**：① 除"落哪个词"外，**加一条"原始帧可追溯"**（呼应 §5.4 自己那条"协议错误要能追溯原始帧"）——每路必须给出**触发原因**的独立痕迹（谁超时 ／ 谁消失）；② 四路的**触发装置**写在判据旁（否则无法复跑）；③ 保留 M2-③ 那条负向对照（**它是对的**：不装答者 ⇒ `unavailable` ＋ 动作 0 次）。

**G4 ⛔ M2-③ 与 §10 的「动作 0 次」必须从被保护对象取证，不能从链路取证。**
- 风险："我没收到请求"／"我回了 error"**都不等于**"动作没发生"。§5.5 自己把这一点说得很准（静默 fail-closed ＝ 假绿源），但 §12 的判据没有落到**被保护对象侧**。
- ⇒ **替代写法**：在**被保护对象上留一个"若执行必然留下"的痕迹位**，读它。⚠️ 对 §10（C 段**真执行本地文件操作**）尤其硬：fail-closed 的判据必须是"**目标文件真的没被创建／命令真的没留痕**"。⇒ 我在 T·P 里的做法可直接照搬：**产物清单 `entriesAfter` 为空**才算"零落盘"，而不是"收到了错误响应"。

**G5 ⛔ §12 全部判据缺「通道四元组」—— 本协议的通道维度比本机测试更多。**
- 风险：我在 T·P 里被要求每条结论注明 **通道 ＋ 运行时 ＋ 身份 ＋ 文件系统**，因为**同一段代码在不同通道下语义可以相反**。A 段的判据横跨 **PC（Tauri）／移动浏览器／云端**三类执行环境，维度只会更多（浏览器引擎 ／ 是否过反代 ／ 网络路径）。
- **可引用的实证（不是理论担忧）**：`chmodSync(dir, 0o500)` 这条破坏动作，我实测在 **Windows 上完全不成立**（落成 `0o444`，写入照常成功）、在 **Linux 上成立**（`EACCES`）—— **同一行代码，语义相反，且装置自身不报错**。⇒ 本项目的"本机验过"与"生产成立"之间的距离**已被实测过一次**。
- ⇒ **替代写法**：§12 每条判据后附「**该判据在哪个通道上成立**」，并明写 ⛔ **不得把"本机绿"写成"协议成立"**（生产 = Linux ＋ 反代 ＋ 跨网络，与开发机不同）。§13 也应把"通道"列入未验项（现在只列了 POSIX 一条）。
