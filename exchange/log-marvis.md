## P4.35 界面基调初稿（产品视角交付，2026-08-15）

### 0. 产品调性（先定调，约束后面所有选择）

LarryAgent 是个人效率工具，不是社交产品，也不是"ChatGPT 套壳"。三个词：**克制、专业、可信赖**；核心美学目标一句话——**克制的高级感**（中性灰阶、低饱和、靠层次与留白，不铺彩色）。

- 克制：界面服务于"快速进入对话"，不过度装饰、不炫技
- 专业：信息层级清晰，工具调用过程可见（Agent 产品的差异化，区别于普通聊天）
- 可信赖：暗色基调 + 稳定语义色，传递"私人助理"而非"玩具"的感觉

### 1. 布局结构

左会话栏 + 右消息流，成熟模式，不创新。

- 左栏：会话列表（含角色标识），默认 260px、可折叠
- 右主区：消息流（上）+ 输入区（下）
- 顶部：会话标题 + 角色切换入口

响应式（产品要求，非具体断点）：桌面双栏；移动端左栏收为抽屉/底部导航、右主区全宽，核心对话流程不断。断点具体数值归 UI Designer。

### 2. 配色基调

**暗色为主，亮色后置**（P4 只做暗色）。理由：个人助理类工具暗色耐看、长时间不疲劳，且 chat.html 已有暗色基因，精化而非推翻。

- 主色：偏克制的灰（中性灰阶，靠灰度深浅建立层次），**替代 chat.html 的霓虹绿**；不设大面积彩色主色
- 用户气泡：灰阶中偏亮一档（归属感）；AI 气泡：中性灰（不抢焦点）
- 语义色：成功/警告/错误保留标准三色，仅状态出现时使用、不常驻
- 彩色只作"可辨识的视觉点"（角色标识、状态），不铺大面积

具体色值交 UI Designer 精化为 token（定案见 UI-Reference §1），产品只定方向。

### 3. 字体

中文为主场景，字体栈优先系统中文（Microsoft YaHei / PingFang SC），英文数字用 Inter/SF。字号：正文 14px、标题 16-20px、辅助 12px；中文行高 1.6 舒适区。

### 4. 组件风格

统一约定（基调，非设计系统）：圆角/间距/阴影/过渡统一为 design token，由 UI Designer 落成 CSS 变量。

- 气泡：用户右对齐主色、AI 左对齐中性色
- **工具调用卡片（灵魂组件）**：可折叠，展示"工具名 + 状态（执行中/成功/失败）+ 结果摘要"。让用户"看得见 AI 在干什么"——呼应原则 4（明确安全边界，让用户知道 AI 的动作）
- 输入框：多行自适应，Enter 发送 / Shift+Enter 换行
- 侧栏条目：会话标题 + 角色色点 + 时间

### 5. 多角色差异化呈现（重点）

**产品意义**：记忆系统 + 多角色是 LarryAgent 区别于"ChatGPT 套壳"的唯一壁垒。差异化不是装饰，是"让用户一眼知道现在在跟谁对话、这个角色是干什么的"的心智锚点。

方案（轻量，不做三套换肤）：

| 角色 | 标识色 | 语义 |
|---|---|---|
| default | 中性灰（无彩） | 通用、中性、可靠 |
| health | 低饱和绿 | 温和、可信赖（健康语义） |
| finance | 低饱和琥珀 | 专业、警觉、数据驱动（金融语义） |

落地方式：侧栏条目角色色点 + 顶部角色专属问候语 + AI 气泡左侧色带 + 工具卡片 header 色跟随角色 + 切换时轻微过渡（色带 slide + 问候语 fade）。

**明确不做**：三套完整主题换肤（成本高、维护噩梦，违背"成本不能上天"）。

**理由**：差异化要"可感知但不喧宾夺主"。用户核心诉求是高效对话，不是换皮肤。轻量色标识 + 问候语足以建立"角色切换"心智，且不增认知负担。

### 6. P4 首版功能优先级（产品视角补充）

- **必做**：会话列表（增/删/切换）、消息流（SSE 流式 + 工具调用卡片）、输入框、角色切换入口
- **后置**（P5 或后续）：记忆管理 UI、设置页、亮色主题、logo/图标资源

## 提案：项目交流「名词解释 / 规范用语」机制（2026-09-03，待讨论）

> 背景：随项目进入复杂打磨期、反复讨论功能状态，交流成本上升。老大征询是否有必要建立统一术语机制。若有推进，后续单独讨论，本提案仅记录方向，不作为正式派发。

**现状结论**：全仓库（exchange/TODO/HUMAN 等）无任何术语/命名规范/黑话消歧落点（grep 零命中）。缺的不是规则而是"词典"——规则已分散在 exchange/README、ai-governance、ui-reference 及各 log-*.md，同物异名、约定散落、讨论后不沉淀是三个主要成本源。

**建议方向（最小可行版）**：
- 定位：不新建"要主动去读"的治理文件，做**消歧索引**寄生在现有必读文件（如 exchange/README.md 内嵌或独立 glossary.md 强链接），避免沦为没人读的散落文件。
- 内容三块：共识术语（标准词+定义+关联文件）／别名映射（黑话→标准词）／命名约定（写代码/文档强制叫法）。
- 触发规则：**只收录实际发生过歧义或重复解释的词**，不预建全集；从 3~5 个反复争论的真实痛词起步。
- 维护：沿用"谁创建谁维护"，WB 定期收口，入 TODO 低成本项。
- 成功判据：下一次跨 AI 讨论提到该词不需再解释一遍；2~3 轮无人消费则回退位置，不堆条目。

**待讨论点**：是否需要做、挂在哪个文件、首批收哪几个词。等老大安排。

## README 定位段补充意见（2026-09-06，产品层，待 WB 整理）

> 背景：老大把 LarryAgent 定位重写进 README 开头，分「能力 / 约束 / 可见性 / 质量 / 形态」五维。老大要求我补两件事：① 为满足预设目标还缺哪些值得列的维度；② 已做/在做/在讨论/在计划但没列出的方面；并检查条目是否混乱、是否需拆分合并。以下为我的看法，供 WB 整理进 README 或定位文档。**注意：本次探讨限定产品层，不含项目实施与协作机制。**

### 一、值得列但没列的（按预设目标"云部署、多端、长期自用"反推）

1. **数据 / 数据主权（最大缺口，缺的是维度）**：云部署意味着对话/记忆/文件访问记录上云，个人项目最在意"数据最终归自己、能迁出、能销毁"。现有"行为安全约束""云/端边界"都没正面回答数据主权。建议条目：数据自托管与归属、导出/备份/迁移、彻底清除能力、key 与凭据存放边界。
2. **可靠性 / 连续性**：云部署单点故障 + 模型厂商 API 波动会直接让助手不可用。建议显式承诺或规划：模型失败降级与重试、"多模型按需切换"升华成冗余手段、依赖（LLM/搜索）不可用时的降级路径、数据备份恢复。
3. **可扩展性（横切维度）**："能力"目前是功能清单，缺"怎么低成本扩展"的承诺：OpenAI 兼容 provider 抽象、工具可插拔注册（registry 已是该形态）、新增能力不上天花板。
4. **个性化 / 可定制程度**：已有"角色切换"，但缺"用户能否自定义角色提示词、开关工具、调记忆强度"——决定产品是"给定功能的助手"还是"个人助理框架"。
5. **成本 / 用量可见**："可见性"目前只有信息可见 + AI 行为可见，缺成本可见。约束里有"使用成本管理"，但看不到花了多少，管理是盲的。
6. **端侧能力边界（离线/降级）**：shell 与文件读写是端侧能力（PC 不上云），移动端跨端时是否可用/降级是产品差异点，值得在形态下点明"能力按端分布"。

### 二、已做/在做/在讨论/在计划，但定位段没露面的（均产品层）

1. **记忆的归档与回收站机制**（已做，P4 收尾）——会话↔记忆两层合一归档、可编辑摘要、恢复/彻底删除。README 只写"长期记忆"，没写"记忆怎么被管理"。
2. **记忆浏览器 / 记忆可视化**（讨论中，远期）——对应"记忆库能否直观分析"，是"沉淀信息可见（可管理）"的具体产品形态。
3. **工具集实际组成**（web_search / shell / file_ops 均实现）——定位段只有"工具挂载"能力级表述，没体现"联网检索"这个对用户感知很强的新能力。
4. **记忆隔离（多角色数据隔离）**（计划中，P5 前架构债）——角色间记忆是否互见是用户可见行为设定，值得列。
5. **shell 白名单化 / 工具权限分级**（计划中，架构债）——"行为安全约束"的落地形态，建议在约束里点名"工具执行最小权限、白名单"。
6. **统一 UTC 存储 + 本地时区注入**（约定已定）——时间链路细节，归属"质量-时间感知"，不必单列。
7. 移动端 HTML5、云/端边界草案、部署架构——README"部署定位"已覆盖，信息完整，无需补。

### 三、结构诊断（混乱点 + 拆分/重组建议）

**真实存在的混乱点：**

1. **「约束-行为安全约束」与「可见性-AI 行为可见」语义交叉**：安全约束的落地手段恰恰是行为透明可见，同一主题分置两维，像两件事。
2. **「质量」维度单薄且与「能力」边界模糊**：时间感知本质是补时间信息维度的能力增强，放"质量"更像"体验质量"。当前只有两条，撑不起独立维度。
3. **「能力」里"长期记忆"与"知识库"未区分**：长期记忆=对话归档摘要（个人经历），知识库=导入外部文档（RAG）。技术上都是向量检索，产品语义完全不同，混着写易误读。
4. **「能力」并列粒度不一**：多模型/工具/角色是"能力类型"，用户画像/会话管理是"数据组织方式"，不在同一抽象层。
5. **「约束」只有两条，偏薄**：成本、安全之外，"资源与频率限制（防失控循环）""凭据保管"也属于约束。

**拆分/重组建议（最低扰动版）：** 五维骨架清晰不必推翻，只做三处：

1. **新增一个维度**承载数据主权与可靠性（备份/迁移/降级）——最大结构缺口，放「形态」后置或独立均可。
2. **「质量」二选一**：扩成"体验质量"（时间感知、超长会话一致性、响应质量等），或降入「能力」，别让空壳维度。
3. **「能力」内部分组**：按"能力类型（对话/检索/工具/记忆）"和"数据与个性化（会话/画像/知识库）"分组，并把"可扩展性/可定制"显式写进去。

**一句话总评**：五维方向对，但按"云部署、多端、长期自用"反推缺了"数据主权/可靠性"这个大维；质量、约束、可见性三处有交叠可收口；能力清单回答"有什么"，建议再回答"能扩到什么程度、用户能定制多少"。
