### 1 · `archive-closed-todos` —— 待办块归档瘦身（归档归你后主用）

**何时用**：「TODO 太长瘦一下」「该归档的归档」「把已完成阶段归档」。
**核心纪律**：
1. **只搬「块内 `[ ]` = 0」的块**，程序化核（别肉眼）——整段标着 ✅ 但块内还有 `[ ]` 的**不搬**。
2. **正文逐字迁出、零改动**——归档区是**锁定快照**，不进讨论、不勾状态、不就地更新。
3. **归档一次成形**，别分几次进（分次会在锁定区留半截）。
4. ⭐ **收件判据是「是否仍被引用」，不是「是否闭环」**——判据类内容仍活跃的，**先落 `docs/` 再搬**（直接搬＝把活跃判据埋进冷存，且原块那句「权威落点 = docs」会变空指）。
5. ⭐ **正确顺序：先归位（判据→docs）→ 再落位（未决→TODO）→ 后搬家（TODO→archive）**——颠倒会把未决项**冻在快照里**。

### 2 · `apply-proposal-to-doc` —— 提案稿/讨论稿套进权威文档 ＋ 退役草稿（docs 归你后主用）

**何时用**：「把 XX 稿应用到 YY 文档」「套用这份提案」「按这份编辑清单改」「他们都加了意见，融合后定稿移入 docs」。
**核心纪律**：
1. ⭐ **先定稿件性质**——内容稿（成品内容，可整段搬）vs **编辑指令集**（逐条「现状原文→建议改后」）。指令集若按"合并"字面理解 ⇒ **造出双份"现状原文"**，成为后续漂移源。
2. **锚点用内容前缀匹配，不用行号**（行号会因他人编辑漂移）；⚠️ 锚点串**从目标文件里读**、不手抄进脚本（差一个字符就 SyntaxError，且前面步骤一行没跑）；表格行有前导缩进，`startswith` 会 0 命中。
3. **脚本化 + 双断言，失败即不落盘**：锚点命中数 `== 1`、批量插入计数 `== 预期；清单逐条独立，不写复合替换。
4. ⭐ **出稿方的清单必查漏项**——自己重扫目标文件 + 相邻文档（实测：清单列 2 处联动，我查出第 3 处）。
5. **转写残留五查**：外部路径（别原样搬进本仓）｜草案口吻（"抄进本条"→正文口吻）｜枚举结构（分号枚举别插散）｜符号一致性｜列表连续性（插入块空行会切断列表）。
6. **退役前置查反向引用**（三类：**承重引用**→同批改指已套用的目标文件、**索引条目**→同批删、**工具自生成缓存**→先核 `git ls-files` 未跟踪）；扫描面**必须含非文档文件**。
**⭐ 多方评审融合六步（顺序不可换）**：① 先按原样提交一版存档（**含全部意见**，提交信息逐方列条数）→ ② 核意见里的外部事实论断（逐条回源、注明通道；**通道不同结论不可互推** ⇒ 写成未验项＋重测建议，不直接采信/推翻）→ ③ 三档处置各自留痕（吸收→标注「v1.x 新增」／部分吸收→写清采纳哪半／**不吸收→必须给理由且落在正文可找到处**）→ ④ ⛔ **删意见前先扫「正文对附录的引用」**（同一文件内引用，实测踩过：正文写「Trae 附录 A·C1」，附录一删即成悬空）→ ⑤ 核稿件本体之外是否还有副本（各方 log 里可能也贴了）→ ⑥ 定稿落位＋同步索引＋提交，正文留「含意见的存档版本 = git `<hash>`」。
**复检**：删块后查连续空行；**加粗奇偶必须程序算、且先剔行内 code span**（glob 会被数成加粗）；**改措辞前先全库 grep 同名表述**（同一矩阵常有多处副本，只改一处＝两套口径）。

### 3 · `doc-governance-recheck` —— 删减/搬家/归档的**事后复检**（你做动作后自检 ＋ 我复验你时共用）

**重心＝查「删掉/搬走的东西有没有承接」**，不是核对改动文字本身。
- **承接 4 条**：删项逐个 grep 承接（`[x]` 已完成项是**搬家**不是删除）｜清交流区前先做「承接转登」｜**「建议改 XX 文档」前先核那个载体存在**（没有载体＝空转，却在清单里看着像待办）｜核承接**拿被移条目的独有细节去 grep 目标段**——只命中名字不算（实测：段名该含"进入前"，实则只含"开门之后"）。
- **引用完整性 3 条**：搬家后**反向 grep 旧落点**（实测一次揪 5 处静默悬空）｜一处明细变动先想「还有谁在别处描述这件事的形态」｜**代码注释里的「事实名」不随文档归档失效**（判别：指向**文档坐标**才改，指向**物自体**〔源码/提交/装置〕不修）。
- **面板不变量 4 条**：✅/[ ] 标记不变量**程序化**｜「延后项收回」是**三处同步**（段首说明＋上游汇总口径＋条目本体）｜「某段已收口」是**带时间戳的断言**——其后任何"段外新增"都会让它过期｜**段内挂 `[ ]` 两种相反成因**（状态标记过期→摘框 ／ 真实在飞项→**保留 `[ ]` 只更新内容**），判别法＝「这条现在还有没有人在干活」。
- **编辑卫生 4 条**：提交前扫凭据｜**提交前必重新 diff**（老大实时改文件，快照会过期）｜**「改状态」与「删内容」是两种动作**，混在同一次编辑里越界不报错｜**大块替换前核覆盖区间有无常设内容**（实测一次 Edit 吃掉「通用纪律 6 条」）。
- **挂起复查**：「等待某条件」的条目，条件一旦满足必须回头改它（实测：一条挂"待复核放行后可改"，而该件早已通过复验 ⇒ 僵死）。

### 5 · `design-verifiable-criteria` —— 判据四问（你写 docs 判据/验收基准时用）

把「验证 X 生效了」展开成**可复算**条款，缺一问就不可复算：

| 问 | 防的坑 |
|---|---|
| ① 作用在哪一层？ | 存在「天然为真」的层 ⇒ 判据被自动满足（如 append-only 存储里"原文还在"恒真） |
| ② 用什么计量口径？ | 比例/绝对值/节点数多套并存 ⇒ 同果异判 |
| ③ 结果态都能区分吗？ | 失败态与「未发生」同形 ⇒ 失败被读成没触发；须从旁路取并规定 fail-loud |
| ④ 在哪个视图上断言？ | 在中间表示上断言 ⇒ 证明不了最终效果 |

**铁律**：判据必须站在「能被自动满足」的**对立面**｜失败态必须 fail-loud｜软阈值用**数量级报警**不用精确区间（精确区间制造虚假精确）｜每条须给「**不写死的后果**」｜**判据的权威落点唯一**（多处出现时指定一处为权威，其余只留指针）。
