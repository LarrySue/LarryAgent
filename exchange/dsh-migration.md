## 零、项目情况简介（供未介入本项目的 AI 参考）

> 本节为自足背景，目标读者是**完全未参与本项目**的外部 AI——读到这里即可对「这是什么项目、为什么讨论时间上下文」形成完整理解，无需再翻其他文件，Trae、Claude、Marvis、Workbuddy、Qoder可忽略此部分。

**LarryAgent 是什么**：个人 AI Agent，单人使用、**第一版起即面向云部署**（当前本机仅开发+测试环境，尚未达到第一版发版）。PC 版为 C/S——client 在本机不上云（选 C/S 而非 B/S 为本地文件操作能力）、server 部署云端；移动版为 B/S。核心能力三件：管对话、有长期记忆、能调工具（读写文件 / 执行命令 / 联网搜索）。技术栈 **Python FastAPI + SQLite + ChromaDB + Vue 3 + Tauri + HTML5**（PC 端 Tauri 壳，移动端 HTML5 规划中）。

**多角色机制**：对话由「角色」驱动，每个角色 = 一套 system_prompt + 可选工具组合。当前有 `default`（通用）/ `code`（编程）/ `health`（健康）/ `finance`（金融）/ `science`（科学）五个角色，角色清单由后端 `config.yaml` 统一管理、经 `GET /api/roles` 下发前端动态渲染。

**记忆系统现状**（本讨论的地基）：

- **短期记忆**：对话消息存 `messages` 表（SQLite），按会话组织。
- **长期记忆**：会话归档时，把整段对话交给 LLM 摘要成单条 summary → 写入 `memories` 表（SQLite）+ 向量化入 ChromaDB。**双写结构：SQLite 是真相源，ChromaDB 只是可重建的索引**。
- **召回**：新对话时按语义相似度从 ChromaDB 检索相关记忆，拼进上下文。

## 二、DSH 事实画像

> 来源：2026-09-06 WebSearch + 公开资料（DeepSeek 官方仓库 `deepseek-ai/deepseek-harness`、官方站 `deepseek.com/harness`、技术社区解读）。
> **注意**：star / fork 各源口径差异较大（65.6k ~ 137.1k），不作为判断依据，此处不录。

| 维度 | 事实 |
|---|---|
| **是什么** | DeepSeek 官方开源 **Agent Harness（智能体运行框架）**。官方公式 `Agent = Model + Harness` |
| **不是什么** | **不是大模型、不是推理引擎**（≠ vLLM / SGLang）。模型负责推理，Harness 负责对接环境、工具闭环、任务调度、权限管控、会话追踪 |
| **定位** | **架构通用、开箱偏编码**。内核无特权、连 Agent Loop 都可换 → 理论可做通用 Agent；但内置工具（文件读写编辑 / Shell / 代码解释器）与四模式**均围绕编码场景**设计，官方对标 Claude Code / OpenHands / Aider |
| **官方口径分歧** | 多数解读称"AI **编程** Agent Harness"；亦有解读明确「**不是单一编码助手**，而是可组装的智能体基础设施」——**并不矛盾**：架构通用 ≠ 开箱通用 |
| **口号** | Everything is a Plugin（万物皆插件） |
| **内核** | **Cordis** 插件总线（Koishi 生态插件内核） |
| **主语言** | **TypeScript**（Monorepo，`packages/` 下 40+ 包） |
| **许可证** | MIT |
| **创建 / 版本** | 2026-08-13 创建；当前 **0.1.0-rc.7**（2026-08-17） |
| **官方状态明示** | **developer preview**，README 加粗大写强调"会有破坏性变更" |
| **运行形态** | Web UI（`127.0.0.1:3080`，`npx @deepseek-ai/dsh web`）+ headless + **ACP** |
| **四模式** | `standard`（完整工具栈）/ `PTC`（程序化工具调用，省 Token）/ `minimal`（benchmark）/ `creative`（插件热加载） |

### 2.1 关键能力（按与本项目相关度排序）

1. **沙箱安全策略分级**（对应 #9）：`workspace-write` / `read-only` / `danger-full-access`；高危操作可人工确认；事件监听可加拦截策略
2. **会话持久化 + 上下文压缩**（对应 #13）：SessionEvent 追加日志，铁律"模型可见即已记录"；支持 **fork 分叉 / resume 恢复 / compaction 上下文压缩 / 回放**
3. **Trajectory 完整轨迹**（对应 #11）：思考、工具调用、返回结果**全记录**，比"工具名+状态+摘要"更完整
4. **结构化工具管道**（对应 #2）：前置策略拦截 → 沙箱守卫 → 审批 → 超时重试 → 结果规范化 → 后置处理
5. **多模型适配**（对应 #1）：内置 5 适配器（DeepSeek-V3 / R1 / OpenAI 兼容 / Anthropic / Ollama），可配置**多模型路由**
6. **子代理委托 + Skill**（对应 #3）：`spawn` / `fork` 两种子代理，支持后台任务与工作流编排
7. **真正的插件总线**：模型适配器、文件工具、Shell、Skill、会话存储、权限、主循环、UI 全部可插拔可热替换，副作用随卸载撤销

> **PTC 模式**（对应 #8，部分）：模型输出 TS 代码编排批量工具调用，减少 LLM 往返、省 Token。
> **ACP（Agent Client Protocol）**：headless 之外的自动化服务协议，是 B / D 路径集成的关键抓手。

### 3.1 读表结论（WB 读表，不拍板）

1. **DSH 的真强项三块：#9 安全审批、#13 超长会话、#11 轨迹可见**——都属"Agent 工程底子"，不是"产品功能"。其中 #13 恰是 LarryAgent **做法不对**的那一项，DSH 有现成正解（compaction 压缩，而非截断丢弃）
2. **四个零是硬边界**：#1（纯重叠）、**#6 用户画像、#7 知识库、#12 时间感知**。**其中 #6、#7 是你的真缺口，DSH 一概不管**——迁移了照样从零做
3. **#4 互补不替代**（最易误判）：
   - DSH 的 `session log` = **原始事件流水**（append-only，强在回放 / 审计 / 断点续跑）
   - LarryAgent 的 `memories` = **LLM 摘要 + 向量化**（强在跨会话语义召回）
   - **迁移 ≠ 获得记忆能力**——换底座后 memory 层仍需自建或双轨并存
4. **#5 注（重要的概念区别）**：DSH 的 sandbox 是**权限沙箱**（控制读写权限级别），**不是**"每个会话一个独立文件沙盒"——后者是 `HUMAN.md` 待办里 LarryAgent 自己的构想，DSH 未必提供
5. **#14 形态冲突**：DSH 的 Web UI 是**本地**形态（127.0.0.1:3080），而本项目要的是 server 上云 + 多端访问。DSH 不直接给，且形态需重新对齐
6. **约束组与可见性组最易被低估，但恰是 DSH 的主场**：#9（安全审批）与 #11（AI 行为可见）是它两大强项。**若只盯"能力组"七项评估，会显著低估 DSH**——它的价值更多在"让 Agent 干活干得安全、可追溯"，而非"能干多少种活"

## 四、对上次判断「完全不适合，也没有必要」的检验

两个**独立**判断，分开看。

### 4.1 「完全不适合」——**说过头了，需修正**

- 原判断依据："DSH = 编码 Agent vs LarryAgent = 通用助手 → 定位错配"。
- **三处事实修正**（2026-09-06）：
  1. DSH **架构通用**——无特权内核、连 Agent Loop 都可换，仅**开箱能力**偏编码（见 §2）
  2. LarryAgent 现有 5 角色**含 `code`**，功能范畴本就涵盖编程
  3. 对标产品 **QoderWork 是通用办公助理**，非纯编码
- 故"**完全**不适合"不成立。
- **但错配风险仍在**：DSH 的开箱能力与优化方向围绕编码场景，要做通用办公仍需自建插件——不是"不适合"，是"**不白给**"。

### 4.2 「没有必要」——**翻掉一半**

DSH 有三样 LarryAgent **现在没有、且自己造挺费工**：

| DSH 能力 | 对应条目 | LarryAgent 现状 |
|---|---|---|
| 沙箱分级 + 高危人工审批 | #9 | 仅有 IP 白名单 / 目录限制 / SSRF 拦截，**无审批、无分级** |
| compaction 上下文压缩 + resume + fork | #13 | 靠**截断旧消息**，做法相反 |
| Trajectory 完整轨迹（含思考） | #11 | ToolCallCard 仅"工具名 + 状态 + 结果摘要" |

> **但：值得借鉴 ≠ 值得迁移。** 借鉴 = 抄思路；迁移 = 换底座，成本差数量级。

## 六、绕不开的风险（无论选哪条路径）

1. **语言栈冲突**：DSH 是 TypeScript，LarryAgent 后端是 **Python FastAPI**。沾 A 或 B 即成本大头。
2. **preview 阶段**：`0.1.0-rc.7`、官方明示**破坏性变更**、项目仅 3 周大。把已过 P4 的 LarryAgent 押在 rc 框架上，返工风险实打实。
3. **记忆层不是搬家，是重建**（见 §3.1-3）：DSH 的 session log 是原始事件流水，LarryAgent 的 memory 是摘要 + 向量。**走 A 路径须重建 memory 层，或接受双轨并存**。

> 补充：上云共识是「PC 版 C/S，client 在本机、**server 上云**」。若走 A 路径，需与 DSH 的本地 Web UI 形态重新对齐（见 §3.1-5）。
