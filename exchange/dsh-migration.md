## 零、项目情况简介（供未介入本项目的 AI 参考）

> 本节为自足背景，目标读者是**完全未参与本项目**的外部 AI——读到这里即可对「这是什么项目、为什么讨论时间上下文」形成完整理解，无需再翻其他文件，Trae、Claude、Marvis、Workbuddy、Qoder可忽略此部分。

**LarryAgent 是什么**：个人 AI Agent，单人使用、**第一版起即面向云部署**（当前本机仅开发+测试环境，尚未达到第一版发版）。PC 版为 C/S——client 在本机不上云（选 C/S 而非 B/S 为本地文件操作能力）、server 部署云端；移动版为 B/S。核心能力三件：管对话、有长期记忆、能调工具（读写文件 / 执行命令 / 联网搜索）。技术栈 **Python FastAPI + SQLite + ChromaDB + Vue 3 + Tauri + HTML5**（PC 端 Tauri 壳，移动端 HTML5 规划中）。

**多角色机制**：对话由「角色」驱动，每个角色 = 一套 system_prompt + 可选工具组合。当前有 `default`（通用）/ `code`（编程）/ `health`（健康）/ `finance`（金融）/ `science`（科学）五个角色，角色清单由后端 `config.yaml` 统一管理、经 `GET /api/roles` 下发前端动态渲染。

**记忆系统现状**（本讨论的地基）：

- **短期记忆**：对话消息存 `messages` 表（SQLite），按会话组织。
- **长期记忆**：会话归档时，把整段对话交给 LLM 摘要成单条 summary → 写入 `memories` 表（SQLite）+ 向量化入 ChromaDB。**双写结构：SQLite 是真相源，ChromaDB 只是可重建的索引**。
- **召回**：新对话时按语义相似度从 ChromaDB 检索相关记忆，拼进上下文。

## 二、DSH 事实画像

> 来源：2026-09-06 WebSearch + 公开资料（DeepSeek 官方仓库 `deepseek-ai/deepseek-harness`、官方站 `deepseek.com/harness`、技术社区解读）。
> **注意**：star / fork 各源口径差异较大（65.6k ~ 137.1k），不作为判断依据，此处不录。

| 维度 | 事实 |
|---|---|
| **是什么** | DeepSeek 官方开源 **Agent Harness（智能体运行框架）**。官方公式 `Agent = Model + Harness` |
| **不是什么** | **不是大模型、不是推理引擎**（≠ vLLM / SGLang）。模型负责推理，Harness 负责对接环境、工具闭环、任务调度、权限管控、会话追踪 |
| **定位** | **架构通用、开箱偏编码**。内核无特权、连 Agent Loop 都可换 → 理论可做通用 Agent；但内置工具（文件读写编辑 / Shell / 代码解释器）与四模式**均围绕编码场景**设计，官方对标 Claude Code / OpenHands / Aider |
| **官方口径分歧** | 多数解读称"AI **编程** Agent Harness"；亦有解读明确「**不是单一编码助手**，而是可组装的智能体基础设施，用于构建各类 LLM 驱动的自主任务系统」——**这两句并不矛盾**：架构通用 ≠ 开箱通用 |
| **口号** | Everything is a Plugin（万物皆插件） |
| **内核** | **Cordis** 插件总线（Koishi 生态插件内核） |
| **主语言** | **TypeScript**（Monorepo，`packages/` 下 40+ 包） |
| **许可证** | MIT |
| **创建 / 版本** | 2026-08-13 创建；当前 **0.1.0-rc.7**（2026-08-17） |
| **官方状态明示** | **developer preview**，README 加粗大写强调"会有破坏性变更" |
| **运行形态** | Web UI（`127.0.0.1:3080`，`npx @deepseek-ai/dsh web`）+ headless |
| **四模式** | `standard`（完整工具栈：文件/Shell/网页检索/Skill/子 Agent 委派/任务规划）<br>`PTC`（程序化工具调用：输出 TS 代码编排批量工具调用，减少 LLM 往返、省 Token）<br>`minimal`（仅文件编辑 + Shell，用于 benchmark）<br>`creative`（运行时动态加载/热卸载插件，用于二次开发） |

### 亮点能力（按与本项目相关度排序）

1. **会话持久化 + 上下文压缩**（对应本项目 #8 真缺口）：SessionEvent 追加日志，铁律"模型可见即已记录"；支持 **fork 分叉 / resume 恢复 / compaction 上下文压缩 / 回放**
2. **结构化工具管道**（对应 #2）：前置策略拦截 → 沙箱守卫 → 审批 → 超时重试 → 结果规范化 → 后置处理
3. **多模型适配**（对应 #1）：内置 5 适配器（DeepSeek-V3 / R1 / OpenAI 兼容 / Anthropic / Ollama），可配置**多模型路由**
4. **子代理委托**（对应 #3）：`spawn`（全新子会话）/ `fork`（继承历史分叉），支持后台任务与工作流编排
5. **真正的插件总线**——模型适配器、文件工具、Shell、Skill、会话存储、权限、主循环、UI 全部可插拔可热替换，靠事件总线 + 服务依赖通信，副作用随卸载撤销
6. **沙箱安全策略分级**——`workspace-write` / `read-only` / `danger-full-access`，高危操作可人工确认
7. **面向代码优化**——目录挂载、增量 diff 改文件（避免 AI 全盘重写）

> 补充：**ACP（Agent Client Protocol）**——headless 之外提供自动化服务协议，是 B / D 路径集成的关键抓手。

## 三、八项需求 × DSH 供给对照（核心）

> ⚠️ **本表基于初版八项**（2026-09-06 16:07）。README 定稿版新增 6 项——**会话为单元管理 / 使用成本管理 / 行为安全约束 / 沉淀信息可见 / AI 行为可见 / 时间感知**——**尚未纳入本对照**，待补。
> 其中两项值得警惕：**「行为安全约束」**（DSH 有沙箱分级审批：workspace-write / read-only / danger-full-access）、**「AI 行为可见」**（DSH 有 Trajectory 轨迹）——**这两项 DSH 大概率另有增量**，故本表对 DSH 的增量评估偏保守。

| # | LarryAgent 需求 | 现状 | DSH 能提供什么 | **净增量** |
|---|---|---|---|---|
| 1 | 多模型按需切换 | ✅ 已有 | ✅ 内置 5 适配器 + 多模型路由 | **无增量**（已有，纯重叠） |
| 2 | 工具 | ✅ 已有（少） | ✅ 结构化工具管道（拦截 / 沙箱 / 审批 / 重试 / 规范化） | **有增量**（完整度高一档） |
| 3 | 专家 / 角色 | ⚠️ 部分 | ⚠️ 子代理委托 + 插件机制，但**专家插件要自己写** | **部分**（给机制，不给内容） |
| 4 | 长期 + 短期记忆 | ✅ 已有 | ⚠️ 会话轨迹日志——**原始事件流水，非语义记忆** | **互补不替代**（见 3.1） |
| 5 | **知识库** | ❌ 无 | ❌ **未提供** | **零**（迁移后仍需自建） |
| 6 | 云端部署 / 多端 | ⚠️ 部分 | ⚠️ Web UI + headless + ACP（有形态，部署自己搞） | **小** |
| 7 | **用户画像** | ❌ 无 | ❌ **未提供** | **零**（迁移后仍需自建） |
| 8 | **超长会话一致性** | ⚠️ 弱且机制反向 | ✅✅ **强项**：compaction + resume + fork + 回放 | **显著增量** |

### 3.1 这张表说明什么（WB 读表，不拍板）

1. **DSH 的真增量集中在两端**：工具管道完整度（#2）、超长会话一致性（#8）。其中 #8 恰是 LarryAgent **现状方向性错误**的那一项——DSH 有现成正解（compaction 压缩而非截断丢弃）
2. **三个真缺口里，DSH 只补一个**：#8 补得上；**#5 知识库、#7 用户画像 DSH 一概不管**，迁移了照样从零做
3. **#4 互补不替代**（关键，易误判）：
   - DSH 的 `session log` = **原始事件流水**（append-only，强在回放 / 审计 / 断点续跑）
   - LarryAgent 的 `memories` = **LLM 摘要 + 向量化**（强在跨会话语义召回）
   - 二者解决的是**不同问题**。**迁移 ≠ 获得记忆能力**——换底座后 memory 层仍需自建或双轨并存
4. **#1 纯重叠**：迁移不带来任何新东西

## 四、对上次判断「完全不适合，也没有必要」的检验

这是两个**独立**判断，必须分开看。

### 4.1 「完全不适合」——**说过头了，需修正**

- 原判断依据："DSH = 编码 Agent vs LarryAgent = 通用助手 → 定位错配"。
- **三处事实修正**（2026-09-06）：
  1. DSH **架构通用**——无特权内核、连 Agent Loop 都可换，仅**开箱能力**偏编码（见 §2）
  2. LarryAgent 现有 5 角色**含 `code`**，功能范畴本就涵盖编程
  3. 对标产品 **QoderWork 是通用办公助理**，非纯编码（见 §0.2）
- 故"**完全**不适合"不成立。
- **但错配风险仍在**：DSH 的开箱能力与优化方向围绕编码场景，要做通用办公仍需自建插件——不是"不适合"，是"**不白给**"。

### 4.2 「没有必要」——**翻掉一半**

DSH 有三样东西 LarryAgent **现在没有、且自己造挺费工**：

| DSH 能力 | LarryAgent 现状 | 差距 |
|---|---|---|
| Trajectory 完整轨迹（暂停/分叉/回放/断点续跑） | 无 | 全新能力，从零造工量不小 |
| 权限沙箱 + 高危操作人工审批 | 无 | 涉及安全边界，需专门设计 |
| 插件总线（可插拔可热替换） | 配置驱动的工具框架（BaseTool / SSRF / 降级） | 弱一档，但**能跑、已验收** |

> **但：这是"值得借鉴"，不等于"值得迁移"。**
> 借鉴 = 局部抄思路；迁移 = 换底座。二者成本差几个数量级。

## 六、绕不开的风险（无论选哪条路径）

1. **语言栈冲突**：DSH 是 TypeScript，LarryAgent 后端是 **Python FastAPI**。只要沾 A 或 B，这是成本大头。
2. **preview 阶段**：`0.1.0-rc.7`、官方明示**破坏性变更**、项目仅 3 周大（2026-08-13 至今）。把已过 P4 的 LarryAgent 押在 rc 框架上，返工风险实打实。
3. **记忆层不是搬家，是重建**（见 §3.1-3）：DSH 的 session log 是原始事件流水，LarryAgent 的 memory 是摘要 + 向量。**换底座不等于带着记忆能力一起过去**——走 A 路径须重建 memory 层，或接受双轨并存。

> 补充事实：上云方向的既有共识是「PC 版 C/S，client 在本机、**server 上云**」。若走 A 路径，云端形态与 DSH 的本地 Web UI（127.0.0.1:3080）形态也需重新对齐。
