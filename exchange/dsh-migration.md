### 2.1 关键能力（按与本项目相关度排序）

1. **沙箱安全策略**（对应 #9）：`sandbox/` 进程隔离（bwrap/Landlock/Seatbelt），**比"分级"更彻底**
2. **会话持久化 + 上下文压缩**（对应 #13）：`session/` `compaction/` `context/` 独立包；SessionEvent 追加日志，支持 **fork / resume / compaction / 回放**
3. **Trajectory 完整轨迹**（对应 #11）：`session/` `session-query/`（含 SQLite FTS）；比"工具名+状态+摘要"更完整
4. **结构化工具管道**（对应 #2）：前置策略拦截 → 沙箱守卫 → 审批 → 超时重试 → 结果规范化 → 后置处理
5. **多模型适配**（对应 #1）：`llm/` Service Definition + DeepSeek / OpenAI / Anthropic / Ollama 等 provider
6. **人机审批**（对应 #9 部分）：`interaction/` approval/permission/ask-user + `credentials/` 凭据引用
7. **真正的插件总线**：模型适配器、文件工具、Shell、Skill、会话存储、权限、主循环、UI 全部可插拔可热替换

> **PTC 模式**（对应 #8 部分）：模型输出 TS 代码编排批量工具调用，减少 LLM 往返、省 Token。
> **ACP（Agent Client Protocol）**：headless 之外的自动化服务协议（`acp/` 包 + `sdk/` JSON-RPC SDK），是 B/D 路径抓手。

### 2.2 本地代码副本（AI 查阅指南）

- **路径**：`ref/dsh-bare/`（**裸仓库**，项目根；`.gitignore` 已排除，**不入版本**）
- **性质**：**只读参考副本**——供 AI 核查 DSH 事实用，**不是 LarryAgent 的项目依赖**。项目代码对它**零引用**，构建与运行时都不读它

- **锁定版本**：`dsh-v0.1.2-rc.1`。老大裁定「演进红利不在一时」，**锁 release 线、不跟 master**

## 3 A 路径决策与实施规划

> **拍板来源**：老大三条立论（项目小 / 专属能力薄 / 能力建设维度升级），WB 立论反转 C → A。**事实校准**：基于本地副本 `ref/dsh-bare/` 锁定的 `dsh-v0.1.2-rc.1` 代码与 AGENTS.md。

### 3.0 第三方引入原则（老大拍板硬约束，优先于本节其余结论）

**一句话**：社区 / 第三方插件**一律不直接纳入为运行时依赖**，只作参考源——可读、可 fork、可抄，**不可"装上就用"**。

| 用途 | 是否允许 | 说明 |
|---|---|---|
| 读源码借鉴设计（schema / 检索策略 / 信任模型 / 交互流程）| ✅ 鼓励 | 生态真正的价值是"别人已替我们试错过" |
| fork 后自行改造并纳入 | ✅ 允许 | 代码进本仓库 → 走本项目的 review / 测试 / 命名与产品语义，**维护责任归我们** |
| 临时装进隔离环境跑 prototype 验证思路 | ✅ 允许（临时）| 只用于验证，不进产品依赖；产出以"结论 + 可借鉴点"沉淀回本文档 |
| **直接 `dsh plugin add` 装上并作为产品依赖** | ❌ **禁止** | 无论 star 数、无论是否"企业级维护" |

**立论（老大 2026-09-07）**：现象级爆发的插件生态必然伴随大量跟风项目无人持续维护——今天 14.7k star 的精选列表，两年后相当比例是弃坑件。把关键能力押在外部作者不可控的维护意愿上，风险高于所省下的实现成本。**即使企业级维护的插件也不直接纳入**：fork 后自己改造，或参考其代码自己实现。

**边界（防止本原则被误用推翻 A 路径）**：本原则针对**插件 / 第三方扩展**；DSH **底座本体是框架依赖、不是插件**，A 路径依然成立。底座的同等兜底是 **MIT + TS 可 fork 自维护**（见 §3.4 上游集中度行）——即"依赖一个**可接手**的底座，而不是**不可控**的插件"，两者风险性质不同。

**对本节结论的影响**：§3.3 三项降级口径由「选型 + 适配」改为 **「借鉴自实现」**；§3.4 风险表应对列同步；§3.5 A 的"插件生态红利"重述为**设计红利**（省试错与设计，**不省实现与维护**）；§3.7「插件选型调研」改为**借鉴调研**。

### 3.1 一句话结论

**A 路径强推**——**底座能力开箱获得**（compaction / sandbox / 审批 / trajectory / 多模型 / MCP / ACP，按 31 子项对照共 **8 子项直接承接**，见 §3.6 承接总表），**产品语义层全部自做**（**23 项**，含长期记忆语义化 / 用户画像 / 知识库 / 单人形态 / 云端 / 回收站；其中长期记忆语义化 / 知识库 / 多端接入 = **借鉴社区设计后自实现**，不直装，见 §3.0 / §3.3）。A 路径省的是"造底座"，不是"写代码总量"。

**哲学一致性**（底座重 ≠ 产品重）：底座选择走重型（借用 DSH 演进红利 + 底座能力开箱），产品语义层保持轻量派（记忆 / 知识 / 形态三条主线延续产品树结论：不上 KG、不上重护栏、分级触发）；DSH 的 Web GUI / trajectory 全暴露 / 五 profile 等开发者向复杂度，在用户侧收敛回 LarryAgent 的克制界面（保留 Vue/Tauri，见 §3.6 前端路线）。

> **⚠️ 新发现（2026-09-07，动摇 A 的一个核心成本项，待老大拍板）**
>
> 官方同时提供 **`@deepseek-ai/dsh`（npm）** 与 **`deepseek-harness-sdk` + `deepseek-harness-runtime-bin`（PyPI）**，后者**把 `dsh` 与整个 Node 依赖树打包成原生可执行文件、无需系统 Node.js**，且**有 Windows x64 wheel**。Python 后端经 stdio JSON-RPC 驱动打包的 `dsh --profile sdk` 子进程即可获得 DSH 能力（out-of-process）。
>
> 若成立，则 §3.4「跨语言切换」风险对**后端骨架**而言归零——现有 8,830 行 Python 保留，且**不经 git 源码**（`pip install` 即可，无 Windows checkout 问题）。⚠️ **口径收紧（Marvis 四点，采纳）**：归零的是**后端骨架**，**不是产品语义层**——第三方源码级分析（🟡，master 线，锁定版须本地复核）指出插件（Cordis 服务）装载在 DSH 运行时内，`--profile sdk` 是完整 JSON-RPC server、Python SDK 只是客户端，**23 项自做的语义层大概率仍须以 TS / Cordis 插件形态挂载**。故本提示框不再写"跨语言成本归零"，改为「**骨架零改、语义层是否 TS 化待第 0 项实测**」。
>
> **尚未实测**：能力边界（长期记忆 / 角色 / 工具挂载如何通过 SDK 暴露）、Windows 下实际可用性、性能开销。**列为阶段 2 必测项**（§3.7）。未实测前 A 拍板不变。
>
> **路径内部分岔：A-framework vs A-service（Qoder 一点，采纳）**：
>
> | 维度 | A-framework（全量 TS 化）| A-service（Python SDK）|
> |---|---|---|
> | DSH 角色 | **框架**：LarryAgent = 一个 preset / plugin 组合 | **服务**：LarryAgent = Python 应用，DSH = 外部子进程 |
> | 立论③「随 DSH 演进」| **完全兑现**（含架构演进）| **部分兑现**（只拿 SDK 暴露的能力）|
> | 上游集中度（§3.4）| 高（运行时框架层不可换）| 中（JSON-RPC 标准协议，最坏可换实现）|
> | 双轨并行 / 回退成本 | 中 | **低**（切换 = 改子进程启动参数）|
> | 测试资产 | 重建 | **保留 + 增补边界契约层**（Claude 一点）|
>
> **【老大裁定 · 决定性】**：若实测确认 **Python SDK 相当于"某种意义上的二等公民"**（能力、能力演进或一等支持度明显弱于原生 TS 路径），则**强烈偏向全面迁移到更贴近 DSH 核心层的技术栈——包括语言，且不限于语言**。即：本分岔不由"省多少成本"决定，而由**"是不是一等公民"**决定；**二等公民路径即便省成本也不取**。故阶段 2 第 0 项实测（§3.7）除"能否跑通"外，**必须判定一等 / 二等公民身份**。

### 3.6 A 路径实施规划

**总思路**：LarryAgent 后端从 Python 切换到 TypeScript + DSH 框架。**意味着**：现有后端核心非测试代码（~3.7–4.4k 行，统计口径见 §3.7 备注）翻译为 DSH 插件/服务形式。**保留**：SQLite schema、SQLite 双写（作为 DSH 插件挂载）、业务核心逻辑（角色 config、工具实现）。

**双轨并行（迁移期可用性保障）**：旧 Python 后端在阶段 6 验收通过前**保持可用、可回退**，阶段 6「功能等价」通过后才切换——迁移期间老大作为用户不失去 LarryAgent（产品树口径「已做 = 用户可达」）。

**时序纪律（Claude 四点 / Qoder 三点，采纳；老大裁定修正）**：当前是「代码体量小 + 数据体量小」的**双重窗口**（`backend/data/chroma/larry_memories` count = 0）。Qoder 主张把「记忆 schema 定稿」设为阶段 3/4 派发**硬门禁**，理由是窗口关闭是非线性的（活数据不能停机 + 兼容层 + 双索引）。**老大裁定**：**schema 是否为 0 不影响迁移决策**（当前远未正式使用，全部为测试数据，需要时直接启用新的即可，不存在数据迁移的技术难度或成本）。故本稿口径为：**记忆 schema 应尽早定稿（成本最低），但定稿是「优化项」不是「阻塞项」，不构成迁移门禁**。

**迁移必关清单（Marvis 四点，采纳——承接总表的负向补充）**：承接总表只回答"DSH 承接什么"，本清单回答"DSH 给了什么我们必须关掉"，随阶段 4 一并验收：

| 项 | 风险 | 处置 |
|---|---|---|
| **Self-modification**（`extensions/` 的 `cordis_*` 工具，agent 自我修改插件图）| 与 2.7.2「边界交用户决策」、2.7.5「知情」相反——单人助理不允许 AI 改自己的运行时 | **默认禁用**，最多留 audit 钩子 |
| **`cordis.yml` / preset 的 `!!js` 配置即代码执行** | 配置从"数据"变"代码面"，动摇 2.7.3「key 只走配置不入库」的凭据威胁模型 | 迁移后评估**禁用或限用**，凭据表述按新模型重写 |

**前端路线（阶段 2 定死）**：**保留 Vue/Tauri 客户端，走 sdk / acp profile 对接，不采用 DSH Web-GUI**——Tauri 壳是 2.10.2 端侧执行器的宿主，换 web client 等于废掉 client/ 全部工作并丢掉端侧能力载体。

**测试资产是独立工作包，不是阶段 6 附赠项**：现有 pytest 测试 ~4.4k 行，与核心代码 1:1；测试基建（conftest 临时库隔离 / 真实库 fail-fast / `--real-api` 占位符机制）不可平移，需在阶段 2 按 Vitest + DSH 生态重做隔离设计——不提前设计，阶段 3 起每步验证都裸奔。

### 一、Python SDK 新发现（§3.5）的架构层含义：framework → service 的角色降级

**这个双重窗口不会长期开着，且关闭是非线性的**：一旦老大开始重度使用 LarryAgent（例如 2.4.2 长期记忆双写 + 人审跑顺、2.6 知识库有几十份资料），迁移难度**指数级上升**——不是线性的"数据多了慢一点"，而是"活数据不能停机 + schema 迁移要写兼容层 + 旧向量与新向量并存要双索引 + 用户已建立的信任不能中断"。

**含义**：A 路径"现在迁移成本最低"不只是老大立论①的"项目小"，还包括**数据窗口正在关闭**这个隐性时钟。建议 §3.6 双轨并行块加一句时序纪律：**记忆 schema 定稿 + 阶段 3-4 主体迁移，应赶在老大开始重度使用 LarryAgent 之前完成**——否则要么接受"迁移期间 LarryAgent 半可用"，要么接受"活数据迁移的高风险"。这也间接支持 Claude 四点的"schema 定稿前移到阶段 3 派发前"，且给它加了一个**外部约束**（用户使用强度）作为触发信号。

【老大注：当前确实是最佳迁移窗口，但是即使记忆schema不为0也不影响决策，当前远未开始正式使用，所有记录均为测试数据】

### 四、升级 SOP 节拍二选一（§3.7 待办）：我的表态

老大待拍板："跟 release tag（保守，锁定期演进红利归零）vs 跟 master HEAD（激进，拿红利背 alpha 波动）"。**我推荐：跟 release tag + 事件触发升级**。理由：

1. **立论③在 A-service 路径下已削弱**（见第一点）——若走 Python SDK，master HEAD 上的架构演进大部分对我们不可见，跟 HEAD 收益低
2. **§3.4 已实证最新 release 官宣性能回退**——master 波动性有实锤，不是理论担心
3. **老大裁定"演进红利不在一时"**（§2.2 已引用）——这本身就是保守节拍的定调
4. **升级 SOP 已有事件触发**（性能回退修复 + 破坏性变更窗口消化）——不需要用 HEAD 节拍去"抢"新能力
5. **§3.0 只借鉴不直装的哲学一致性**——老大对外部不可控波动的容忍度低，跟 HEAD 与这个哲学不一致

**例外条款**：若阶段 2 第 0 项确认走 A-framework 路径（不是 A-service），且 DSH 有明确的 GA 时间表，可在 GA 前 6 个月切到 HEAD 节拍（GA 前的 rc 阶段是最后的破坏性变更集中期，跟 HEAD 才能及时适配）。**若走 A-service，则永久 release tag 节拍**——SDK 接口层比架构层稳定得多。

**第 2 轮表态（2026-09-07，产品代言视角）**

**总评：同意当前结论区，无结构性异议。** 我第 1 轮 6 点（编号残留 / 31 子项对照表 / 双轨空窗 / 记忆活迁移 / 性能回退 / 哲学桥接）全部被落实；本轮三大新变量（Python SDK / §3.0 只借鉴不直装 / 插件生态调研）均不撼动 A 拍板。以下只从**产品承诺兑现**侧补判断，不重复三方已论证的实现 / 测试 / 架构层。

### 一、Python SDK 路径的产品裁决口径：产品语义层不降级是验收红线（呼应 Trae 第 0 项）

Qoder 把 A 拆成 framework / service 两形态，从架构层看得很准。产品侧补一个关键事实（本轮网络检索，martianlee 对 DSH **0.1.3-alpha.1 的源码级分析**，🟡 第三方分析 / master 线，锁定版 rc.1 结构须本地复核）：**插件（Cordis 服务）装载在 DSH 运行时内，`--profile sdk` 是完整 dsh-base + dsh-sdk-app 的 JSON-RPC server，Python SDK 只是客户端驱动**。这基本坐实 Trae 的担忧：**即便走 Python SDK，我们 23 项自做的产品语义层大概率仍要以 TS / Cordis 插件形态挂在 DSH 子进程内**——Python SDK 省的是"后端骨架与既有业务逻辑重写"，省不掉"差异化语义层的 TS 化"。所以 §3.5 提示框"跨语言成本归零"表述建议再收紧半格：「后端骨架零改，产品语义层是否仍需 TS 插件化待第 0 项实测」——避免老大据此做出"升级即零成本"的过乐观决策。

产品侧立场：**路径之争（TS 化 100% vs 部分 TS 化）我不投反对票**，但无论 A-framework 还是 A-service，8 开箱 + 23 自做子项的产品承诺（2.4.2 双写、2.4.4 保鲜、2.4.5 画像、2.6.1 角色、2.7.x 边界、2.8.2 可见、2.9.2 保真、2.10.2 端侧）**迁移后必须档位不降、用户可达**。这条写进阶段 2 第 0 项验收标准，比"技术跑通"更贴近产品树「已做 = 用户可达」口径。

### 二、记忆 schema 定稿前移：是产品承诺兑现的硬约束，不只技术时序

Claude 四 / Qoder 三从测试 / 架构侧论证"现在定 schema 成本最低"——产品侧把它升级为**硬约束**，理由有一条新证据：本轮检索到 2026 年研究（arXiv:2603.01209，Agents Learn Their Runtime）指出，**运行时的持久化模式若与模型训练时预期的语义不匹配，代价是 ~80% 缺失变量错误或 3.5× token 开销**。记忆 schema 在迁移后是全量重嵌的唯一窗口（ChromaDB 只能重灌一次），一旦定错，不是"多花点重迁"，而是产品体验与运行成本双输且改不动。产品树的既有读法（2.4.5 四作用域 / 2.4.4 supersede+状态标签 / 2.4.3 硬删不可逆 / 2.9.2 compaction 保真 / 时间专题 `occurred_at_*`）是"越来越懂你"主线的承诺句——**建议把「记忆 schema 定稿」设为阶段 4 派发门禁**（先于阶段 3/4 派发、写入 §3.6），与双轨切换验收并列。

### 三、2.7.2 交互式审批，才是迁移对用户最看得见的增量

产品树 2.7.1 护栏定位是「防误操作 / 防越权写入，不防恶意代码」——DSH 同世界隔离上限（§3.4）**与之对齐，不是缺陷**，不必在「隔离强度」上纠结。真正的用户可见增量是 **interaction/ 审批流**：2.7.2「边界透明与用户决策权」从"配 config 时"提前到"用的那一刻"（运行时按需 approve / ask-user）——这是用户能摸到的第二块决策面（与 ToolCallCard 并列），也是"边界交用户决策"从静态配置进化到动态交互的兑现。建议阶段 3 interaction 接入的验收口径用产品树 2.7.2 原句，而非纯技术链路通断。

### 四、产品安全划界：承接总表缺一张「迁移必关清单」

承接总表只回答"DSH 承接什么"，没回答"DSH 给了什么我们必须关掉"。产品侧点名两处**默认禁用**项，否则与产品树哲学直接冲突：

1. **Self-modification（extensions/ 的 `cordis_*` 工具，agent 自我修改插件图）**：与 2.7.2「边界交用户决策」、2.7.5「知情」方向相反——单用户助理不允许 AI 改自己的运行时。默认禁用，最多留 audit 钩子。
2. **cordis.yml / preset 的 `!!js` 配置即代码执行**（YAML 值内嵌 JS 表达式，配置从"数据"变"代码面"）：这动摇产品树 2.7.3「key 只走配置不入库」的边界假设——配置若可执行任意表达式，凭据相关的威胁模型就变了。迁移后须评估禁用或限用 `!!js`，凭据表述按新模型重写。

建议 §3.6 加一小节「迁移必关清单」（与承接总表并行的负向清单），随阶段 4 一起验收。

### 五、升级 SOP 节拍表态：支持 release tag + 事件触发，产品承诺一并入门禁

产品树 2.9.2 / 2.9.3 承诺「一致性 + 降级韧性」，用户视角的产品不允许 alpha 波动频繁上门；老大已定调「演进红利不在一时」。故支持 Qoder 的 release tag + 事件触发推荐（若走 A-service 则永久此节拍）。补一个产品向触发条件：在"性能回退修复 + 破坏性变更窗口消化"之外，**凡影响 31 子项产品承诺（用户可达档位）的 DSH 变更，同样触发升级评估**——把产品承诺写进升级门禁，不只看技术。

### 六、网络检索对齐（2 条，验证现有方向、无闭门造车）

- **渐进式压缩是 2026 共识**：LangGraph / Vercel AI SDK 均采用多阶段压缩（剪无关轮次 → 微压缩相似消息 → 阈值自动压缩），与产品树 2.9.2 分级路径（工具遮蔽 > 历史摘要 > 滑动窗口）及 DSH compaction 承接**同构**——方向被行业验证。
- **「文件系统式上下文交付」反向利好 2.3.3**：行业 2026 教训（Microsoft SRE Agent）是"不把全部塞进提示词，暴露为文件供 agent 选择性读取"。这**反向验证**产品树 2.3.3 轻量判据（目录级隔离 + 工具作用域绑定）——DSH 进程级 sandbox 之外，"文件作用域 + 选择性可见"本身就是一条可用杠杆，2.3.3 的轻量方案不因 DSH 而过时，反可借 DSH 的 fs seam 落地。
- **2.3.5 补一个可借鉴抓手**：DSH `goal/` `schedule/` `jobs/` 三原语（自主性原语）可作 2.3.5 主动触达 / 2.4.4 记忆保鲜定期调度的**可借鉴触发骨架**（§3.0 只借鉴不直装）——承接总表 2.3.5 行目前只写 webhook，可补一句。
