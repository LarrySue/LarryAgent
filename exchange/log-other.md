## QoderWork · README 产品定位五区审阅意见（2026-09-03）

> **背景**：老大在 README 开头新立了产品定位区（能力 / 约束 / 可见性 / 质量 / 形态），要求从两个方向补充——① 为满足预设想法，还有哪些**值得列出但未列出**的维度；② 已做 / 在做 / 在讨论 / 在计划的工作里，还有哪些**未反映到列表**；并检查条目有无混乱、是否需要拆分重组。范围限定**产品层**，不含项目实施与协作机制。本意见基于 README、HUMAN.md、TODO.md、backend 代码现状与设计文档的交叉核对。

### 一、值得列出但未列出的维度

1. **数据主权 / 隐私边界**（最明显的缺失）
   部署计划已明确"数据落云厂商磁盘、embedding 自有服务器跑、LLM API 是唯一出境通道"，实践中也有 key 不入库、不落日志。对存放私人记忆 / 健康 / 理财对话的个人 Agent，"数据在哪、什么出境"是核心产品承诺而非实现细节。当前五区均无位置，建议在「约束」下单列"隐私 / 数据出境边界"。

2. **可逆性与人类决策权**
   HUMAN 原则 4（明确安全边界而非控制）+ 归档需用户确认 + 文件绝不覆盖 + 软删除回收站，合起来是一个独立产品价值观：**AI 的关键动作要么事前经用户确认、要么事后可撤销、要么至少让用户知情**。该承诺目前被拆散在「约束」「可见性」两区各露一角，未作为维度立起。这是"个人项目、人类至高训导权"在产品层的直接体现。

3. **韧性 / 降级品质**
   "任何组件挂掉不崩、不丢数据、如实告知"——已全系统实践（ChromaDB 降级、搜索降级、LLM 重试、异常统一出口），但「质量」区只收了上下文类质量，韧性无体现。

4. **可扩展性 / 生长性**
   新模型纯配置零代码接入、provider 可插拔、工具挂载契约预留第三方接口。作为"绝对长期项目"，"能一直长"是产品层卖点，建议在「能力」或「形态」占一条。

5. **质量可评估性**
   HUMAN 普通待办"建设评估类代码以服务项目迭代"的产品层含义：记忆召回质量、回答质量要有自己的度量而非体感调参。可作为「质量」的支撑条目。

6. **（存疑，待老大回答）主动性**
   定时任务 / 提醒 / 主动跟进类"AI 先开口"的能力，全项目目前无任何规划痕迹。个人助手类产品几乎最终都会走向这里。若在预设想法内，「能力」区应预留；若明确不要，也值得写一条"不做主动性"来划界。

### 三、条目混乱检查与拆合建议（按严重度排序）

1. **成熟度混杂（最大结构问题）**：「能力」区里已实现（多模型切换）、在建（自动路由 = 意图识别）、纯愿景（用户画像、知识库，后者甚至无任何设计）并列。对照 HUMAN 原则 6（让中途参与的 AI 能正确理解项目），新读者无法区分"产品现状承诺"与"方向宣称"。建议每条标注状态（已实现 / 进行中 / 规划），或拆"当前能力"与"愿景能力"两层。

2. **「约束」与 HUMAN 原则 4 哲学不匹配**："行为安全约束"一名读作"系统替用户管住安全"，但项目哲学是"可以危险，用户要知道哪里危险"。且实际混有两类性质不同的东西：**硬护栏**（文件绝不覆盖——真控制）与**透明+放权**（shell 黑名单、IP 白名单均 config 可调——明确边界交用户决策）。一条装不下，建议拆两条或改区名（如"边界与决策权"）。

3. **"专家（或者叫角色）切换和自动路由"**：术语未定（"或者叫"不应出现在定位文档）；且手动切换（已实现）与自动路由（长期愿景）成熟度悬殊，捆绑一条。建议定死术语、拆开标注。

4. **"知识库"与"长期记忆"边界未说明**：前者是用户主动喂的文档资料（未实现、未见任何设计路径），后者是对话自动沉淀（已实现）。并列易被读成"记忆的两种类型"。建议补一句边界定义，或知识库先降级到愿景层。

5. **"用户画像"层级不对**：它是记忆的衍生物（TODO 原文"从记忆中提炼"），与"长期记忆和短期记忆"并列奇怪，建议作为记忆条目子项。

6. **「质量」定义过窄**：现两条（时间感知、超长会话一致性）全是"上下文供给质量"。建议内部三分：内容/上下文质量（时间感知、长会话一致性、召回质量、事实溯源）、运行质量（韧性降级）、体验质量（交互）。第二部分"已做未列"的大半能归入后两类。

7. **成本"管理"无配套"可见"**：原则 2"成本不能上天"，约束区列了管理（截断、轮次上限），但 token_counter 统计的消耗用户不可见。若成本是核心约束，「可见性」应补"资源消耗可见"。

8. **"沉淀信息可见（可管理）"括号超额承诺**："可管理"意味着能对记忆编辑 / 删除 / 重归档，目前仅 is_active 停用一种操作。建议明确承诺档位或收回括号。

9. **五区框架本身成立，不建议推翻**。唯一可考虑：第一部分的"数据主权 + 可逆性 + 知情决策"合起来是一个**信任基座**维度——可新增第六区「信任」，也可分散归入约束 / 可见性。分散利于五区简洁，集中利于把产品灵魂卖点立起来。个人倾向后者："值得托付"恰是个人 Agent 区别于通用聊天产品的核心。此取舍属产品判断，交老大与 WB 裁量。

### 四、一句话总结

五区骨架健康；最大的两个问题是**成熟度不加标注**（影响所有后续读者对现状的判断）和**产品哲学缺位**（原则 4 的知情决策、数据主权、可逆性——这套东西最有辨识度的部分，目前只在 HUMAN.md 和部署小字里若隐若现，没进定位区）。
