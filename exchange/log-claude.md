## README 定位段（能力/约束/可见性/质量/形态）补充意见（2026-09-04，Claude 产品层视角）

> 背景：老大要求从三方面审视定位段——① 值得列出但没列的方面；② 已做/准备做/讨论中/计划中但没列的；③ 条目是否混乱、需否拆分重组。以下为完整意见，供 WB 整理进定位段。

### 一、值得列出但尚未列出的方面

1. **记忆系统的主线地位被低估**：现有"能力"仅一行"长期记忆和短期记忆"，但项目主线是"越来越懂你"的记忆闭环（会话→归档提取→摘要确认→双写存储→语义召回→保鲜/画像愿景），已实现远超一行：记忆提取（LLM 摘要+用户确认）、双写结构（SQLite 真相源 + ChromaDB 可重建）、跨会话召回、归档/回收站/记忆管理 API。建议"记忆"升格为带子结构的方面，或注明闭环形态。
2. **降级与韧性（做了大量工作却无处安放）**：已实现——ChromaDB 不可用静默降级、搜索失败限流退避→"未能联网核实"降级不中断、无 key/key 失效明确提示、tenacity 网络重试、错误统一出口（不泄漏内部）。这套"接得住失败"的韧性设计在现有五维度无对应位置。建议并入"质量"或单列。
3. **隐私与数据主权（可见性的另一面）**："沉淀信息可见（可管理）"只说半面；另半面是"什么不该被记、谁能看到、数据能否带走"。已做：key 不落盘（占位符机制）、临时目录清理、双写结构（删向量库可重建，数据不绑架于向量库）。建议"可见性"扩为"可见与隐私/数据自主"双向维度。
4. **开放性 / 扩展成本（配置驱动是核心设计）**：加新角色只改 config.yaml+重启、新工具写类+登记、新模型加段——零代码接入是架构级卖点，契合个人项目低维护需求。建议单列"开放性"或并入能力注明。
5. **对话体验本身**：SSE 流式打字机 + 停止生成是 P3 核心交付，"会话为单元管理"完全没提对话过程体验。建议在"会话"条目下注明。
6. **多模型/角色"当前只手动"与愿景区分**："专家切换和自动路由"把已做（手动）与纯愿景（自动路由/意图识别）混一条。建议拆开标注。

### 三、条目审视：混乱 / 拆分 / 重组建议

1. **"知识库"与"长期记忆"语义混淆（建议拆分）**：长期记忆=对话产生经提取（已实现闭环主线）；知识库=用户主动导入资料（从未做过无排期，技术上同走 RAG 但来源语义不同）。建议分开标注状态。
2. **"专家/角色切换和自动路由"含两态（建议拆）**：手动切换 ✅ 已做；自动路由（意图识别）❌ 愿景。同类状态混排问题也存在于"用户画像""知识库"（纯愿景）与"多模型切换""工具挂载"（已做）并列。
3. **"AI 行为可见"缺实现载体**：实际载体=工具卡片（过程可见）、降级提示（"未能联网核实"）、来源 URL 标注。建议条目下注明，否则不可验收。
4. **"约束-行为安全约束"太笼统（建议内部拆层）**：实际三层且都已做——防 AI 乱来（路径沙箱/Shell 黑名单/SSRF/危险操作前说明）、防外部攻击（API Key 鉴权/上云后 HTTPS）、防数据泄漏（key 占位符不入库/临时目录清理/异常不泄漏）。建议拆三条或加"分三层"一句。
5. **"质量"维度偏窄且缺韧性（建议重组为"质量与可靠性"）**：现仅时间感知+超长会话一致性；降级/重试/错误出口/测试分层这些支撑"可靠"的已做工作无归属。
6. **潜在新维度"开放性/可扩展"**：加新模型/工具/角色零代码接入 + 远期第三方工具挂载——个人项目低维护成本的差异化卖点。
7. **潜在新维度"数据自主"**：SQLite 真相源+Chroma 可重建=数据不绑架于向量库、可迁移可备份。可与隐私合并成"数据与隐私"。
8. **"可见性"建议改名"可管理性+隐私"**：沉淀信息可见（可管理）✅ 已支持看改删；补反面（什么不记/谁能看）更完整。

### 总结建议

① 记忆升格为主线带子结构；② 加"降级与韧性"到质量（或单列）——已做工作量最大却最无处安放；③ 加"数据与隐私"维度（或并入可见性改名）；④ 加"开放性"维度（或并入能力注明）；⑤ 拆三处混排（手动 vs 自动路由；知识库 vs 记忆；成本/安全内部层次）；⑥ 全列表加状态标注（✅已做 / 🚧部分 / 🌱愿景）。

一句话：五维度框架本身是好的，但填进去的内容只覆盖了"已做且好归类"的部分；**已做的韧性设计、数据主权设计、开放性设计三块最值钱的家底反而没位置。补维度比改维度更优先。**
