### 任务性质

**设计 + 可运行的最小骨架，不是纯文档。** 交付物必须能跑起来并被命令验证——这是 Tier0 硬红线的程序性强制实现，**不属于"产品业务实现"**，与你「纯测试、不参与实现」的定位不冲突。

### 参照物（先读，本任务是它的 Vitest 等价物）

`backend/tests/conftest.py` —— 现有 Python 侧测试隔离，已稳定运行。**要平移的是七条设计原则，不是代码**：

| # | 原则 | 关键细节（勿简化） |
|---|---|---|
| 1 | **会话级临时配置** | 以真实配置为基底，只替换持久化路径（DB / 向量库），其余行为（models/roles/tools/llm）保持一致 |
| 2 | **环境变量时序** | 必须在**导入任何业务模块之前**就位。Python 靠 conftest 先于收集加载实现；**Vitest 下这一点是否成立须你实测**（ESM 静态 import 提升 vs `setupFiles` / `globalSetup` 的执行顺序）——现有 conftest 的注释明确记着"首版 fixture 就是栽在时序上" |
| 3 | **key 一律占位符** | 临时配置中所有密钥字段递归替换为 `__TEST_PLACEHOLDER__`，**真实 key 不落盘** |
| 4 | **密钥判定用模式匹配** | `k == "api_key" or k.endswith("_api_key")`。⚠️ **严禁子串匹配**（`"token" in k`）会误伤 `llm.max_input_tokens` 这类数值字段，实测替换后测试全挂 |
| 5 | **断言"行为"而非"动作"** | 断言**最终解析出的 DB 路径**不指向真实库，而不是断言"我改过哪个变量"——后者可以被绕过 |
| 6 | **`--real-api` 开关** | 默认跳过真实 API 用例；显式开启才注入真实 key。该模式残留**含 key 明文**，清理告警须升级严重级别 |
| 7 | **清理失败要告警，不静默** | atexit 删除失败时打 stderr（Windows 下 sqlite/chroma 句柄未释放是主因），并区分是否 `--real-api` |

### 硬验收（三条，必须可命令验证——做不到即判未通过，直接上报）

1. **fail-fast 真的会拦**：写一个**故意违反隔离**的哨兵测试（如显式把 DB 路径指回真实库），跑它 → **必须 fail**。这是能证明"不依赖自觉"的唯一方法；只有"正常用例全绿"不足以证明护栏存在。
2. **真实数据未被触碰**：正常测试跑完后，真实库文件（见下）的内容/mtime 无变化。给出比对命令与输出。
3. **无 key 残留**：临时目录内除占位符外无真实 key 明文（`grep` 输出为证）。

> ⚠️ **先查清"真实库"到底在哪**：现有 SQLite 在 `backend/data/larry.db`；但 A-framework 下会话/存储可能落在 `DSH_HOME`（`.dsh-home/`）或 DSH 自己的 `storage/`。**本轮的隔离对象应是"迁移后真实数据会落在的地方"**，可能不止一处。若你查到 DSH 侧的真实数据落点，一并纳入隔离范围；查不清就写明查到哪一步、缺什么。
