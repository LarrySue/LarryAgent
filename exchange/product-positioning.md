## 迭代规则（怎么用这份文档）

1. **结论区（上半）** = 待定稿的共识与决策，由 **WB 综合各方意见后维护**。
2. **讨论区（下半）** = 各方在各自区块下给意见（新增 / 修改 / 否决 / 补充）。

## 一、贯穿性底层原则（非独立域）

> **「信任」不单列为一个域**——它是贯穿所有层面的底层逻辑与方向，渗透于能力树每一处，而非与能力并列的分类项。以下为它在树中的落点（每个落点仍在本域编号下）：

### 2.0 读法

**状态图例**

| 标记 | 含义 | 落地方式怎么写 |
|---|---|---|
| ✅ | 已实现 | 写**怎么做的**（代码 / 配置事实） |
| 🚧 | 部分实现 | 分别写已做的部分与缺的部分 |
| 📐 | 有计划（TODO 有条目 / 讨论稿有方案，但无排期） | 写**怎么计划的**（引用来源） |
| 🗣️ | **老大裁定占位**：有意向、有优先级，但零方案零排期 | 写**裁定内容**（不写落地方式） |
| 🌱 | 愿景，**无承接**（TODO 无条目、exchange 无稿、无设计、**无老大裁定**） | **不写**（如实标注无承接） |

> 🗣️ 与 🌱 的区别在**承接强度**：老大口头裁定是比 TODO 条目更强的承接信号，但弱于「有方案」。**1.3 / 1.4 / 1.5 / 2.6 属此档**，优先级差异写在各条目内。

> **🗣️ 优先级汇总**（老大裁定序列，强→弱）：**2.6 知识库（必要、非常必要）> 1.4 多模态（中）> 1.3 会话沙盒（意向）> 1.5 主动触达（很低）**。四者均无方案、无排期。

- 凡 🚧 项须写明**已做到哪一档**（承诺档位澄清），不以愿景充数。
- **已做 = 用户可达**：代码层存在但无 API / UI 入口的，不算已做，须注明「层内具备、未暴露」。

> **触发依赖**：需以 7.1 时间感知 + 2.2 长期记忆为前提，定案时一并考虑触发源与频率。

### 2.3 二、记忆与知识

> 本域由单行升格而来（项目主线是「越来越懂你」的记忆闭环，一行装不下）。

#### 2.1 短期记忆 ✅

会话内消息历史，超长按 `llm.max_input_tokens` 截断旧消息（见 7.2 — 该机制本身是一致性问题的根源）。

#### 2.2 长期记忆闭环 ✅

- **提取**：`memory/archiver.py::generate_summary` — 归档时 LLM 生成摘要（`POST /api/memory/archive`）
- **人审**：`POST /api/memory/archive/confirm` → `confirm_and_store`，**确认（可编辑）后才入库**
- **双写**：SQLite 为真相源 + ChromaDB 向量库（**结构事实**：可由 SQLite 重建；**重建工具未实现**，属 2.4 计划）；Embedding 用本地 bge-small-zh
- **召回**：新对话按语义相似度检索（`memory/engine.py::get_long_term_memory`），拼进上下文
- **降级**：ChromaDB 不可用时静默降级，不阻塞对话

#### 2.3 记忆可管理 🚧

**已做（用户可达）**：`GET /api/memory` 列表可查；`DELETE /api/memory/{id}` 删除（**硬删，不可恢复**）；编辑发生在 `archive/confirm` 入库前（入库前可编辑）。

**层内具备、未暴露**：db 层有 `deactivate_memory`（`is_active` 软删），但 **API 层无调用方**，用户实际不可达 —— 故「可停用」**不计入已做档位**。

**承诺档位澄清**：当前档位 = **可看 / 可删（硬删、不可恢复）/ 入库前可编辑**，**不含**停用、入库后编辑与重归档。

> **删除不可逆是设计决策，不是信任缺口**：用户主动删记忆的动机通常是想删干净。撤销覆盖由「入库前确认可编辑 + 删除前如实提示不可恢复」保障；**不为记忆另建回收站**（单用户场景下属过度工程）。
>
> 远期想法「记忆浏览器 / 可视化」落点在 6.1，未进 TODO。

#### 2.4 记忆保鲜与代谢 📐

**计划**（`TODO.md` 记忆系统调优段，长期、按使用体感调）
- 检索参数调优（`score_threshold` / `top_k` / 分级阈值）
- 相邻 chunk 合并（避免 LLM 看到被截断片段）
- **保鲜机制**：`last_hit_at` / `priority`，被频繁检索的记忆提升保留权重
- **失效机制（新增钩子，2026-09-06 行业对齐）**：上述字段管「不该忘的别忘」，**管不了「该更新的没更新」**。行业证据：记忆系统加入「遗忘惩罚」后，时间线越长表现越差（周级 −18.2 分 → 季度级 −29.5 分）；删除 / 失效能力实测极低（ForgetEval：Graphiti 4.4–7.0%、Letta 52.7%）。低成本修正 = **版本化 supersede + `valid_from` / `valid_to` + 检索证据打 `current / historical / transition` 状态标签**；**不需要知识图谱**（单人单实例下不划算）
- 向量同步补偿（ChromaDB 恢复后校验 SQLite ↔ Chroma 一致性并补写）
- Embedding 模型迁移脚本（重建 collection + 全量重索引，待触发）

#### 2.5 用户画像 📐

**计划**（`TODO.md` 多场景 AI 架构段，标「长期」）：从记忆中提炼结构化用户画像，注入 system prompt；落地手段含长期记忆按 `source_role` 加权（软隔离）。

> 层级：它是**记忆的衍生物**（TODO 原文即从记忆提炼），故为记忆域子项，不与长期记忆并列。
>
> **隔离强度待定**：`source_role` 加权目前是**软隔离**。若未来转硬隔离（角色间记忆不可见），涉及已入库摘要在角色间的重分属，成本随数据量递增——须与记忆隔离设计一并拍板。
>
> **四作用域 schema（2026 行业已收敛）**：生产记忆系统普遍按 **user / agent / session / app** 四类作用域标识符组织，检索时组合且 user 级权重最高。本项目对应：2.5 用户画像 = **user 级**、1.3 会话沙盒 = **session 级**、`source_role` 角色归属 = **agent 级**——三者是**同一张记忆元数据 schema 的三列**，须一次设计（与 2.4 保鲜 / 失效字段、时间专题的 `occurred_at_*` 同批定：ChromaDB payload 写入后不可改，只能重灌一次）。

#### 2.6 知识库 🗣️

**老大 2026-09-06 裁定：知识库是必要的，非常必要**——当前无方案、无排期，待立项（TODO 无条目、`exchange/` 无讨论稿、无设计）。

与 2.2 的区别：长期记忆 = 对话自动沉淀（已实现）；知识库 = 用户主动导入的外部资料（RAG 同源、产品语义不同）。

> 与 1.4 的升级通道：见 1.4（临时→持久）。
>
> **立项时四个产品决策点（预列，降低将来讨论成本）**：① 首批资料格式范围；② 与长期记忆同 collection 还是分 collection（直接影响召回加权与来源标注）；③ **引用从第一天就有**（无引用则退化为黑盒回答机，与 6.2 来源标注哲学同构）；④ 1.4 升级通道接入位。
> **分型**：个人知识库已收敛为「RAG 应用带聊天」与「聊天应用带 RAG」两型——LarryAgent 属**后者**，且可与 2.2 长期记忆共用同一条召回管线（chunker / 向量库 / 本地 embedding 均现成），故 2.6 与 7.2 同构，同为「既有能力延伸」。

### 2.4 三、能力扩展

#### 3.1 多模型按需切换 ✅

`config.yaml` 的 `models.<name>` 任意新增，`config.py` 自动解析，**加模型零代码**。当前为手动指定，无自动路由。

#### 3.2 工具挂载 ✅

**已做**
- 框架：`tools/base.py`（BaseTool 护栏基类：超时强制 / 错误归一 ToolError / 执行日志）+ `registry.py` 注册 + `config.yaml` `enabled_tools` 开关
- 已挂：`shell` / `file_ops` / `web_search`
- `web_search`：Brave provider（可插拔），2026-09-04 真机验收通过（成功路径 + 关梯子单边挂降级路径双实测）
- **范围边界（首版）**：`web_search` 只取搜索结果的标题 / 摘要 / URL，**不做 `web_fetch` 正文抓取**（代价高：SSRF / 反爬 / 内容清洗 / 阻塞风险，复杂度高一个量级）

**计划（未定案）**：`web-search-design.md` 有多 provider 按角色路由方案（Tavily / Brave / Wolfram）；当前共识是**先用 Brave 攒真实体感**，换 provider 因封装可插拔成本已封死。

#### 3.3 扩展性与零代码接入 ✅

- 加模型 → config 加段（3.1）
- 加工具 → 写类 + 登记（3.2）；第三方挂载契约已留接口
- 加角色 → config `roles` 段 + 重启，`GET /api/roles` 下发，**前端零改动**（2026-09-03 改造验证）

**未做**：以上定制目前只能改 `config.yaml`，无 UI 设置页（见 1.1）。

**方向提示（🌱 无承接，仅留痕、不立项）**：2026 年工具连接的事实标准已收敛为 **MCP**（1 万+ 公开 server、SDK 月下载约 9700 万、OpenAI / Google / 微软 / AWS 全部原生支持、已捐赠 Linux 基金会）。**是否纳入扩展性方向待老大裁定**（是否进位 🗣️）。
> ① **不需要推翻现有框架**：BaseTool + registry + `enabled_tools` 结构上就是干净的适配闸门，接 MCP client 的成本在协议握手与传输层，不在工具模型重构。
> ② **MCP 不外包安全**：行业实测仅 **12.9%** server 评为高信任；2026 年 1–2 月 30+ CVE；有跨租户泄漏与路径穿越事故；社区 server 安装失败率 30–50%。若接入，沿用 5.1 / 5.2 哲学——新 server **默认禁用、按需开启**。

### 2.5 四、角色与路由

#### 4.1 角色切换 ✅

`config.yaml` `roles` 段 + `GET /api/roles` 动态下发 + 前端动态渲染（2026-09-03 改造，加角色零前端改动）。当前角色：default / code / health / finance / science。

**已知缺口**：会话级角色归属无数据模型（`TODO.md` 角色归属设计，老大暂缓）。

#### 4.2 自动路由（意图识别） 📐

**计划**（`TODO.md` 多场景 AI 架构段，标「长期」）：对话开头快速分类意图、自动切换角色。同段另有「根据记忆向量空间分析自动建议新角色」。

> **语义扩展（2026 行业对齐）**：上下文工程把「**路由**」列为一等模式——不只选角色，还选**上下文源**（用哪个知识库 / 哪组工具 / 加载什么记忆）。多域 agent 全量加载会稀释上下文、拉低准确率。故 4.2 的语义应为「意图 → **角色 + 上下文源 + 工具集**」的联合路由，定案时与 2.6（知识库）、3.2（工具集）、4.1（角色）联审。

### 2.6 五、边界与约束

#### 5.1 行为安全硬护栏 ✅

- `file_ops`：工作目录 `file_ops_workspace` 限制读写范围；文件不覆盖
- `shell`：命令黑名单 + IP 白名单 `shell_allowed_ips`
- `web_search`：SSRF 内网拦截 + 硬性超时
- 工具调用轮次上限（防失控循环）

**已知弱点**（`TODO.md` 部署段原文）：ShellTool 黑名单为**字符串包含匹配、可穿透**，加固随「本地能力下沉」一并做（正则 / 词法解析或换沙箱）。

#### 5.2 边界透明与用户决策权 ✅

按 `HUMAN.md` 原则 4（明确安全边界，而非由系统替用户管控）：白名单 / 黑名单 / 工具开关**全部 config 可调**，边界交给用户决策；工具调用过程以 ToolCallCard 展示（见 6.2）。

#### 5.3 凭据与密钥边界 ✅

`config.yaml` 含真实 key 且不入库（`.gitignore` 保护）、`config.example.yaml` 占位符；测试默认占位符、涉 key 路径需显式 `--real-api`；异常统一出口不泄漏内部信息；临时目录用后清理。

#### 5.4 成本约束 🚧

**已做**：`token_counter` 统计（**落日志，未入库**）+ `max_input_tokens` 截断 + 工具轮次上限。

**未做**：无预算 / 限额 / 告警。`TODO.md` 其他长期增强有「chat_service token 累计上限」，但老大标「优先级很低，不做主动处理」。

> **与 6.3 共享同一事实基座**：本条统计与 6.3 是同一件事的两种表述，当前均只落日志。这已保留将来做成本可见所需的**数据底座**——不提前建预算 / 告警系统（单用户下的主动成本管理是过度工程）。

#### 5.5 数据主权与出境边界 📐

**计划**（`exchange/deployment-architecture.md` 草案 + `TODO.md` 部署段）
- 数据落云厂商磁盘；Embedding 在自有服务器跑
- **出境通道不止一条**：LLM API 是其一，**`web_search` 的查询词同样出境**（发往境外搜索服务商）。行业实证（MosaicLeaks，ServiceNow Research 2026-06）：搜索查询序列可被外部观察者反推用户正在研究什么——基础 agent 34% 查询泄漏信息，**能力越强的 agent 泄漏越多（51.7%）**。对健康 / 理财类个人助理尤其敏感：用户问「我这个指标要不要紧」时，**查询词本身就是健康信息**
- **上云硬前置（不满足别上，共 4 条）**：① 强随机 `server.api_key`（P3.4 校验已就绪）② HTTPS（Nginx TLS 终止）③ 上云初期显式禁用 `shell` + `file_ops`（`enabled_tools: ["web_search"]`），防云端误操作云机器 ④ **最小备份 / 导出能力**（见 5.6，老大 2026-09-06 认可升格）

#### 5.6 数据可恢复与可迁移 🚧

**已做（技术事实，未作产品承诺）**：SQLite 为真相源、ChromaDB 可重建 → 数据不绑架于向量库；**会话**为软删除 + 回收站可恢复（1.1）。

**已知边界**：**记忆删除当前为硬删、不可恢复**（见 2.3，属设计决策而非缺口）；故「可恢复」目前只覆盖会话，不覆盖记忆。

**未做**：整体备份 / 导出 / 迁移 — TODO 无条目。

> **已升格为上云硬前置第 4 条（老大 2026-09-06 认可）**：本条不再等「上云后变重要」，而是**上云前必须闭环**——最小备份 / 导出能力与 5.5 的另三条并列。理由：数据可恢复可迁移是「数据不被绑架」里最硬的一条，且最容易「上了云才发现需要」，无过渡期。

### 二、树里没有位置的行业级变化：MCP（建议本轮至少留痕）

**事实**：MCP（Model Context Protocol）2026 年已成工具连接的事实标准——1 万+ 生产服务器、SDK 月下载近 10 亿、500+ 客户端（Claude / ChatGPT / Cursor / VS Code）、已捐赠 Linux 基金会，OpenAI / Google / 微软 / AWS 全部采用。

**与我们的关系**：
- 3.3「扩展性与零代码接入」当前语义是 config 驱动的**内部**注册表；2026 行业里"扩展性"的答案已收敛为 **MCP 兼容**——做 MCP client 意味着免费获得上万现成工具服务器（文件系统 / git / 数据库 / 各类 SaaS），不用每个工具自己写；我们自己的 shell/file_ops 未来也可包成 MCP server 反哺生态。

- **反向提醒（安全不外包）**：MCP 不解决安全——生产实践文献明确指出协议缺身份传播、工具预算、结构化错误，tool sprawl 与恶意 server 的 prompt injection 是主要事故源。5.1 / 5.2 的护栏立场（工具开关、边界透明、用户决策）接 MCP 后一条都不能松，且 MCP server 应默认不全信。

### 二、三个 🗣️ 项的行业对标（2026 资料，均为 Trae / Marvis 未覆盖区）

#### 2.6 知识库——行业已给出成熟产品分型，LarryAgent 的位置很清楚

2026 个人知识库产品收敛为两种分型：**"RAG 应用带聊天"**（AnythingLLM：workspace 为独立知识域、本地向量库、单用户桌面取向）与 **"聊天应用带 RAG"**（Open WebUI：per-chat 上传 + knowledge collections 双轨，默认 Chroma 底座）。对照之下：

- **老大划的 1.4 / 2.6 边界（临时 vs 持久）被行业直接验证**——Open WebUI 的"会话内上传 / 知识集合"双轨就是这个分型的产品化，说明这条边界不是我们的发明而是行业收敛结果，立项时可放心沿用；
- **LarryAgent 属"聊天带 RAG"分型，且有独特资产**：KB 与长期记忆可共用同一条召回管线（chunker / vector_store / bge-small 本地 embedding 全是现成的）——**2.6 与 7.2 同构，也是"既有能力延伸"而非新建**，立项成本比"知识库"三个字听起来低得多；
- **立项时的四个产品决策点**（建议 🗣️ 条目内预列，降低将来讨论成本）：① 首批资料格式范围；② 与记忆同 collection 还是分 collection（直接影响召回加权与来源标注）；③ **引用从第一天就有**——NotebookLM 类产品的护城河就是 per-claim 引用可信，这与我们 6.2 来源标注哲学同构，KB 若无引用会退化成黑盒回答机；④ 1.4 升级通道的接入位。

#### 1.3 会话级沙盒——行业两模式恰好映射老大意向的两半

2026 Agent 沙盒市场两条路线：**E2B**（Firecracker microVM、会话级即抛、强隔离、启动慢、面向不可信代码）与 **Daytona**（Docker 容器、长期有状态工作区、快、弱隔离）。有意思的是，**老大意向的两半分别对应这两个模式**："指定工作空间" = 持久型（Daytona 式），"未指定自动创建" = 即抛型（E2B 式）——直觉与行业分型同构，立项时可直接拿这个二分当框架。

但两家都是商业云且对自托管不友好（E2B 控制面自运维重、Daytona 已闭源不可完全自托管）。**单人 + 自托管场景的启示**：不必上容器/microVM，**目录级隔离 + 工具作用域绑定**（每会话绑定 `file_ops_workspace` 下一个子目录）即可拿到大部分产品价值，复杂度低一个量级，且与现有 pathlib 沙盒同构、是自然延伸。这也给 1.3×8.2 联审钩子补了具体判据：**工具下沉端侧后，沙盒就是端上目录作用域；只有云端保留副作用工具时才需要容器级隔离**（而 5.5 上云硬前置第 ③ 条恰恰是云端禁用 shell/file_ops——两条现有决策合起来，意味着轻量目录方案在可预见的形态下始终够用）。

#### 1.4 多模态输入——行业共识是"分类路由 + 混合管线"，且有一个树里没写的依赖

2026 共识：不存在"一个万能 VLM 打天下"，主流是**按输入类型路由**——文本型 PDF 走解析管线（确定性抽取 + VLM 校验兜底）、截图/图表走 VLM 直读、长文档走检索 + 选择性页面注入。上下文注入三原则与原则 2（成本不能上天）完全对齐：不整文件灌入、先注入结构化提取物（JSON/表格/摘要/页码引用）、需要时才补原图或裁剪。

**树里没写的依赖（建议 1.4 补钩子）**：当前主力模型若无视觉能力，1.4 就**不只是上传 UI 问题，而是模型阵容问题**——要么新增 VLM（3.1 多模型切换的新用例：按输入类型路由模型，与 4.2 意图路由同族），要么走本地解析管线（不加模型但加基建）。这是 1.4 优先级"中"里最重的一块成本，定案时应与 3.1 / 4.2 联审。另：行业管线标配"解析产物落库"，这天然就是 1.4→2.6 升级通道的物质基础（升级 = 保留已解析产物，无需重解析）——升级通道钩子可行，行业已验证。

（3.2 搜索格局按老大指示不在此展开：一句话记录——2026 AI-native 搜索 API 赛道持续活跃、新玩家以准确率基准营销，provider 可插拔已封死切换成本，"先用 Brave 攒体感"策略维持，态势跟踪归 `web-search-design.md` 专项。）

### 三、活样本证词两条（我的独特维度：我本身就是被讨论的东西）

1. **MCP——背书 Trae / Marvis 的"3.3 留痕、不进位、不立项"**。活样本证据：我本身就运行在 MCP 上（本会话即挂着 Microsoft 365 与浏览器自动化两个 MCP server），日常经历的生产模式恰是他们研究到的那套：**懒加载发现**（工具不全量灌上下文、按需取 schema——与 registry + enabled_tools 哲学同构）、统一调用封装、权限门。从每天被 MCP 服务的产品视角给一条活样本判断：**BaseTool + registry + config 开关在结构上就是干净的适配层，未来接 MCP client 的主要成本在协议握手与传输层，不在工具模型重构**——3.3 钩子文案可按此口径写，安抚"要不要推翻现有框架"的顾虑（不用）。
2. **1.5 主动触达——我本身就是"主动触达已产品化"的样本**（定时任务体系：一次性 / 间隔 / cron 三种调度 + IM 通道委托投递）。背书 Trae 的三件事拆解（触发引擎 / 触达通道 / 审批模型），并从活样本经验**补第四件事：missed-run 语义**——设备休眠、后端下线期间错过的触发，恢复后是补跑全部、只补最近一次、还是跳过？这在云端常驻后端里不存在，但 LarryAgent 的形态（8.1/8.2 端云分工）使**触发引擎的位置直接决定 missed-run 是不是必答题**：引擎在云端常驻则问题很薄，在端侧则必须有显式策略。建议 1.5 钩子补一句「触发引擎位置与 8.2 联审；missed-run 策略为必答产品决策」。投递侧活样本细节佐证 Marvis：主动消息应**委托到用户已在的通道**而非自造推送基建——我们 PC 系统通知 + PWA push 的组合够用。
